# OneBase Digital Twin — Operational Twin: план интеграции (этап 1)

Дата: 04.11.2026. Основа — ТЗ «ONEBASE DIGITAL TWIN — OPERATIONAL TWIN» и модель территории `factory-3d.html` (10 корпусов, ворота на юге,
проезд до Цеха 1). План составлен до изменений кода, по результатам изучения backend, frontend, документации и отчётов разделов.

## 1. Архитектура OneBase, на которую ложится двойник

| Слой | Что есть | Что берёт двойник |
|---|---|---|
| Backend | .NET 10, ASP.NET Core, EF Core + PostgreSQL; сервисы разделов в `OneBase.Application` (Work, Hr, Procurement, Sales); права — коды в JWT (`perm`), доступ к данным решают сами сервисы по контексту пользователя (`WorkContext`, `HrContext`, `ProcurementContext`) | те же сервисы и контексты — двойник ничего не считает по-своему |
| Отделы | `public."Departments"` (Guid `Id`, `Code`: sales, production, supply, finance, marketing, hr) | постоянный идентификатор отдела |
| Склады | `procurement."Warehouses"` (один «Центральный склад», Guid), склад готовой продукции «Завод» в Linko (`linko."Stocks"`, `Id`) | постоянные идентификаторы складов |
| Frontend | Next.js 16 (App Router), React 19, Tailwind 4, тёмная «стеклянная» тема по умолчанию, токены в `globals.css`; данные страниц — с сервера (`apiTry`), из браузера — через `/bff`; обновление — `router.refresh` / опрос при видимой вкладке | страница `/twin`, тот же каркас, токены и опрос |
| Языки | ключ — русский текст, словари `i18n/uz/*.ts`, кириллица строится автоматически | новый словарь `i18n/uz/twin.ts` |
| Демо-данные | `lib/demo-data.ts` (карточки отделов на `/departments`) | **не используются** |

## 2. Какие данные есть, а каких нет (инвентаризация)

Права — те же, что у разделов. «Нет доступа» — данные есть, но у пользователя нет права; «Нет данных» — в OneBase их нет.

| Показатель карточки (ТЗ) | Источник в OneBase | Право | Состояние |
|---|---|---|---|
| Производственный план, фактический выпуск, % выполнения, загрузка | — (в Linko и OneBase выпуска нет, `docs/ai-data-map.md`) | — | **Нет данных** |
| Отгрузки завода (первичка) — рядом с производством, **не выпуск** | `PrimaryService` (`/api/sales/primary`) | `sales.read` | есть (план — если загружен) |
| Количество сотрудников, явка, опоздания | Verifix: подразделения, привязанные к отделу (`HrReference.DepartmentCode`, с дочерними), `HrService.OverviewAsync` | `hr.read` или руководитель отдела | есть, если подразделения привязаны |
| Пользователи OneBase отдела | `Users.DepartmentId` | `users.manage` | есть |
| Активные / просроченные / на проверке / заблокированные задачи | `WorkTaskService` (`/api/work/departments`, `/api/work/overview`) | `work.tasks` | есть |
| Заявки на снабжение: открытые, на согласовании, срочные, просроченные к закупке | `ProcurementRequestService.SearchAsync`, `ProcurementPurchaseService.ToBuyAsync` | заявки — по видимости раздела «Заявки»; просрочка — снабжение, директор | есть |
| Потребность в сырье | открытые заявки с категорией «Сырьё» (`raw_materials`), позиции «Сырьё» на складе ниже минимума | как выше; склад — `procurement.warehouse/read/manage` | есть |
| Состояние складских запасов | склад снабжения: позиции, ниже минимума, нет в наличии, к выдаче (`ProcurementStockService.SummaryAsync`); склад «Завод» (готовая продукция): кг, дни покрытия, дефицит SKU (`StockService`) | склад снабжения — как выше; «Завод» — `sales.read` | есть; стоимость запасов — **Нет данных** |
| Бюджет подразделения | — (бюджетов в OneBase нет) | — | **Нет данных** |
| Фактические расходы | только закупки отдела через снабжение за месяц (`ProcurementInsightService.ExpensesAsync`, строки заказов с НДС) — подписываются как «Закупки», не как все расходы | снабжение, директор | есть частично |
| Продажи: выполнение плана, прогноз, выручка, АКБ, проблемные агенты | `SalesDataLoader` → `OverviewView` (кэш раздела) | `sales.read` | есть |
| Финансы: дебиторка, просрочка (ПДЗ), оплаты месяца | `SettlementsService` → `DsoCompute` | `sales.read` + `finance.read` | есть |
| Маркетинг: кампании, лиды, рекламные расходы | — | — | **Нет данных**; рядом — акции (скидки во вторичке, `PromoService`, `sales.read`) |
| Проблемы и предупреждения | просроченные и заблокированные задачи, отсутствующие и опоздавшие, позиции ниже минимума, просроченные закупки, находки AI (`AiAlerts`, категория = код отдела; правила есть только для продаж и снабжения) | по правам источников | есть |

## 3. Решения

### 3.1. Объекты и постоянные идентификаторы

- Здания модели — постоянные ключи `A`…`J` из `factory-3d.html` (геометрия — в коде фронтенда, `lib/twin/site.ts`; данные модели не меняются).
- Привязки хранятся в OneBase (новая схема `twin`, только добавление таблиц):
  - `twin."Objects"` — ключ здания и его название (по умолчанию — из модели, администратор может переименовать: «Цех 1» → настоящее имя);
  - `twin."ObjectLinks"` — связь здания с сущностью: `DepartmentId` → `Departments`, `WarehouseId` → `procurement."Warehouses"` (внешние ключи) или
    `LinkoStockId` — склад Linko (готовая продукция «Завод»). Ровно одно из трёх в строке.
- В одном здании может быть несколько отделов (офис: продажи, финансы, HR…) и склад.
- Привязки меняет администратор пользователей (`users.manage`, как руководителей в «Настройки → Отделы»); каждое изменение — в журнал аудита.
- Начальных привязок нет: какой корпус чей — знает только компания. Пока привязок нет, двойник показывает здания как «Не привязано» и предлагает
  администратору привязать. Никаких «угаданных» отделов.

### 3.2. Backend: модуль Twin (только чтение данных разделов)

- `TwinService` (`OneBase.Application/Twin`) собирает снимок двойника, **вызывая те же методы сервисов, что и контроллеры разделов**, с контекстом
  текущего пользователя. Каждый источник — в своём scope параллельно (DbContext не потокобезопасен) и в своём `try`: нет права — `noaccess`,
  ошибка — `error` (остальные блоки работают).
- `GET /api/twin` — снимок: здания и их привязки, общие KPI предприятия, показатели по отделам и складам, свежесть источников, время сборки.
  Числа и коды, без русских подписей (подписи и перевод — на фронтенде).
- `GET /api/twin/options` и `PUT /api/twin/objects/{key}` — справочник для привязки (отделы, склады) и сохранение привязок (`users.manage`).
- Сам раздел — с общими правами компании (как «Обзор»: `workspacePermissions`).
- Бизнес-логика, данные и настройки разделов не меняются; новые таблицы — одной миграцией `Twin1_Objects`.

### 3.3. Frontend: страница `/twin` «Цифровой двойник»

- 3D-сцена — порт `factory-3d.html` на npm-пакет `three` (вместо CDN r128); загружается только на клиенте (`dynamic(..., { ssr: false })`).
  Цвета сцены — из токенов темы (тёмная и светлая), фон страницы просвечивает.
- Поверх модели: верхняя полоса KPI предприятия, переключатель слоёв, подписи-индикаторы на зданиях (статус и значение слоя), легенда,
  «3D / План сверху / Сбросить вид», время обновления. Справа — контекстная панель выбранного здания (на телефоне — шторка снизу).
- Выбор здания — плавный перелёт камеры; без выбора панель показывает список объектов территории (доступ к зданиям без мыши).
- Из карточки — переход в модуль: «Продажи», HR, «Снабжение», склад, задачи отдела, заявки, ПДЗ.
- Автообновление: опрос `/bff/api/twin` раз в минуту, пока вкладка видна, и кнопка «Обновить»; камера и выбор при обновлении не сбрасываются.
- Пункт меню «Цифровой двойник» после «Обзора».

### 3.4. Слои и цвета

Цвет здания в слое — худший из статусов привязанных к нему отделов/складов по показателю слоя. Серый — «Нет данных» (или нет доступа),
приглушённый — здание не относится к слою, синий — данные есть, нормы нет (только сведения).

| Слой | Показатель | Зелёный / жёлтый / красный | Основание |
|---|---|---|---|
| Все | худший статус из слоёв ниже | — | — |
| Production | выпуск и план выпуска | всегда серый «Нет данных» | данных нет |
| Warehouse | склад снабжения: позиции ниже минимума / нет в наличии; «Завод»: SKU с дефицитом | нет проблем / ниже минимума или дефицит / нет в наличии | правила склада снабжения и «Рек. остатка» |
| Supply | заявки отдела | нет просрочек / есть срочные открытые / просрочена дата закупки | «К закупке» снабжения |
| Finance | ПДЗ (финотдел); закупки отделов — сведения | нет ПДЗ / — / есть ПДЗ | как плитка «Просрочено (ПДЗ)» на странице DSO |
| HR | явка сегодня по подразделениям отдела | ≥ 80% / 70–79% / < 70% | правило HR (как на главной) |
| Sales | выполнение плана месяца (в идущем месяце — прогноз) | ≥ 90% / ≥ 60% / ниже | `ExecutionLevelOf` раздела «Продажи» |
| Marketing | кампании, лиды, расходы — нет; акции — сведения | серый / синий | данных нет |
| Tasks | просроченные задачи отдела | нет / есть просроченные / просрочено ≥ 25% открытых | просрочки красные на «Обзоре»; порог 25% — новый, указан в легенде |

## 4. Порядок реализации (приоритеты ТЗ)

1. **Интеграция 3D-модели** — `three`, сцена, камера (вращение, сдвиг, масштаб, план сверху, плавные переходы), подписи, тема.
2. **Привязка зданий** — таблицы `twin`, миграция, API привязок, редактор в панели здания, аудит.
3. **Общие KPI** — продажи (выполнение и прогноз, выручка), первичка, явка, задачи, заявки, склад, ПДЗ, выпуск — «Нет данных».
4. **Операционные карточки** — по каждому привязанному отделу и складу: показатели из таблицы раздела 2, проблемы и предупреждения, переходы в модули.
5. **Реальные данные** — `TwinService` через сервисы разделов, права пользователя.
6. **Цветовая индикация** — правила раздела 3.4, легенда.
7. **Информационные слои** — 8 слоёв + «Все».
8. **Автообновление** — минутный опрос при видимой вкладке, «обновлено N мин назад», свежесть Linko и Verifix.

## 5. Проверка

- Backend: тесты на настоящем PostgreSQL (`ONEBASE_TEST_POSTGRES`, временная база): привязки (права, проверка ключей и целей, аудит),
  снимок (без права — `noaccess`, показатели отдела совпадают с сервисами разделов, просрочки и заявки по отделам).
- Frontend: `npm run typecheck`, `npm test` (чистые функции слоёв и цветов), `npm run build`.
- Запуск: API на отдельном порту с `Ai__Safety__BlockPaidCalls=true`, страница `/twin` в браузере, тёмная и светлая темы, телефон.

## 6. Следующий этап (не входит в этап 1)

AI-аналитика двойника, прогнозирование и симуляция сценариев. Для полноты двойника нужны данные, которых в OneBase нет: модуль производства
(план и факт выпуска, загрузка линий, простои), бюджеты и расходы отделов (модуль «Финансы», туда же — платежи поставщикам), маркетинг
(кампании, лиды, расходы). Когда они появятся, карточки заполнятся без переделки сцены: показатели приходят из `TwinService`.
