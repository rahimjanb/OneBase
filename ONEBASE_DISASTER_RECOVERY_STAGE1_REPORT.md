# Disaster Recovery — этап 1: полная резервная копия

Дата: 07.11.2026. План — [IMPLEMENTATION_PLAN_DISASTER_RECOVERY.md](IMPLEMENTATION_PLAN_DISASTER_RECOVERY.md), инструкция для
администратора — [docs/disaster-recovery.md](docs/disaster-recovery.md).

## Что сделано

Одна команда снимает всю систему в один зашифрованный набор:

```bash
bash deploy/onebase-backup.sh backup --keep 14
```

| Часть | Как |
|---|---|
| PostgreSQL | `pg_dump -Fc` в экспортированном снимке (`pg_export_snapshot`); **строки каждой таблицы** и список миграций считаются в том же снимке — сверка после восстановления будет точной; роли кластера — `pg_dumpall --globals-only --no-role-passwords` |
| MinIO | все объекты бакета через собственный S3-клиент (AWS SigV4, только стандартная библиотека): SHA-256 и Content-Type каждого объекта; список берётся после снимка базы — всё, на что ссылается дамп, в нём есть |
| Qdrant | снимок каждой коллекции через REST API, точный счёт точек, параметры коллекции; временный снимок в Qdrant удаляется |
| Конфигурация | `.env`, все `docker-compose*.yml` проекта (в том числе override вне git), `crontab`, версии ОС / Docker / Compose / Python, образы сервисов с ID и digest |
| Код | `git bundle` текущего коммита; если на сервере правили файлы — `worktree.patch`; неотслеживаемые файлы перечислены в манифесте |
| Манифест | версии, счётчики, SHA-256 каждого файла; открытая часть (`manifest.public.json`) — без секретов и персональных данных |
| Шифрование | `age` на открытые ключи (`recipients.txt`); на сервере закрытого ключа нет; поток tar сразу в `age` — открытого архива на диске нет |
| Набор | `payload.tar.age` + `.sha256` + `manifest.public.json` + `onebase-restore.pyz` (программа той же версии) |

Защита от ошибок:

- предпроверка места (≈2× база+файлы+векторы и 1 ГБ запаса) — до начала;
- блокировка от двух одновременных запусков;
- незавершённый набор — `*.partial`, при ошибке удаляется; временный каталог с открытыми данными удаляется всегда;
- в конце набор проверяется (состав, формат age, SHA-256) и только потом получает своё имя;
- `last-backup.json` — `success` / `failed` с причиной; журнал `backup.log`;
- значения секретов из `.env` маскируются в журнале и тексте ошибок, плюс шаблоны (закрытый ключ age, JWT, токены ботов);
- ротация — только с `--keep N`, только наборы этого инструмента, только после успешного нового; старые `*.dump` не трогаются.

Ещё: `init-key` (пара ключей восстановления, закрытый ключ — забрать с сервера), `verify` (без ключа — целостность, с ключом —
расшифровка и SHA-256 каждого файла).

## Проверка

**Модульные тесты** (Ubuntu 24.04, Python 3.12, age 1.1.1) — 10 из 10: подпись S3 совпадает с примерами из документации AWS
(GET Object и ListObjects), кодирование кириллицы и спецсимволов в ключах, разбор `.env` как в compose, маскирование,
манифест и обнаружение порчи, ротация (старые `*.dump` и `.partial` не трогаются), шифрование туда-обратно и отказ чужому ключу.

**Учебный сервер** — чистый Ubuntu 24.04 в WSL2 (`onebase-dr-src`), свой Docker CE 29.9.3 / Compose 5.7.0, OneBase с текущего
коммита `b72af60` собран и запущен как на сервере; Telegram и синхронизации выключены, туннеля нет. Учебные данные: 47
объектов MinIO (кириллица и пробелы в именах, пустой файл, `+ & =`, 20 МБ, вложенные папки), 250 точек Qdrant (1536, Cosine).

## Что выяснилось по ходу

- **Порты.** Инструмент обращается к MinIO и Qdrant по адресу контейнера в сети проекта, а не `127.0.0.1`: так он попадает
  ровно в свой проект (на учебной машине рядом работает Docker Desktop с опубликованными портами). На учебных серверах порты
  сервисов не публикуются, сайт — `127.0.0.1:18080`.
- **Docker 29 (хранилище containerd).** Поле Image у `docker compose ps` — digest, по которому образ не находится; имя образа
  берётся из настроек контейнера.
- **Windows PATH в WSL.** В новом дистрибутиве `docker` находился как программа Docker Desktop; подстановка Windows PATH в
  учебных дистрибутивах выключена (`/etc/wsl.conf`), Docker — свой.

## Как начать на сервере

1. `sudo apt install -y age`
2. `cd ~/onebase && git pull` (после того как этап попадёт в main)
3. `bash deploy/onebase-backup.sh init-key` → закрытый ключ скачать, сохранить, удалить с сервера.
4. `bash deploy/onebase-backup.sh backup --keep 14` — первая копия.
5. `crontab -e` — строка из `docs/disaster-recovery.md` вместо `deploy/backup.sh`.
