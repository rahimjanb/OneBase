# OneBase — HR Recruitment AI: аудит и план

Цель: AI-рекрутер, который принимает заявки на сотрудников, ведёт вакансии, получает кандидатов из HH.uz и Telegram, сам
переписывается с кандидатами **через уже подключённый пользовательский аккаунт Telegram** (тот же механизм, что у продаж),
оценивает резюме, назначает собеседования и передаёт HR только исключения.

Статус: **все этапы 0–7 сделаны 08.11.2026** — [отчёт этапа 1](ONEBASE_HR_RECRUITMENT_PHASE1_REPORT.md), руководство — [docs/recruitment.md](docs/recruitment.md).
Решение 08.11.2026 (Р1): **у HR отдельный номер**, подключённый тем же механизмом. Production, сессии и авторизации Telegram не менялись.

## 0. Главное

1. **Telegram-интеграция есть и подходит.** Пользовательский аккаунт (MTProto, WTelegramClient), вход по номеру, коду и паролю
   2FA, сессия зашифрована в базе, приём сообщений переживает перезапуск, чаты, отправка текста и файлов, ошибки и ограничения
   Telegram разобраны. Второе подключение, второй вход и вторая сессия для HR **не нужны и не делаются**.
2. **Но сейчас она «на одного хозяина».** Все входящие идут одному потребителю — AI-агенту продаж (`TelegramAgentWorker` →
   `TelegramAgentService`). Чтобы HR работал на том же аккаунте, перед агентом продаж нужен **маршрутизатор диалогов** — это
   главное изменение этапа 1. Продажи при этом не меняются: всё, что не закреплено за HR, идёт им, как сейчас.
3. **Рекрутинга в OneBase нет совсем**: ни вакансий, ни кандидатов, ни резюме, ни собеседований, ни заявок на сотрудника. HR
   сейчас — зеркало Verifix (сотрудники, табель, посещаемость; только чтение) и одно право `hr.read`.
4. **Календарь есть** (`work.CalendarEvents`), но без свободного времени, напоминаний и внешних участников — расширяем его, а не
   делаем второй.
5. **OneBase — одна компания, арендаторов (tenant) нет**: слова Tenant нет ни в одной строке кода. «Изоляция» здесь — подразделение
   и права, а не `TenantId`. Вводить мультиарендность ради HR не предлагаю; разделение продаж и HR делается на уровне диалога.
6. **Главный риск для продаж — ограничение аккаунта Telegram за спам** (`PEER_FLOOD`). Аккаунт общий: если HR начнёт писать
   незнакомым людям и на него пожалуются, Telegram ограничит **весь аккаунт** — перестанут уходить автоотчёты ТП, рассылки и
   ответы агента продаж. Поэтому: никаких первых сообщений незнакомым по умолчанию, свой лимит отправки HR на аккаунт и —
   решение за вами — отдельный номер для HR, подключённый **тем же механизмом** (раздел 13, Р1).
7. **HH.uz** — только официальный API работодателя: приложение регистрирует работодатель на dev.hh.ru, каждый метод и права
   проверяются по документации на этапе 4. Без регистрации приложения и входа работодателя этап 4 не начать.

## 1. Существующая архитектура Telegram

```
my.telegram.org: api_id + api_hash ──► строка интеграций «telegram» (TelegramCredentialsStore; api_hash — Data Protection)

«Настройки → Telegram» ──► TelegramController /api/settings/telegram ──► TelegramAccountService
      (аккаунты, вход номер → код → 2FA, проверка, выход, пользователи агента, чаты, настройки агента, журнал)

WTelegramGateway : ITelegramGateway   — singleton, ОДИН клиент WTelegram.Client на аккаунт на весь процесс
   │  сессия ⇄ telegram.Accounts.ProtectedSession (Data Protection), состояние приёма ⇄ telegram.Accounts.UpdateState
   │
   │  ВХОДЯЩИЕ: UpdateManager → OnUpdateAsync → TelegramInbox (очередь в памяти, 1000, DropOldest)
   │                                                 │
   │                                       TelegramAgentWorker — до 4 сообщений одновременно, в одном чате — по очереди
   │                                                 │
   │                                       TelegramAgentService.ProcessAsync — AI-агент ПРОДАЖ
   │                                         → telegram.IncomingMessages (уникально аккаунт × чат × сообщение)
   │                                         → фильтры (свои, боты, каналы, старше 30 мин, группы без обращения, права)
   │                                         → консультант OneBase / «только отправленные данные» → ответ
   │
   │  ИСХОДЯЩИЕ (SendAsync) — три независимых отправителя:
   ├── TelegramAgentService       — ответы агента
   ├── TelegramCampaignRunner     — рассылки (очередь telegram.CampaignRecipients, пауза 5 с на аккаунт, FLOOD/PEER_FLOOD)
   └── TelegramReportSender       — автоотчёты (telegram.ReportDeliveries, уникальные ключи «запуск × день × чат × область»)

TelegramConnectionWorker — при запуске и раз в 5 мин поднимает аккаунты по сохранённым сессиям, находит Telegram ID по username,
                           раз в час обновляет чаты (TelegramChatSync → telegram.Chats)
```

Подробное описание поведения — [docs/telegram.md](docs/telegram.md).

## 4. Сессия и авторизация

- `api_id` открыто и `api_hash` (Data Protection) — в строке интеграций `telegram`; не в `.env`.
- Вход: номер → код → пароль 2FA. Код и пароль уходят на сервер один раз и **нигде не сохраняются**; номер — зашифрован.
- Сессия MTProto — `telegram.Accounts.ProtectedSession`: шифрование библиотеки + Data Protection. Восстанавливается без кода по
  известному `user_id`; повторный вход при сбое запрещён (`reloginOnFailedResume: false`) — код сам на телефон не придёт.
- Один аккаунт Telegram — одна запись; **один клиент на аккаунт на весь процесс**; OneBase рассчитан на один экземпляр backend
  (две копии с одной сессией разорвут её — `AUTH_KEY_DUPLICATED`).
- `Telegram:Enabled=false` (локально) и `Recovery:Isolated` (копия для проверки) — клиент не поднимается вовсе.

**HR ничего из этого не меняет**: не создаёт вход, не трогает сессии, не запускает свой процесс или контейнер с клиентом
Telegram. Всё, что делает HR в Telegram, идёт через тот же `ITelegramGateway` внутри того же процесса API.

## 5. Поток входящих и исходящих

**Входящие.** Telegram → `UpdateManager` (порядок без пропусков) → `OnUpdateAsync` берёт только новые сообщения (правки и прочие
события — нет), определяет чат (из памяти или `telegram.Chats`), запоминает документ для скачивания и кладёт `TelegramIncoming` в
`TelegramInbox`. Состояние приёма сохраняется через 5 с отдельно. `TelegramAgentWorker` забирает сообщения (4 одновременно, в
чате — по очереди) и вызывает агента продаж; тот регистрирует сообщение в `IncomingMessages` и решает, отвечать ли.

**Исходящие.** Три независимых отправителя (агент, рассылки, автоотчёты) вызывают `SendAsync`. У каждого — свои статусы и
защита от дублей: строка «отправляется» → после сбоя «неизвестно, дошло ли» **без автоповтора**. Короткий FLOOD_WAIT (до 10 с)
библиотека выжидает сама; длинный — ошибка `Flood` с временем ожидания.

**Чего не хватает для HR** (найдено в коде):

| Пробел | Почему важно для HR |
|---|---|
| Текст входящих не хранится (только метаданные; вопрос и ответ — в журнале агента продаж) | нет истории переписки с кандидатом |
| Очередь входящих — в памяти; состояние приёма сохраняется независимо от обработки; строки `received` после перезапуска не дообрабатываются | для продаж приемлемо (ответ старше 30 минут не нужен), сообщение кандидата терять нельзя |
| Вложение скачивается только из памяти (последние 200 документов, до перезапуска) | резюме нужно сохранять в MinIO сразу при получении |
| В `TelegramIncoming` нет «ответ на какое сообщение» (только «обратились ко мне») | нельзя понять, что человек ответил на пост вакансии |
| Фото (`MessageMediaPhoto`) не передаются | резюме фотографией не увидим (на первом этапе — ок) |
| Нет чтения истории чата, ссылки на сообщение, сведений о профиле | история диалога после сбоя, ссылка на публикацию |
| Нет общего лимита отправки на аккаунт: модули шлют независимо | HR добавит нагрузку на тот же аккаунт |
| Очередь в чате — `SemaphoreSlim`, порядок не гарантирован; ждущее сообщение держит общий слот | два быстрых сообщения кандидата могут обработаться не по порядку; долгий ответ HR занимает слоты продаж |

## 6. Как HR безопасно делит аккаунт

```
TelegramInbox ──► TelegramMessageRouter ──┬──► «Продажи»: TelegramAgentService (без изменений)
                (замок на чат — общий)     ├──► «HR»: RecruitmentConversationHandler (этап 3)
                                           └──► «Не распределён»: никто не отвечает; видно HR и администратору
```

**Хозяин диалога** — строка `telegram.Conversations` (уникально аккаунт × чат): подразделение, тип, статус, AI или вручную,
ответственный. **Строки нет — диалог у продаж, как сейчас**: заполнять таблицу для существующих чатов не нужно, поведение продаж
не меняется.

Правила маршрутизатора (по порядку, без AI на первом этапе):

1. Чат закреплён за подразделением — туда.
2. Признак HR в новом чате → диалог создаётся за HR, дальше все сообщения этого чата — HR:
   - ответ на сообщение вакансии, опубликованное OneBase (номер сообщения есть в публикациях);
   - код вакансии в личном сообщении (из текста поста: «напишите #V12»);
   - кандидат, которому HR уже написал (Telegram ID подтверждён кандидатом).
3. Человек есть в списке пользователей агента продаж и при этом дал признак HR → «Не распределён» (решает человек), а не
   молча к рекрутеру.
4. Иначе — продажи (как сейчас).
5. Сменить хозяина диалога может только человек (HR или администратор) — с записью в аудит.

Изоляция:

- агент продаж не получает HR-диалоги вовсе, рекрутер — диалоги продаж; подсказка рекрутера собирается только из данных подбора
  (вакансия, кандидат, его сообщения), инструментов продаж у него нет;
- HR-переписка не попадает в журнал агента продаж (`AgentExecutions`) и в «Материалы» продаж;
- в интерфейсе HR — только диалоги HR, по правам HR;
- замок на чат общий: один чат никогда не обрабатывают два подразделения одновременно; гонку «кто первый закрепил чат» решает
  уникальный индекс.

Отправка HR — через свою очередь в базе (`telegram.OutgoingMessages`, этап 3): ключ идемпотентности (диалог × шаг), статусы
`pending → sending → sent | failed | unknown`; `unknown` — без автоповтора, как у рассылок. Лимиты аккаунта для HR: пауза между
сообщениями, новых диалогов в день, сообщений в день. `PEER_FLOOD` или длинный `FLOOD_WAIT` → вся отправка HR на аккаунте
останавливается, HR получает исключение; продажи этим не останавливаются (но ограничение Telegram, если оно наступило, касается
всего аккаунта — отсюда Р1).

**Какие подразделения работают с аккаунтом** — `telegram.AccountDepartments` (аккаунт × подразделение, включено, лимиты). По
умолчанию — только продажи. HR на аккаунте включает администратор. Это же позволяет дать HR отдельный номер без единой строки
другого кода.

- все существующие `TelegramTests`, `TelegramRulesTests`, `TelegramReportDbTests` — **без изменений**;
- нет строк `Conversations` → каждое сообщение у агента продаж, ответы те же, что раньше;

- смена хозяина — только через сервис, с записью в аудит;
- `Telegram:Routing:Enabled=false` → прежний путь.

- **Рекрутер «как живой»**: пауза перед ответом и «печатает…», 1–3 коротких сообщения, вопросы отбора по одному (агента и вакансии), опора на
  резюме, ответы кандидата — в отклик; написал ещё до ответа — ответ на всё сразу; вне рабочего времени — утром. На прямой вопрос честно
  говорит, что он виртуальный помощник (не настраивается).

  номеров Telegram; все настройки внутри агента, ограничения (темы, запрещённые фразы, «сразу к человеку», лимиты, рабочее время), режим
  «С проверкой» (черновики), журнал ответов с правкой в готовые ответы, диалоги отдела, проверка без отправки. Включение AI-рекрутера, имя
  и напоминание перенесены из «Настроек подбора» в агента (рекрутер по умолчанию создан из прежних настроек — ничего не включилось само).
