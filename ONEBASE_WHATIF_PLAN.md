# OneBase Аналитик — What-If Simulator: аудит и архитектурный план

Дата: 12.11.2026. Раздел: «Аналитик → Симулятор» (`/analytik/simulator`). Устройство после реализации — `docs/analytik-simulator.md`.

## 1. Аудит: что уже есть и будет переиспользовано

| Что нужно симулятору | Что есть в OneBase | Как используется |
|---|---|---|
| Продажи по продуктам и регионам | `SkuSalesService.AggregateAsync` — вторичка Linko по товару × региону × месяцу, правила `SecondarySales` (как отчёт «Продажи по SKU») | База: кг и выручка по товару × региону за базовый период |
| Область продаж (РМ, супервайзер, агент) | `AnalytikAccess` → `SalesRowScope` | В базу попадают только регионы пользователя; агенту — только итог |
| Цена и скидки | `LinkoOrderLine.Price/TotalPrice/TotalDiscount`; цена за кг = выручка ÷ кг (`SkuSalesReport`) | Цена нетто за кг, доля скидки периода |
| План продаж | `SalesRegionPlan` (кг по региону и месяцу) | План на горизонт, выполнение |
| Оплаты точек и срок оплаты | `linko.Payments` (принятые), связь с заказом | Доля оплат к выручке, средний срок оплаты |
| Техкарты → сырьё на кг продукции | `ProductionCalc.Plan` (этапы, выход, брак, потери) по действующей версии, `ProductionRecipe.LinkoProductId` | Сырьё на кг каждого продукта |
| Себестоимость сырья | `OperationsAnalytik.LastPricesAsync` (последняя цена прихода) | Сырьевая себестоимость кг |
| Склад сырья, резерв, непригодное | `SupplyPlanner` (`ProductionStock.AvailableAsync`, баланс, движения) | Доступный остаток позиции |
| Ожидаемые поставки, сроки, минимумы, кратность закупки | `ProcurementArrivalService.ExpectedAsync`, `Supplier.LeadTimeDays` (или факт по заказам), `Item.MinQty`, единица закупки | Поставки по датам, срок поставки, округление закупки |
| Страховой запас, дата дефицита, «заказать до», бюджет | `SupplyPlanMath` (MRP: Z = 1,645, √срока поставки, округление) | Те же формулы и константы — вынесены в общие функции |
| Выпуск, смены, брак | `ProductionShift` (утверждённые смены: годный выход, номер смены, брак) | Оценка фактической мощности: выпуск за смену × смен в день |
| Персонал | `HrService` (Verifix: работающие по подразделениям, область `HrContext`) | Численность по подразделениям |
| Прогнозы | `Forecaster` (6 методов, диапазон ошибки) | Оптимистичный / пессимистичный набор — по реальному разбросу прогноза продаж |
| Свежесть данных | `DataReadiness` | Дата и статус каждого источника в снимке базы |
| AI | `AnalytikEngine` (Chief Analyst + аналитики, инструменты `analytik_*`) | Новый инструмент `analytik_simulate` и аналитик сценариев |
| Отчёты | `IReportWorkbookWriter` / `IReportPdfWriter` (ClosedXML / QuestPDF) | Экспорт Excel и PDF |
| Права | `analytik.use` + права разделов, `SalesRowScope`, `HrContext` | Каждый блок базы — только при праве на его раздел |

Мультиарендности в OneBase нет (одна компания на развёртывание, `Analytik:Tenant`). Сценарии всё равно хранят `Tenant` и
фильтруются по нему.

### Чего в OneBase нет — и как симулятор с этим поступает

Симулятор **не выдумывает** недостающие данные. Есть три вида входов, и у каждого числа в результате видно, какой это вход:

1. **Факт OneBase** — с источником и датой данных.
2. **Введено пользователем** — исходные значения, которых в OneBase нет. Они хранятся в сценарии с пометкой «введено вами»:
   - мощность производства в кг/день;
   - средняя зарплата;
   - расходы компании в месяц;
   - начальный остаток денег;
   - кредитный лимит;
   - вместимость склада;
   - прочая себестоимость кг.
3. **Изменения сценария** — параметры.

Если без недостающего входа результат посчитать нельзя, симулятор не подставляет ноль. Он показывает «нет данных», причину и что
заполнить: в OneBase или в исходных данных сценария.

| Нет в OneBase | Последствие в симуляторе |
|---|---|
| Мощности линий | Мощность берётся по утверждённым сменам: средний выпуск смены × смен в день. Смен нет — нужна мощность, введённая пользователем, иначе ограничение мощности не проверяется (так и пишется) |
| ФОТ и зарплаты вне продаж | ФОТ — численность Verifix × средняя зарплата, введённая пользователем |
| Расходы компании, денежный поток, кредиторка | Операционная прибыль и кассовые разрывы — только при введённых расходах и остатке денег; поток считается по оплатам, закупкам и введённым расходам |
| Вместимость склада, MOQ, отсрочка поставщикам числом | Параметры сценария, по умолчанию не ограничивают |
| Себестоимость готовой продукции без техкарты | Себестоимость продукта без связанной техкарты — только при введённой прочей себестоимости кг; доля выручки, покрытая себестоимостью, показывается |

На базе разработки на 12.11.2026:
- продажи полные (1,27 млн строк, 330 товаров), оплат 38 605, сотрудников Verifix 1 313;
- действующая техкарта одна, связей техкарт с товарами Linko — 0;
- цена прихода есть у 2 позиций из 545, срока поставки нет ни у одного из 126 поставщиков.

Цепочка «продажи → производство → сырьё» заработает, когда технологи свяжут техкарты с товарами Linko. Симулятор показывает,
сколько процентов продаж покрыто техкартами.

## 2. Архитектура

```
Браузер /analytik/simulator ─ /bff ─ /api/analytik/simulator/*   (AnalytikSimulatorController, [analytik.use])
  ├─ catalog       ScenarioCatalog: параметры, виды сценариев, граф зависимостей
  ├─ baseline      BaselineBuilder → ScenarioBaseline (снимок, analytik.ScenarioBaselines) — только разделы пользователя
  ├─ run           ScenarioEngine (чистый, детерминированный) ← DependencyGraph, ConstraintValidator
  ├─ scenarios     ScenarioService: сохранить, открыть, копия, правка, пересчёт на актуальных данных, архив, сравнение
  ├─ export        ScenarioExport → Excel / PDF
  └─ ai            ScenarioAnalyst: объяснение результата (по кнопке)
Чат Аналитика ─ AnalytikEngine ─ «Аналитик сценариев» ─ analytik_simulate → BaselineBuilder + ScenarioEngine
```

Код:
- `OneBase.Application/Analytik/Simulation`: модель, граф, проверки, движок, снимок, сервис;
- `OneBase.AI/Analytik`: инструмент, агент, экспорт;
- `OneBase.Api`: контроллер;
- `frontend/src/app/(app)/analytik/simulator`, `frontend/src/components/analytik/simulator`.

### Компоненты (названия из ТЗ)

| Компонент | Что делает |
|---|---|
| `ScenarioDefinition` | Название, вид (продажи, производство, сырьё, закупки, финансы, персонал, новый регион, комбинированный), горизонт, параметры, исходные данные пользователя |
| `ScenarioParameter` | Код, значение, цель (регион, продукт, позиция) — проверяется по каталогу параметров |
| `ScenarioBaseline` | Снимок исходных данных: кто, когда, период, источники и их свежесть, версия формул, показатели |
| `DependencyGraph` (`DependencyResolver`) | Явный граф «показатель ← от чего зависит»: какие показатели пересчитываются от параметра, порядок расчёта, цепочка влияния для экрана |
| `ConstraintValidator` | Проверка параметров (диапазоны, двойной учёт, сложность, нужные данные) и бизнес-ограничений результата |
| `ScenarioEngine` | Расчёт: база и сценарий по одним формулам, ограничения, риски, заключение |
| `SimulationResult` | Показатели «база → сценарий → разница (абсолютная и %)», продукты, регионы, сырьё, закупки, деньги по дням, ограничения, риски, допущения, источники |
| `ScenarioComparison` | Сравнение 2–5 сценариев по одному набору показателей |
| `SimulationAudit` | Журнал: сохранение, пересчёт, копия, архив, экспорт, AI (`IAuditLogger`, `analytik.scenario.*`) |

### Параметры — одни узлы для всех видов сценариев

Вид сценария — это только набор панелей. Параметр с одним смыслом существует один раз, поэтому в комбинированном сценарии
одно воздействие не учитывается дважды:
- «Количество смен» — один параметр для производства и персонала.
- «Зарплаты» — один для финансов и персонала.
- «Объём закупки» — один для закупок и финансов.
- «Спрос» и «объём продаж» — один драйвер запрошенного объёма.

Оставшиеся пересечения запрещает `ConstraintValidator`. Пример: «Изменение выручки» финансового блока вместе с любым параметром
продаж — ошибка «выручка уже меняется через продажи».

## 3. Модель и формулы

База — фактические значения за базовый период (по умолчанию последние 3 полных месяца). Пересчёт на горизонт H дней
(по умолчанию 30): `k = H ÷ дни базы`.

**Продажи.** По каждой ячейке «товар × регион»:
- `кг_запрос = кг_база · k · (1 + спрос) · (1 + регион_r) · (1 + товар_p) · (1 + эластичность · цена)`. Эластичность — параметр,
  по умолчанию 0, а не выдуманный коэффициент.
- `цена_нетто = цена_база · (1 + цена) · (1 − (скидка_база + Δскидки)) ÷ (1 − скидка_база)`.
- Новый регион: план кг/мес × H/30, ограничен спросом. Цена и состав продаж — как у выбранного региона-образца или в среднем по
  компании.
- `кг_продано = кг_запрос · доля_обеспечения_товара`.
- Недополученная выручка = (запрос − продано) · цена.

**Производство.**
- Требуемый выпуск товара с техкартой = запрос (кг) · (1 + изменение объёма производства).
- Мощность за горизонт = `мощность_кг/день · (1 + мощность) · смен_сценария ÷ смен_база · фактор_персонала · рабочих дней`.
- Загрузка = требуемый выпуск ÷ мощность.
- Если выпуск больше мощности, все товары режутся пропорционально — ограничение мощности.
- Брак: `коэффициент сырья = (1 − брак_база) ÷ (1 − брак_сценария)`.

**Сырьё** (по позициям техкарт):
- Расход в день = Σ выпуск товара/день · норма на кг · (1 + изменение норм) · коэффициент брака.
- Остаток по дням = доступно + поставки (сдвинутые на задержку) + новая закупка (в день «срок поставки + задержка») − расход.
- Дни без сырья до прихода закупки → доля обеспечения позиции; доля обеспечения товара = минимум по его сырью.
- Дефицит — позиция и дата.

**Закупки** — формула MRP `SupplyPlanMath`:
- `закупить = max(0, расход за горизонт + страховой запас − доступно − поставки в горизонте)`.
- Страховой запас = `max(1,645 · σ · √(срок + задержка), минимум) · (1 + изменение страхового запаса)`.
- Количество округляется до кратности закупки и минимальной партии.
- Стоимость = количество · цена · (1 + изменение цены сырья); изменение цены задаётся для всех позиций или для одной.
- Излишки — остаток на конец горизонта больше 90 дней расхода.
- Оборотный капитал = изменение стоимости запаса + изменение дебиторки − изменение кредиторки (по сроку оплаты поставщику).

**Себестоимость и прибыль.**
- Сырьевая себестоимость кг = Σ норма · цена.
- Прочая себестоимость кг — только если введена.
- Валовая прибыль = выручка − себестоимость проданного.
- Операционная прибыль = валовая − ФОТ − расходы компании − логистика. Считается только при введённых расходах, иначе
  «нет данных».

**Деньги** (по дням горизонта):
- Поступления = выручка · доля оплат, со сдвигом на срок оплаты.
- Выплаты = закупки (по сроку оплаты поставщику), ожидаемые поставки, ФОТ, расходы.
- Минимальный остаток → потребность в финансировании и дни кассового разрыва (с начальным остатком, если он введён).

**Персонал.**
- ФОТ = численность · средняя зарплата · (1 + изменение зарплат).
- Фактор персонала для мощности = (численность производственного подразделения сценария ÷ базы) · (1 + производительность). Учитывается,
  только если выбрано производственное подразделение.

**Новый регион.**
- Выручка.
- Расходы: себестоимость, персонал · зарплата, операционные, логистика за кг или в месяц.
- Точка безубыточности: `постоянные расходы ÷ (цена кг − переменные кг)`.
- Окупаемость: вложения ÷ месячная прибыль, только при введённых вложениях.
- Потребность в персонале — по продажам на агента в регионе-образце.

### Граф зависимостей (явный, проверяется тестом)

```
спрос, цена, скидки, регион, товар, новый регион → запрошенный объём → требуемый выпуск → загрузка мощности
мощность, смены, персонал, производительность ───────────────┘                    ↓
нормы, брак ─→ расход сырья ←────────────────────────────────── выпуск ──→ продано → выручка
цена сырья, поставщик ─→ себестоимость кг                          ↑                     ↓
запас, срок поставки, задержка, партия, страховой запас, объём закупки → дефицит → обеспечение
расход сырья → закупка → бюджет закупки → оборотный капитал → денежный поток → кассовый разрыв
зарплаты, численность → ФОТ → операционная прибыль; условия оплаты → поступления
```

LLM формул не придумывает: модель только переводит вопрос в параметры. Всё считает `ScenarioEngine`.

## 4. Ограничения (Constraint Engine)

| Ограничение | Откуда | Что показывается |
|---|---|---|
| Мощность | смены или ввод пользователя | Загрузка больше 100 % → выпуск урезан, недополученная выручка |
| Сырьё и резерв | склад, резерв заявок, непригодные партии | Дата дефицита, дни простоя, позиция |
| Сроки поставки | поставщик или факт, задержка | «Заказать до» в прошлом → приход после дефицита |
| Минимальная партия, кратность | единица закупки, параметр | Излишки от округления |
| Смены | параметр (1–3 в сутки) | Больше 3 — ошибка |
| Склад | ввод пользователя | Остаток больше вместимости |
| Финансовый лимит | ввод пользователя | Потребность в финансировании больше лимита |
| Технологические нормы | брак и нормы | Снижение норм ниже допуска техкарты — предупреждение «согласовать с технологом» |

Рост спроса не равен росту выручки: продано = запрос · обеспечение.

## 5. Хранение (миграция `Analytik3_Scenarios`, только новые таблицы)

- `analytik.ScenarioBaselines`:
  - Tenant, автор, время, базовый период, разделы, область продаж;
  - версия формул, источники и свежесть (`jsonb`), данные снимка (`jsonb`), хеш.
- `analytik.Scenarios`:
  - Tenant, автор, название, вид, набор (базовый, оптимистичный, пессимистичный, свой), статус (активен, архив);
  - снимок, горизонт, параметры (`jsonb`), введённые данные (`jsonb`), результат (`jsonb`), заключение;
  - AI-анализ и время, время расчёта, версия формул, «скопирован из», версия строки.

Открытый сценарий показывает сохранённый результат на своём снимке. Обновление данных OneBase его не меняет. Команда
«Пересчитать на актуальных данных» делает новый снимок и сохраняет новый результат. Прежний снимок остаётся в истории
сценария.

Фактические бизнес-таблицы симулятор только читает (тест сравнивает их до и после).

## 6. Права

- Раздел — `analytik.use`.
- Каждый блок снимка — только при праве на раздел:
  - продажи — `sales.read` и область регионов;
  - финансы — `finance.read`;
  - производство и сырьё — права производства или снабжения;
  - персонал — `HrContext`.
- РМ моделирует только свои регионы. Агенту доступен только итог своих продаж.
- Сценарий видит автор. Управляющий Аналитиком (`analytik.manage`) видит чужие сценарии, только если его права покрывают разделы
  и область снимка.
- Все проверки — на сервере.

## 7. Производительность

- Снимок кэшируется на 10 минут по ключу «пользователь, область, период».
- Продажи по SKU берутся из кэша раздела.
- Строить снимок одновременно могут не больше 2 пользователей, считать сценарии — не больше 8.
- Пределы сложности:
  - горизонт — до 365 дней;
  - точечных правок (регион, товар, позиция) — не больше 100;
  - сравнение — до 5 сценариев.
- Движок работает в памяти: база считается один раз на снимок.
- Экран: debounce 400 мс, отмена устаревшего запроса, индикатор.
- AI — только по кнопке после расчёта.

## 8. Этапы

1. Аудит и план (этот документ).
2. Сущности, миграция, снимок базы (`BaselineBuilder`).
3. Движок (`ScenarioEngine`).
4. Граф зависимостей и ограничения.
5. Экран симулятора.
6. Сравнение сценариев.
7. AI: инструмент `analytik_simulate`, аналитик сценариев, AI-анализ на экране.
8. История, экспорт, оптимизация.
9. Тесты и проверка в настоящем интерфейсе на копии базы.

После каждого этапа — сборка и тесты.
