# Disaster Recovery — этап 2: режим изоляции и проверка копии в API

Дата: 07.11.2026. План — [IMPLEMENTATION_PLAN_DISASTER_RECOVERY.md](IMPLEMENTATION_PLAN_DISASTER_RECOVERY.md), инструкция для
администратора — [docs/disaster-recovery.md](docs/disaster-recovery.md), раздел 7.

## Зачем

Восстановленная копия работает на настоящих данных: в базе та же сессия Telegram, push-подписки сотрудников, токены Linko,
Google, Verifix и ключи AI. Без изоляции учебное восстановление настоящей копии отправило бы уведомления людям, разорвало бы
рабочую сессию Telegram (один ключ авторизации с двух мест), запустило бы синхронизации и потратило бы деньги на AI. Без этого
этапа восстанавливать настоящую копию даже для проверки нельзя.

## Что сделано

**Режим изоляции** — переменная API `Recovery__Isolated=true` (в настройках — `Recovery:Isolated`). Защита в несколько слоёв,
каждый перекрывает следующий:

| Слой | Как |
|---|---|
| Фоновые службы | 13 служб, которые пишут людям или ходят наружу, в изоляции не регистрируются вовсе (`isolation.AllowOutbound`); работают только 2 внутренние — журнал ошибок и прогрев кэша продаж |
| HTTP | каждый HttpClient из фабрики первым обработчиком отклоняет запрос (`RecoveryIsolatedException`, наследник `HttpRequestException` — код ведёт себя как при недоступном сервере): Linko, Google, Verifix, провайдеры моделей, голос, Web Push, проверка подключения папок — в том числе то, что человек запустит кнопкой |
| Telegram | подключение аккаунта отклоняется (так же, как `Telegram:Enabled=false`), экран автоотчётов показывает «Telegram выключен» |
| AI | платные вызовы заблокированы (`Ai:Safety` — блокировка, даже если задан эмулятор); ключи моделей в изоляции не читаются; AI Data Manager (официальный SDK со своим HttpClient) получает выключенного провайдера |
| Интерфейс | плашка «Копия для проверки: внешние интеграции выключены» вверху каждой страницы — вход, OneBase, Sales Base (RU/UZ) |
| Журнал | при запуске — строка «Режим изоляции … не запущены: …» со списком служб |

Значение `Recovery:Isolated` разбирается безопасно: пусто / `false` / `0` / `no` / `off` — изоляции нет, `true` / `1` / `yes` / `on` —
есть, **опечатка — тоже изоляция**.

Выключаемые службы: Linko — синхронизация продаж; Google-таблицы — источники данных и журнал склада; Verifix — HR; Telegram —
подключение аккаунтов, автоотчёты, рассылки, ответы AI-агента; push-уведомления; напоминания о сроках задач и снабжения; AI —
проактивный анализ и план на день; Sales Base — статистика, AI-рекомендации и напоминания о просрочке.

**Проверка копии изнутри приложения** — `GET /api/recovery/check` (для Health Check программы восстановления, этап 4, и раздела
«Резервные копии», этап 5). Доступ: заголовок `X-Recovery-Token`, равный `Recovery:CheckToken` (не короче 32 символов, сравнение
за постоянное время; без настройки вход по токену выключен), или администратор с правом «Журнал ошибок». Данных не меняет,
наружу не ходит. Отвечает:

- режим: изоляция, Telegram, блокировка платного AI, список выключенных служб;
- база: применённые миграции, последняя, неприменённые; счётчики — пользователи, роли, сессии, подразделения, сотрудники, журнал
  аудита, файлы, задачи, документы базы знаний, аккаунты Telegram;
- ключи Data Protection: в базе и действующих;
- **расшифровка каждого вида секрета** — ключи AI, токены Linko, client_secret Verifix, api_hash, сессии и номера Telegram, ключи
  Google, пароли и ссылки папок отделов, ключ VAPID: сколько сохранено и сколько расшифровалось, без значений;
- файлы: объектов в хранилище; по каждому месту, где база ссылается на файл (файлы отделов, вложения задач, документы снабжения,
  база знаний, файлы AI Data Manager, материалы и вложения Telegram, фото визитов, еженедельные PDF), — ссылок и сколько объектов
  нет (первые 5 ключей); пробное чтение файла приложением;
- `problems` — каждая неудача текстом; `ok` — только если проблем нет.

**Назначения ключей шифрования** всех секретов собраны в одном месте (`ProtectionPurposes`) и используются и при сохранении, и в
проверке — разойтись они больше не могут. Строки назначений не менялись: уже сохранённые секреты расшифровываются как раньше.

## Проверка

**Новые тесты** — 22 (`RecoveryIsolationTests`, `RecoveryCheckDbTests`), все проходят:

| Тест | Что доказывает |
|---|---|
| ни одной внешней службы в изоляции | все 15 фоновых служб OneBase находятся по коду; вне изоляции все зарегистрированы, в изоляции — ни одной из 13 внешних, хост запускает только 2 внутренние. **Новая служба, добавленная без `AllowOutbound`, уронит тест** — её придётся явно отнести к внешним или внутренним |
| ни одного внешнего HTTP-запроса | вне изоляции запрос доходит до обработчика клиента (тест честный); в изоляции клиенты Linko, Verifix, Google, Anthropic, OpenAI, Web Push и безымянный отклоняют запрос, до обработчика не доходит ничего — даже при подставленном основном обработчике |
| AI и Telegram | платные вызовы заблокированы (и при заданном эмуляторе), Telegram выключен даже при `Telegram:Enabled=true` |
| разбор настройки | 11 значений, опечатка — изоляция |
| доступ к проверке | без токена, с коротким или чужим токеном — 401; вошедший без права — 403 |
| проверка на PostgreSQL | секреты сохранены теми же сервисами, что в работе (настройки AI, Linko, Telegram, ключи push), — все расшифрованы; испорченный номер Telegram и пропавший файл базы знаний — ровно 2 проблемы, `ok: false`; ни одно значение секрета не попало в ответ |
| эндпоинт по токену движка | ответ с режимом, проблемами и блокировкой AI |

**Все тесты бэкенда** на PostgreSQL 16: Files 41/41, Sales 460/460, AI 1114/1116 (2 — платные проверки моделей, пропускаются без
разрешения). Фронтенд: типы — без ошибок, тесты 70/70.

**Учебный сервер** (`onebase-dr-src`, чистый Ubuntu 24.04, свой Docker; образы api и web собраны с кодом этапа). В override
оставлена только `Recovery__Isolated=true` — без `Telegram__Enabled=false` и `Sales__Sync__Enabled=false`, чтобы копию от
внешнего мира отделял только режим изоляции. Всё время работы API записывался трафик моста Docker к адресам вне сети проекта:

| Проверка | Результат |
|---|---|
| запуск API | 14 с; в журнале — «Режим изоляции … не запущены: …» — все 13 служб |
| `GET /api/recovery/mode` | `isolated: true` и текст плашки |
| `GET /api/recovery/check` без токена / с чужим токеном | 401 / 401 |
| то же с токеном движка | `ok: true` за 582 мс: 79 миграций, неприменённых 0; ключ Data Protection 1, действующий; 47 объектов MinIO; Telegram выключен; платный AI заблокирован |
| то же администратором (без токена) | 200 |
| «Проверить подключение» к Linko | отказ: «Сервер недоступен … (RecoveryIsolatedException)» — в сеть не вышло |
| токены Linko и ключ AI сохранены через API, как в «Настройках» | проверка: Linko 2/2, AI 1/1 расшифрованы; значений нет ни в ответе, ни в журнале API |
| **трафик наружу за 232 с работы API** (фоновые службы стартуют с задержкой до минуты) | **0 пакетов** |
| холодный перезапуск дистрибутива | API снова поднялся в изоляции (тот же override) |
| страница входа, 1280 и 500 px | плашка вверху по центру, вход и выбор языка не перекрыты (скриншоты — `C:\Users\Admin\OneBaseDR\screenshots`, вне git) |

Замечание по ходу: при самом первом запросе после холодного запуска плашки может не быть — web готов раньше API, ответ о
режиме не пришёл. Компонент неудачу не запоминает и спрашивает снова на следующей странице; к тому времени войти в копию тоже
ещё нельзя.

## Ограничения

- Изоляция — свойство процесса API. Туннель Cloudflare в учебном восстановлении не запускается вовсе (это решает программа
  восстановления, этап 3); браузер пользователя по-прежнему загружает карты и шрифты сам — к копии это отношения не имеет.
- Если все ключи Data Protection в копии истекли, при первой расшифровке приложение создаёт новый ключ — это обычная работа
  Data Protection, старые ключи остаются и расшифровывают сохранённые секреты.
- Счётчики в проверке — ключевые таблицы; полную сверку строк всех таблиц с манифестом копии делает программа восстановления
  сразу после восстановления базы, до запуска API (этап 3–4).
