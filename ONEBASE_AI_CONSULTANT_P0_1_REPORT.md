## 1. Почему итоговая модель трактовала ошибку как отсутствие данных

| Где | Что было | Следствие |
|---|---|---|
| `OrchestratedConsultantEngine.ComposePrompt` | «Если сотрудник вернул **no_data или ошибку** — прямо скажи, каких данных нет.» | Прямая инструкция: сбой → «данных нет» |
| `OrchestratedConsultantEngine.ComposePrompt`, данные итогов | Итоговой модели передавались `status`, `summary`, `error` сотрудника как есть | При сбое модель видела `summary` «Данных о продажах нет» (слова модели сотрудника) и `error` с техническим текстом (сообщение провайдера, имена инструментов) |
| `ConsultantPrompts.QualityRules` / `GroundingPolicy` (общие с AI-сотрудниками) | Один шаблон отказа для всех случаев: «В OneBase нет достаточных данных…», «не найдено подтверждение…» | Нет различия между «нет прав», «сбой», «не подключено», «не найдено» |
| Ветка «сотрудники не привлекались» | «данных OneBase в этом ответе нет» | Модель могла повторить это как «данных нет», хотя поиск не выполнялся |
| `AgentDefaults.Director` (промпт консультанта) | «Если отдел сообщил, что данных нет, так и скажи» | Само по себе верно для «не найдено», но без различения остальных состояний |

Как статусы обрабатываются в остальных местах — они трактуют их правильно, правок не требовалось:
- `AgentRunner.Parse/Classify/Salvage/Failed`;
- `AgentOrchestrator` (прогресс и причины сбоя);
- `OrchestratedConsultantEngine.Denied`;
- `ConsultantAnswerCache.Cacheable` (кэширует только `completed`/`partial`);
- `AiMemoryStore` (хранит только `completed`/`partial`);
- `AiAuditService`;
- фронт: `Consultant.tsx`, подписи статусов.

## 2. Что сделано

### 2.1 Одно состояние на итог — `AnswerOutcome`

Новый класс `Consultant/AnswerOutcome.cs`. Состояние выводится кодом из статуса и причины, а не из текста модели:

| Статус и причина сотрудника | outcome | Что говорит итоговый ответ |
|---|---|---|
| `completed` | `completed` | Ответ по найденным данным |
| `partial` (в т.ч. прерван после данных) | `partial` | Ответ по подтверждённой части + ограничения |
| `forbidden`, `no_data` + `no_access` | `forbidden` | Нет прав на эти данные |
| `no_data` + `source_not_connected`, `disabled` | `source_not_loaded` | Источник не подключён / не загружен |
| `failed` (любая причина: `tool_error`, `model_unavailable`, `internal_error`, `interrupted`) | `tool_error` | Технический сбой источника |
| `no_data` + `not_found` (или без причины) | `not_found` | Не найдено после проверки доступных источников |
| `no_data` + `out_of_range` | `out_of_range` | Ограничение периода |
| `no_data` + `not_in_onebase` | `not_in_onebase` | Информация не представлена в источниках OneBase |

Новые причины в `AgentRunner.Classify`:

| Причина | Когда ставится | Как распознаётся |
|---|---|---|
| `out_of_range` | Сотрудник не получил данных из-за ограничения периода | Ответ инструмента об ограничении периода: «Период — не больше 62 дней», «Отрезок — в пределах одного месяца», «Данных о продажах за июнь 2025 в OneBase нет. Есть: …». Распознаёт `ToolFailures.IsOutOfRange`; такие ошибки считаются сбоем вида `out_of_range`. Текст ограничения передаётся в пояснение |
| `not_in_onebase` | Сотрудник ответил «нет данных», ни разу не обратившись к инструментам данных (новый счётчик `attempts`) | Это не «не найдено»: поиска не было |
| `no_access` | Отказ по праву на отдел | Ставится и здесь, а не только при отсутствии инструментов |

### 2.2 Данные итогового ответа — `ComposeData`

`OrchestratedConsultantEngine.ComposeData` (внутренний статический метод) передаёт по каждому сотруднику:
- `outcome`;
- `note` — безопасное пояснение;
- `limitations` — какие источники не ответили, по человеческому названию инструмента: «Остатки и дозагрузка: технический сбой»;
- `summary`;
- факты (`findings`), показатели (`metrics`), проблемы, рекомендации;
- источники (`dataSources`) и `unverified`.

Правила сборки:
- **Факты, показатели, проблемы, рекомендации** — только у `completed` и `partial`.
- **`summary` модели сотрудника** — только у `completed`, `partial`, `not_found`, `not_in_onebase`. У сбоя, «нет прав», «не подключено» и «период» он не передаётся: там модель сотрудника могла написать «данных нет».
- **`status`, `reason`, `error`, `toolErrors` в сыром виде** больше не передаются. Исключения, адреса, SQL, имена инструментов и сообщения провайдера до итоговой модели не доходят.

### 2.3 Правила итогового ответа — `ConsultantPrompts.FinalAnswerRules`

Новые правила только для итогового ответа консультанта (`ComposeRules` добавляет их после общих правил). У AI-сотрудников их нет: общие `QualityRules` и `GroundingPolicy` не менялись.

Состав:
- соответствие восьми outcome и формулировок;
- семь обязательных правил из задания:
  1. «данных нет» нельзя при `tool_error`, `forbidden`, `source_not_loaded`;
  2. нельзя утверждать отсутствие без поиска;
  3. не скрывать частичное;
  4. не придумывать цифры;
  5. отвечать по остальным отделам, если один не ответил;
  6. сказать, что проверено;
  7. не раскрывать технические детали.

Правки в `ComposePrompt`:
- строка «Если сотрудник вернул no_data или ошибку — прямо скажи, каких данных нет» заменена на «Сотрудников без данных называй по их outcome — по правилам итогового ответа (note — готовое пояснение)»;
- ветка «сотрудники не привлекались»: «данные OneBase не запрашивались… Не утверждай, что данных нет: поиск не выполнялся».

Проверка чисел (`GroundedComposer` / `EvidenceCheck`) не менялась. Число, которого нет в результатах инструментов, исправляется одной правкой или помечается «Не подтверждено данными OneBase».

## 6. Оставшиеся риски

1. **Формулировки на настоящей модели не проверены.**
   - Код гарантирует: итоговая модель не получает вводящий в заблуждение текст сотрудника и технические детали; у каждого итога однозначный `outcome` с готовым пояснением; неподтверждённые числа убираются или помечаются.
   - Но формулировку пишет модель, и следует ли она правилам, покажет только платный прогон.
2. **Общие правила остались.** Итоговая модель по-прежнему видит фразу «Если данных нет, прямо скажи: «В OneBase нет достаточных данных…»» из `QualityRules`: эти правила общие с AI-сотрудниками и не менялись. `FinalAnswerRules` явно уточняют их, но противоречие формулировок полностью уйдёт только после правки общих правил (требует согласования: меняет промпты сотрудников).
3. **Промпт консультанта (`Director`)** — «Если отдел сообщил, что данных нет, так и скажи» — не менялся. Он может быть переопределён администратором в БД.
4. **`out_of_range` распознаётся по формулировкам** ошибок инструментов. Новый инструмент с иначе сформулированным пределом периода даст `not_found`.
5. **`not_in_onebase` — это «сотрудник не вызвал инструменты данных».** Если он вызвал только источник истины (`get_source_of_truth`) и выяснил, что таблица не привязана, итог всё равно будет `not_in_onebase`, а не `source_not_loaded`.
6. **Интерфейс показывает старые подписи.** Карточки сотрудников под ответом подписаны по статусу: для `out_of_range` и `not_in_onebase` метка «нет данных» может расходиться с текстом ответа. Правка фронта (подпись по причине) — отдельно.
7. **Язык.** Правила на русском; ответ на узбекском зависит от того, как модель переведёт формулировки состояний.
8. **Инструкции канала Telegram** (задаются администратором) попадают в данные итогового ответа и теоретически могут противоречить правилам.

## 7. Требует отдельного согласования

1. Отправка в git и выкладка на production.
2. Правка общих правил `QualityRules` и `GroundingPolicy` — убрать единый шаблон отказа. Меняет и промпты AI-сотрудников.

5. Подписи состояний (`outcome`) в карточках сотрудников на фронте.
