# Аналитик: Advanced Intelligence

Что умеет AI-аналитик сверх ответа «аналитики отделов → сводка»:
- исследует сложные вопросы по плану;
- проверяет гипотезы расчётом и отделяет наблюдаемое от доказанного;
- моделирует решения: чувствительность, безубыточность, риск, оптимальный выпуск;
- проверяет свои выводы;
- помнит управленческие решения и через срок проверяет их результат;
- показывает, где ошибается.

Аудит и план — [ONEBASE_ADVANCED_INTELLIGENCE_PLAN.md](../ONEBASE_ADVANCED_INTELLIGENCE_PLAN.md), отчёт —
[ONEBASE_ADVANCED_INTELLIGENCE_REPORT.md](../ONEBASE_ADVANCED_INTELLIGENCE_REPORT.md).

Главное правило: числа, статусы гипотез и вердикты считает код. Модель планирует, формулирует гипотезы и пишет текст. Данные для расчётов
берутся только движком срезов с правами пользователя — модель не передаёт чисел в расчёт.

## Как устроено

```
Чат «Аналитика» (AnalytikEngine)
 ├─ простой вопрос → прежний путь: маршрутизатор → аналитики → ответ           (ни одного лишнего вызова модели)
 └─ сложный (InvestigationTriage, правила) → InvestigationEngine
      Planner (модель)        план: цель, шаги с зависимостями, гипотезы с проверкой
      шаги волнами            AgentOrchestrator / AgentRunner — те же аналитики, инструменты, права, проверка чисел
      Statistician (код)      ComputeService → HypothesisJudge: статус и класс вывода
      противоречия (код)      один показатель с разными значениями, одна гипотеза с разными статусами
      Replanner (модель)      пробелы, противоречия, недоказанные гипотезы → новые шаги и проверки (не больше 1 раза)
      Skeptic (модель)        только глубокое исследование: возражения и альтернативы → их тоже проверяет код
      Decision Advisor        ответ Chief Analyst: причины — только по статусам гипотез, рекомендации, предложение записать решение
      Reviewer                правила кода + пересчёт финансовых выводов + независимая модель (глубокое) → возврат на этап
      трасса и метрики        analytik.Investigations
```

### Когда вопрос исследуется

`InvestigationTriage` считает баллы по словам вопроса, без вызова модели:

| Признак | Баллы |
|---|---|
| Поиск причин: «почему», «из-за чего», «что повлияло» | 3 |
| Просьба исследовать: «исследуй», «разберись», «найди причину» | 3 |
| Гипотезы: «проверь гипотезу», «влияет ли», «связано ли» | 3 |
| Несколько отделов | 1 за каждый сверх первого |
| Длинный горизонт: «за год», «по месяцам», «динамика» | 1 |
| Рекомендации: «что делать», «как увеличить» | 1 |
| Прогноз или сценарий вместе с другими признаками | 1 |

- Порог исследования — `Analytik:InvestigationThreshold` (3).
- Глубокое исследование (со скептиком и проверкой ответа моделью) — с `InvestigationDeepThreshold` (6).
- Короткое уточнение («а в Бухаре?») наследует намерение прошлого вопроса.
- Просьба об отчёте Excel идёт прежним путём.

Примеры:
- «Как продажи за октябрь?» — 0 баллов, прежний путь.
- «Почему упали продажи в Хорезме?» — 3, исследование.
- «Исследуй, почему падают продажи, хватает ли сырья и закупок и что делать» — 9, глубокое исследование.

### Гипотезы (Multi-Hypothesis Engine)

У гипотезы есть формулировка и проверка — метод `analytik_compute` со срезом. Ожидание задаёт направление, участника или эффект. Статус по
результату расчёта ставит код (`HypothesisJudge`):

| Метод | Подтверждена | Частично | Отклонена |
|---|---|---|---|
| `drivers` | доля участника во всех изменениях ≥ 50 %, знак — ожидаемый | ≥ 20 % | изменился в другую сторону или вклад меньше 20 % |
| `pvm` | эффект (цена, объём, ассортимент) ≥ 50 % всех эффектов и того же знака, что изменение | ≥ 20 % | эффект в другую сторону |
| `before_after`, `trend` | p < 0,05 в ожидаемую сторону | — | значимо в другую сторону или изменение < 2 % |
| `did` | значимо, контроль с параллельными трендами | значимо, но тренды не проверены | — |
| `correlation`, `regression`, `lag` | значимая связь нужного знака | — | значимая обратная |

Остальное — «не доказана» с тем, чего не хватает.

**Класс вывода** — отдельно от статуса:
- наблюдаемая зависимость;
- статистически подтверждённая связь;
- проверенная причинная гипотеза — только разность разностей с контрольной группой и параллельными трендами до события;
- предположение.

Корреляция не превращается в причину: «подтверждена» с классом «наблюдаемая» значит «данные согласуются».

Уверенность:

| Статус и класс | Уверенность |
|---|---|
| подтверждена, проверенная причинная | 0,85 |
| подтверждена, статистическая | 0,75 |
| подтверждена, наблюдаемая | 0,6 |
| частично | 0,45 |
| не доказана | 0,2 |
| отклонена | 0,6–0,7 |

Таблицу гипотез под ответом пишет код, поэтому статусы модель исказить не может.

### Проверка выводов (Reviewer)

Ревизор не соглашается по умолчанию. Правила кода:
- остались числа, не подтверждённые данными;
- причиной названа отклонённая гипотеза;
- причина без подтверждённой гипотезы и без данных шагов;
- при неполных данных нет ограничений;
- в ответе год, которого нет в данных;
- для финансовых вопросов — пересчёт расчётов подтверждённых гипотез по записи журнала. Расхождение без обновления данных — гипотеза
  перепроверяется.

В глубоком исследовании ответ дополнительно проверяет независимая модель с отдельным промптом.

При ошибке — возврат на этап: ответ переписывается с замечаниями или гипотеза перепроверяется. Циклов не больше
`InvestigationReviewCycles` (2). Не исправилось — предупреждение в тексте ответа.

### Перепланирование и защита от зацикливания

- **Перепланирование** — если шаг без данных, есть противоречие или все гипотезы не доказаны: планировщик получает состояние и предлагает
  альтернативный источник, проверочный шаг или другой метод. Делается не больше `InvestigationMaxReplans` (1) раза.
- **Повторы в цикле аналитика:** тот же неудачный вызов с теми же аргументами не выполняется повторно. После 3 сбоев инструмент закрывается до
  конца анализа (`AgentRunner.MaxToolFailures`).
- **Query Repair:** отказ движка срезов возвращается вместе с исправленным запросом.
  - Безопасные исправления (план по дням → по месяцам, опечатка в коде показателя) выполняются сразу.
  - Остальные — подсказкой с готовыми аргументами: разделить несовместимые показатели, взять шаг крупнее, разбить длинный период.

### Трасса и метрики

`analytik.Investigations` хранит:
- вопрос, цель, сложность, статус;
- роли, план и волны, шаги с промежуточными результатами;
- гипотезы со статусами;
- противоречия, циклы проверки, возражения скептика, трассу событий, ограничения;
- глубину, шаги, вызовы модели и инструментов, токены, стоимость, время, возвраты проверки, перепланирования.

Расчёты гипотез пишутся в `analytik.Computations` с id исследования.

## Вычислительный движок (`analytik_compute`)

Методы — `Application/Analytik/Compute`, у каждого алгоритм и версия:

| Группа | Методы |
|---|---|
| Описание и ряды | `describe`, `trend`, `seasonality`, `anomalies`, `forecast` (Forecaster) |
| Связи | `correlation` (Пирсон, Спирмен), `regression` (МНК), `lag` (корреляция со сдвигом, Бонферрони) |
| Изменение | `drivers` (вклад участников), `pvm` (цена, объём, ассортимент, новые и выбывшие — сумма равна изменению), `mix` |
| Причины | `before_after` (Уэлч, тренд «до»), `did` (разность разностей, параллельные тренды) |
| Сегменты | `abc`, `abc_xyz`, `rfm`, `cohorts`, `clusters` (k-means++), `churn` |
| Финансы | `plan_variance`, `unit_economics`, `cash_conversion` |
| Запас | `stock_health` (дни запаса, дефицит, излишек, без продаж 30/90 дней) |

Отдельно — математика без данных: EOQ, страховой запас, точка заказа, возраст запаса (`InventoryMath`), симплекс (`LinearProgram`).

- **Журнал.** Каждый расчёт — строка `analytik.Computations`: вход (запросы срезов, их id в журнале, отпечаток данных), алгоритм, версия,
  параметры, результат, период, источники, ограничения, класс вывода.
- **Повтор.** `ReplayAsync` повторяет расчёт по записи и сообщает, совпал ли результат и обновлялись ли данные.

## Методы отделов (`analytik_methods`)

Реестр `ComputeCatalog.Expert` для каждого метода отдела говорит, чем он считается:
- методом движка;
- существующим инструментом (`analytik_production`, `analytik_procurement_plan`, `get_hr_timesheet`…);
- не считается — с причиной. CAC, ROMI, отклонение от бюджета — данных в OneBase нет.

Метод без прав пользователя не предлагается.

## What-If: анализ сценария

`ScenarioAnalysis` запускает чистый `ScenarioEngine.Run` на том же снимке много раз, исходный сценарий не меняется:

| Режим | Что даёт |
|---|---|
| `sensitivity` | Торнадо: каждый параметр ± шаг, размах показателя |
| `matrix` | Показатель на сетке двух параметров (до 9 × 9) |
| `goal_seek` | Значение параметра для цели (бисекция в пределах параметра): «найдено», «недостижимо в пределах», «не влияет» |
| `break_even` | То же, цель — нулевая прибыль |
| `monte_carlo` | Треугольные распределения, SplitMix64 по seed: квантили P5–P95, вероятность ниже нуля и ниже базы, гистограмма |
| `cases` | Худший, базовый и лучший случаи |
| `optimize` | Симплекс: выпуск товаров с техкартой по марже «цена − сырьё по нормам» при ограничениях сырья (с поставками за горизонт), мощности и спроса; узкие места с теневой ценой |

- **Где доступно:** экран симулятора, вкладка «Анализ»; API — `POST /api/analytik/simulator/analyze`; AI — `analytik_scenario_analysis`.
- **Журнал:** анализ пишется в журнал расчётов (метод `scenario.<режим>`).

## Фоновые находки: авторасследование и история

- **Авторасследование.** Новая или выросшая находка расследуется кодом (`InsightInvestigator`). Для отклонения выручки или оплат дня:
  - вклад регионов, товарных групп и агентов;
  - PVM против того же дня неделей раньше.
- **Что записывается в находку:**
  - уверенность — по сосредоточенности вклада и полноте данных;
  - класс вывода — «наблюдаемая»: это вклад, а не причина;
  - расследование.
- **Правила с причиной в данных** (запас, сроки) получают уверенность по тому, подтверждена ли причина.
- **История.** Все события находки — в `analytik.InsightEvents`: создана, важность, масштаб, расследована, закрыта, вернулась.
- **Уведомления** — без повторов, как раньше.

## Память решений

«Аналитик → Решения» (`/analytik/decisions`):
- **Запись.** Решение, автор, причина, показатель с фильтрами, ожидание (рост, снижение, без изменений и на сколько %), дата проверки.
- **Исходное значение** — срез за 30 дней до решения.
- **Проверка в срок** — ежедневная фоновая задача, по правам автора. Сравниваются средние в день после решения и до него.
  - Значимость считается t-тестом по дням.
  - Вердикт: ожидание выполнено, частично, не выполнено, не ясно (меньше 7 дней данных).
  - Это сравнение «до / после», а не доказательство причины.
- **Права.** Видят автор и управляющий Аналитиком.
- **AI:**
  - читает историю решений — `analytik_decisions`;
  - готовит черновик — `analytik_decision_draft`, уровень «подготовить». Черновик ничего не сохраняет: ссылка открывает форму, человек
    сохраняет сам.

## Execution Safety

У каждого инструмента есть уровень (`ITool.Level`):

| Уровень | Что |
|---|---|
| 1 | Читать |
| 2 | Анализировать |
| 3 | Рекомендовать |
| 4 | Подготовить |
| 5 | Выполнить |

- **Аналитикам** инструменты выше 4 не выдаются и не выполняются — отказ «нет доступа».
- **Остальным** уровень 5 — только через подтверждение человеком.
- **Расчёты, прогнозы, сценарии** — уровень 2. Управленческий отчёт и черновик решения — 4.
- **Права и компания** проверяются, как раньше, в движках.

## Качество аналитика

«Аналитик → Качество» (`/analytik/quality`, только `analytik.manage`), по журналам за 7, 30 или 90 дней:
- доля ответов без сбоев и неподтверждённых чисел, доля неполных;
- исследования: статусы, средние шаги, глубина, время, стоимость, вызовы, доля возвратов проверки и перепланирований;
- статусы и классы гипотез, замечания проверки;
- ошибки срезов: одинаковые причины складываются, конкретные значения заменяются;
- ошибки расчётов и сбои инструментов;
- прогоны набора;
- слабые места — повторяющиеся причины по частоте.

## Набор сложных вопросов

`BenchmarkCatalog` — 104 сценария по 14 категориям:
- простая, многомерная и межмодульная аналитика;
- финансовые расследования;
- поиск причин;
- прогнозирование, оптимизация, «что если»;
- противоречивые данные, нехватка данных;
- неоднозначные, длинный горизонт, многошаговые, провокационные.

У каждого — вопрос и эталонная операция: срез, расчёт, анализ сценария, исправление запроса, решение о глубине, проверка ответа, план,
уровень инструмента.

Три вида прогона:

| Прогон | Как работает |
|---|---|
| Регрессия в тестах (`IntelligenceBenchmarkTests`) | Все сценарии на тестовом мире (`IntelligenceWorld`). Статус — как ожидается; числа 33 сценариев сверяются с независимым расчётом по строкам мира |
| Регрессия в продукте | Кнопка в «Качестве» или `POST /api/analytik/benchmark/regression`. Те же операции на данных компании, бесплатно. Статус, зависящий от данных (есть ли планы, оплаты), сравнивается и с прошлым прогоном: регрессия — изменение того, что работало |
| Живой прогон моделью | `POST /api/analytik/benchmark/live` — **платный**: нужны `confirm = true` и `analytik.manage`, бюджет по умолчанию $2. Вопросы задаются чату Аналитика, ответ оценивается — глубина, инструменты, упоминания, неподтверждённые числа, число эталона в ответе |

## Ограничения

- **Причинность.** Проверенная причинная гипотеза требует контрольной группы с параллельными трендами. Без неё вывод — не выше
  «статистической связи»; влияние решения на результат не отделить от других факторов.
- **Финансы.** Расходов компании, бюджетов, маркетинговых затрат в OneBase нет: CAC, ROMI, отклонение от бюджета не считаются, прибыль
  сценария — только при введённых расходах.
- **Оптимизация** — только по товарам с техкартой и ценами сырья. На базе разработки таких товаров нет — режим объясняет это, а не считает.
- **Модель.** Живого прогона моделью не было: он платный и запускается по разрешению. Механика проверена на подставной модели.
