# Аналитик: Statistics Engine и исследования (Phase 2)

Phase 2 расширяет Аналитик, ничего не дублируя:

- вычислительный движок (`Application/Analytik/Compute`) — новые статистические методы;
- движок срезов — факт «визиты»;
- реестр возможностей — паспорт показателя, карта показателей отделов, проверка совместимости;
- исследования-шаблоны — исследование одним серверным вызовом (`Application/Analytik/Research`): план операций, параллельное выполнение и выводы с уровнем доказательности.

Модель не считает статистику формулами. Она выбирает метод или шаблон и пересказывает выводы.

## Математика (код, без внешних библиотек)

| Файл | Что считает |
|---|---|
| `Compute/StatMath.cs` | Описательная статистика, Пирсон, Спирмен, распределения t, F и нормальное, критерий Уэлча (были и раньше) |
| `Compute/CorrelationMath.cs` | Кендалл τ-b (асимптотическое p с поправкой на связки), интервал Фишера (Пирсон; Спирмен — Бонетт — Райт; Кендалл — Филлер), частная корреляция (остатки МНК; Спирмен — по рангам), скользящая корреляция, Бенджамини — Хохберг (q), Жарк — Бера, z, модифицированная z (Иглевич — Хоглин), границы Тьюки (IQR) |
| `Compute/RegressionModels.cs` | МНК с интервалами коэффициентов, Дарбин — Уотсон, Жарк — Бера и Бройш — Паган для остатков, VIF, число обусловленности, LOOCV (PRESS); полиномиальная регрессия степени 1–3; Ridge (λ по GCV); Lasso (координатный спуск, λ по 5-кратной проверке непрерывными блоками) |
| `Compute/TimeSeriesMath.cs` | SES, Хольт, Хольт — Уинтерс (аддитивный); классическая декомпозиция; скользящая статистика; точки перелома (бинарная сегментация, штраф 2σ²·ln n); тест Чоу |
| `Compute/CorrelationAnalysis.cs` | Отчёт о связи по контракту ТЗ: проверки данных, общий тренд, день недели, «часть и целое», совместимость, статус и уровень |

Все функции сверены с эталонами: scipy 1.13, statsmodels 0.14, sklearn 1.6 (тесты `StatisticsEngineMathTests`).

## Методы вычислительного движка

| Код | Что делает |
|---|---|
| `correlation` (1.1) | Первый показатель против остальных |
| `partial_correlation` | Частная корреляция с контрольными показателями |
| `rolling_correlation` | Корреляция в скользящем окне |
| `correlation_matrix` | Все пары; с `members` участники измерения становятся рядами: каждый — против итога и против «всех остальных» |
| `regression` (1.1) | `model` = linear, polynomial, ridge или lasso |
| `smoothing` | Экспоненциальное сглаживание |
| `decomposition` | Сезонная декомпозиция |
| `change_points` | Сдвиги уровня |
| `rolling_stats` | Скользящая статистика |
| `anomaly_scan` | Обзор аномалий по нескольким показателям |

Данные для метода:
- срез движка (с правами пользователя);
- `query_id` — срез из журнала `analytik.Queries`;
- `series` — структурированные ряды: до 25 рядов, до 5 000 значений в ряду и 20 000 всего.

Каждый расчёт записывается в `analytik.Computations` и повторяется по записи.

### Отчёт о связи

Поля отчёта:
- метод и коэффициент;
- p, а при переборе пар — q (поправка Бенджамини — Хохберга);
- доверительный интервал;
- размер выборки, пропуски, дубли ключей, выбросы, период;
- коэффициенты Пирсона, Спирмена и Кендалла;
- связь без общего тренда (первые разности);
- связь без дня недели (остатки после среднего своего дня цикла — для дневных рядов);
- математическая зависимость показателей и класс совместимости;
- предупреждения, статус и уровень.

Статус:
- `valid` — связь значима, оговорок нет;
- `warning` — значима, но с оговорками;
- `not_significant` — не подтверждена;
- `unreliable` — меньше 10 пар;
- `invalid` — нулевая дисперсия, меньше 5 пар или несовместимые данные.

Уровень связи никогда не выше CORRELATION. Связь понижается до HYPOTHESIS, если:
- без общего тренда она пропадает;
- без дня недели она пропадает;
- показатели связаны формулой (часть и целое, расчёт одного из другого);
- она значима только без поправки на множественные сравнения.

**Участники измерения** (группы, регионы) в матрице `members` сравниваются с итогом (часть и целое — всегда оговорка) и со «всеми, кроме себя». Ряд «все, кроме X» стоит в паре только с самим X: любой другой участник входит в «всех, кроме X», и связь с ними была бы завышена.

**Сравнение участников по показателям разных источников** (выручка × визиты по регионам): если у участника нет ни одной записи одного из источников (у «Сетей» визиты ТП не ведутся), это «нет данных», а не ноль. Участник в расчёт по этому показателю не идёт, а в оговорках названо, кто выпал. Внутри одного источника суммы и счётчики пустыми не бывают. В дневных рядах пустой день — ноль (воскресенье); пропуск загрузки находит обзор аномалий.

### Обзор аномалий

Разложение устойчивое:
- сезон — медиана значений каждого дня цикла;
- тренд — скользящая медиана.

Все проверки идут по остатку: модифицированная z, z, IQR, резкое изменение к ожидаемому, пропавшие данные (ноль там, где обычно есть значения). Поэтому один выброс не делает «аномалиями» соседние дни, а воскресный спад — не аномалия.

Аномалия засчитывается, когда:
- модифицированная z остатка больше 3,5;
- и её подтверждает ещё хотя бы один метод (или пропали данные).

У показателей-отношений (средний чек, страйк, выполнение маршрута) шаги без знаменателя не проверяются вовсе.

## Визиты в движке срезов

Факт `visits` (`linko.Visits` + `linko.Markets` + проданные заказы) считается по правилам «Календаря визитов».

| Показатель | Как считается |
|---|---|
| `visits_planned` | Визиты маршрута, кроме сегодняшних и будущих невыполненных |
| `visits_done`, `visits_done_in_plan`, `visits_off_plan` | Выполненные визиты: все, по маршруту, вне маршрута |
| `visits_missed` | Визиты маршрута прошедших дней в статусе pending |
| `visits_with_order` | У ТП есть проданный заказ в этой точке, введённый в день визита |
| `visits_without_order` | Выполненные визиты без заказа |
| `visited_outlets` | Посещённые точки |
| `route_execution` | Выполнение маршрута |
| `visit_strike` | Страйк — доля визитов с заказом |

Измерения: дата, регион и связанные с ним (по филиалу точки), филиал, агент, точка, тип точки.

Сверка на копии базы разработки: октябрь 2026, 20 ТП трёх регионов. Расхождений со страницей региона «Продаж» нет — совпали план, выполнено по маршруту, вне маршрута и всего.

Регион визита определяется по филиалу точки. Календарь визитов относит визит к региону ТП, поэтому по регионам суммы могут отличаться. Срез об этом предупреждает.

## Реестр возможностей

- **`MetricPassports.Profiles`** — паспорт каждого показателя движка: смысл, таблицы, поле, тип, агрегация, складывается ли по строкам, часть чего, из чего считается.
- **`MetricPassports.Business`** — карта показателей отделов из ТЗ: продажи, визиты, промо, финансы, склад, производство, HR. Для каждого показателя указано, где он считается (`engine`, `compute`, `tool`, `missing`) и какой модуль должен его дать, если данных нет. Живое наличие данных берётся из каталога таблиц Аналитика: через запятую — нужны все таблицы, через «|» — достаточно любой.
- **`DataCompatibility`** — проверка пары показателей по двенадцати пунктам ТЗ: источник, ключи, шаг, период, единицы, атрибуция региона и агента, дубли, пропуски, права, кардинальность, размножение сумм. Плюс бизнес-смысл: оплаты — не выручка; первичка — не вторичка; остаток на дату — не оборот; месячный план — не дневной факт.
  - Классы: `DIRECTLY_COMPATIBLE`, `COMPATIBLE_AFTER_AGGREGATION`, `COMPATIBLE_WITH_LIMITATIONS`, `NOT_COMPATIBLE`, `SOURCE_MISSING`, `ACCESS_DENIED`.
  - Проверяются и показатели инструментов отделов: `primary_kg`, `dealer_debt`, `promotions`, `linko_kpi_fact`, `expenses`.
  - Движок срезов добавляет оговорки совместимости в заметки результата, если срез собран из нескольких фактов.

## Исследования-шаблоны

Шаблон по вопросу выбирает `ResearchPlanner.Match` — по правилам, без модели, для русского и узбекского (латиница и кириллица). Он же извлекает период:
- «за последние 103 дня», «за месяц», «за квартал», «за год»;
- месяц по названию («в октябре», «за сентябрь и октябрь», «oktabrda», «за май 2026») — с первого по последний день; месяц позже текущего — прошлого года;
- «в прошлом месяце», «в этом месяце».

Шаблон не берётся, и вопрос решает агент (у него `analytik_compute`, `analytics_query` и `analytics_research` с датами), если:
- спрашивают о конкретной связи: «есть ли связь…», «посчитай корреляцию…», «коэффициент корреляции», корреляции «по регионам / ТП / товарам» без слова «все»;
- в вопросе точные даты: «с 1 по 15 октября», «01.10».

| Шаблон | Что делает |
|---|---|
| `correlations` | Матрицы показателей продаж и визитов; товарные группы и регионы — против итога и против остальных; запаздывание визиты → заказы |
| `decline_drivers` | Изменение показателей; разложение выручки (точки × заказы на точку × средний чек); вклад регионов, групп, ТП, точек; цена — объём — ассортимент; отток; визиты; точки перелома; проверка двенадцати гипотез |
| `agent_efficiency` | Визиты и продажи каждого ТП: выручка на визит, страйк, маршрут; связь, регрессия, кластеры. Пользователи без заказов с визитов идут отдельно |
| `visits_vs_sales` | Регионы, где визиты растут, а выручка падает; значимость дневных трендов. Если таких нет — сколько регионов с ростом визитов и с падением выручки и три ближайших к условию |
| `group_influence` | Доля групп; вклад в колебания итога (Cov(группа, итог) / Var(итог) — в сумме 100 %); вклад в изменение; связь с остальными группами |
| `anomalies` | Обзор аномалий продаж, визитов и оплат |
| `promo_effect` | Эффект акций как на странице «Акции» (месяц конца периода), плюс разность разностей к контрольной группе и скидки на товары акции (с датами проверки). Акции с общим окном проверки и почти теми же товарами (≥ 80 % общих) проверяются вместе; проверки с одинаковыми продажами и скидками товаров в одном окне — один вывод под общим названием. Отдача разности разностей — только для значимого эффекта; отдача страницы «Акции» — гипотеза «статистически не проверено» |
| `company_health` | Ключевые показатели, визиты, оплаты к выручке, план и прогноз месяца, тренд, аномалии, отток, запасы, открытые риски |

**Как выполняется план** (`ResearchService`):
- Операции без невыполненных зависимостей идут параллельно, каждая — в своей области DI, одновременно не больше `InvestigationParallelSteps`.
- Одинаковые срезы выполняются один раз (`SliceCache`).
- У каждой операции свой таймаут.
- Отказ среза исправляется через Query Repair не больше одного раза.
- Если зависимость операции упала, операция пропускается с причиной.
- Прогресс сохраняется в `analytik.Investigations` (роли `research` и `<шаблон>`) после каждой операции.
- Исследование можно отменить.
- Исследование заканчивается последним полным днём данных: день последней загрузки Linko не входит.
- Выводы строит код (`ResearchFindings`) только из успешных операций. Если вывод опирается на операцию без результата, он понижается до UNVERIFIED.

**Статусы операций и сбоев:**

| Статус | Значение |
|---|---|
| `SUCCESS` | Готово |
| `PARTIAL_RESULT` | Результат по неполным данным |
| `DATA_NOT_FOUND` | Данных нет |
| `TOOL_UNSUPPORTED` | Не поддерживается |
| `SOURCE_UNAVAILABLE` | Сбой или таймаут источника |
| `NO_ACCESS` | Нет доступа |
| `INSUFFICIENT_GRANULARITY` | Нет нужной детализации |
| `CALCULATION_FAILED` | Расчёт не выполнен |
| `VALIDATION_FAILED` | Проверка не пройдена |
| `SKIPPED` | Пропущено |
| `CANCELLED` | Отменено |

Ошибка базы — это `SOURCE_UNAVAILABLE`, а не «данных нет».

**Уровни доказательности** (`EvidenceLevels`): FACT, CALCULATED, STATISTICALLY_SUPPORTED, CORRELATION, HYPOTHESIS, FORECAST, UNVERIFIED.

## AI

- **Источник `sales.stats`** («Статистика и исследования») открыт всем отделам консультанта и аналитикам Аналитика. Ему принадлежат `analytik_compute` (перенесён из источника `analytik`; право — продажи, финансы или Аналитик) и новый `analytics_research`. Гранты добавляет `AiSeeder` при старте.
- **`analytics_query`** отдаёт `query_id` — по нему можно продолжить анализ в `analytik_compute`.
- **`analytics_capabilities`**:

  | `section` | Что отдаёт |
  |---|---|
  | `metrics` | Паспорта показателей |
  | `business` | Карту показателей отделов |
  | `compatibility` | Совместимость пары |

- **Сбои инструментов** несут `status` (по ТЗ) и `alternatives` — существующие инструменты, которые дают те же данные другим путём.
- **Калькулятор** при длинном выражении направляет к `analytik_compute` и `analytics_research`. AgentRunner подсказывает: статистика — только сервером.
- **Чат Аналитика:** вопрос по шаблону (`Analytik:ResearchMode` = `auto`) исследуется кодом, а ответ пишется одним вызовом модели строго по выводам — числа проверяет `GroundedComposer`. Если модель недоступна или платные вызовы заблокированы, ответом становится отчёт исследования (`ResearchBrief`, одиннадцать разделов ТЗ). `ResearchMode` = `off` возвращает прежний путь (исследование моделью). Своих прогнозов и «связей» модели добавлять нельзя: прогноз — только из выводов, в «Корреляциях» — только посчитанные связи.
- **Маршрутизатор** знает слова «корреляц», «закономерн», «аномал», «акци», «промо», «скидк» (русские и узбекские).

## Экран

**«Аналитик → Исследования»:**
- блок «Исследование без модели» — выбор шаблона и числа дней, запуск;
- список исследований;
- запись исследования-шаблона (`ResearchView`):
  - обзор: период, сравнение, область, операции, срезы и расчёты, кэш, время;
  - выводы по разделам ТЗ с меткой уровня;
  - гипотезы со статусом проверки;
  - матрицы корреляций: цвет — знак и сила, насыщенность — подтверждение q < 0,05, подсказка при наведении;
  - таблицы;
  - операции — метод, параметры, статус, причина сбоя;
  - ограничения и источники.

**«Аналитик → Качество»:**
- блок «Исследования без модели»;
- разбор ответа по id разговора.

Экраны проверены на компьютере 1440 px и телефоне 390 px.

## Настройки

`Analytik:ResearchMode` — `auto` (по умолчанию) или `off`.

Параллельность, таймауты и пределы берутся из имеющихся настроек: `InvestigationParallelSteps`, `QueryTimeoutSeconds`, `MaxQueryCost`.

Новых таблиц и миграций нет: исследования хранятся в `analytik.Investigations`, расчёты — в `analytik.Computations`.
