# Раздел «Задачи» OneBase

Кнопки раздела — в верхней панели, как в «Продажах» (у «Предложений AI» — счётчик ожидающих, `GET /api/work/nav`): **Обзор** (сводка, мои сроки, отделы, предложения AI), **Все задачи** (таблица), **Канбан**, **Мои задачи**,
**Задачи отдела** (кнопки отделов; в «Продажах» ещё задачи и маршруты полевой команды Sales Base), **Архив и завершённые**,
**Предложения AI** (руководителям), **Проекты** (проекты и руководители отделов). Карточка задачи — `/tasks/task/{id}`
(на неё ведут уведомления). Таблица и канбан — одни и те же задачи `work.Tasks` и одно API `GET /api/work/tasks`.

## Доступ (проверяет backend — `WorkTaskService`, интерфейс только показывает то, что вернул API)

| Кто | Видит | Управляет (правит, назначает, переносит срок, принимает, возвращает, отменяет, архивирует) |
|---|---|---|
| Руководство — право «Пользователи и роли» (администратор, директор) | задачи всей компании | всеми |
| Руководитель отдела — `work.DepartmentHeads` (назначает руководство во вкладке «Проекты»; можно несколько отделов) | задачи своих отделов | задачами своих отделов, проектами отдела |
| Руководитель проекта (PM) — участник проекта с отметкой PM | задачи проекта | задачами проекта |
| Сотрудник | задачи своего отдела, назначенные ему, поставленные им и задачи проектов, где он участник | задачами, которые поставил сам |

- Ведёт задачу исполнитель (у задачи без исполнителя — сотрудник отдела или участник проекта, который её возьмёт): в работу,
  чек-лист, процент, блокировка, на проверку, комментарии, вложения.
- Ставит задачу тот, кто видит отдел (или участник проекта — в проекте); исполнитель — любой действующий пользователь OneBase.
  В выборе исполнителя поиск по имени, должности и отделу; сначала — сотрудники отдела задачи и участники проекта, ниже — остальные.
  Исполнитель из другого отдела видит задачу в «Моих задачах» и ведёт её как обычно. Отключённого пользователя назначить нельзя.
- **«Продажи»** открываются и всем, у кого есть доступ к Sales Base (`field.use`, `field.manage`, `field.plan`): вкладки
  «Агенты и супервайзеры» и «Маршруты». Право `field.plan` — планирование полевой организации из OneBase.
- Чужой отдел по ссылке — 403, чужая задача, вложение или предложение по номеру — 404.

## Статусы и действия

«Новая» → «В работе» → «На проверке» → «Выполнена»; «Отменена». Исполнитель отправляет на проверку; постановщик или руководитель
принимает результат или возвращает на доработку (причина обязательна — она пишется в комментарии и уведомление). Управляющий
может закрыть задачу сразу, отменить и вернуть выполненную или отменённую в работу. Заблокированность — признак с причиной
(красная метка в таблице и на канбане), не статус. Архив — только выполненные и отменённые; задачи никогда не удаляются
автоматически и возвращаются из архива. Процент выполнения: с чек-листом — доля выполненных пунктов, без — указывает исполнитель;
у выполненной — 100. История — `work.TaskEvents` (каждое изменение: кто, когда, что было и стало).

Вложения — до 20 МБ и 30 файлов на задачу, в хранилище файлов (MinIO, ключ `tasks/{задача}/{вложение}`); скачивает тот, кто
видит задачу, всегда как файл (`Content-Disposition: attachment`, `nosniff`; тип — только безопасный, иначе двоичный).

## AI-диспетчер задач (`TaskSuggestionService`)

- Источники (только данные OneBase): находки проактивного анализа `ai.Alerts` (снижение продаж, риск невыполнения плана,
  дефицит остатков, проблемные агенты, первичка; находка старше 7 дней — «повторяется» и выше приоритет), просроченные задачи
  отдела, задачи на проверке дольше 3 дней. Только по отделам, которыми руководит пользователь; находка с правом — только при нём.
- Формулирует модель через AI Gateway (`work.suggestions`: учёт токенов, бюджет, лимиты) одним запросом на запуск. Ответ
  проверяется: числа названия, проблемы и обоснования — только из фактов источника (`EvidenceCheck`), исполнитель — из сотрудников
  отдела, срок — 1–30 дней, приоритет — из допустимых. Не прошло проверку или модель недоступна — текст по правилу из самих
  фактов, без исполнителя и срока («не предложен»).
- Каждое предложение — «Ожидает подтверждения». Руководитель подтверждает (можно поправить название, текст, исполнителя,
  приоритет, срок) — тогда создаётся задача от его имени и с его правами; или отклоняет с причиной. Сам диспетчер задач не создаёт.
- Без дубликатов: уникальный отпечаток источника за период (`alert:{ключ находки}`, `overdue:{отдел}:{неделя}`,
  `review:{отдел}:{неделя}`) — повторный запуск предлагает только новое, отклонённое не возвращается. Два одновременных
  подтверждения — одна задача (решение фиксируется условным обновлением).
- Запуск — кнопкой «Найти задачи» (руководителю отдела и руководству); новые предложения — уведомление руководителям отдела.

## Задачи агентам и супервайзерам

Вкладка «Агенты и супервайзеры» ставит задачу в Sales Base (`field.Tasks`) от имени сотрудника офиса: у задачи тип «Офис»
и имя автора. Исполнитель сразу получает уведомление в Sales Base и видит задачу в «Задачах». С точкой и сроком задача попадёт
в маршрут агента на этот день. Когда агент выполнит или перенесёт задачу, автору приходит уведомление в OneBase.

## Уведомления

- Задачи OneBase: назначение (`TaskAssigned`: «Новая задача: …», в тексте — постановщик, отдел и срок), изменение и отмена (`TaskChanged`), перенос срока (`TaskDeadlineChanged`),
  на проверку — постановщику (`TaskReview`), возврат на доработку (`TaskReturned`) и принятие результата (`TaskAccepted`) —
  исполнителю, выполнена — постановщику (`TaskDone`), комментарий (`TaskComment`), предложения AI-диспетчера — руководителям
  отдела (`TaskSuggestion`). Себе уведомление не приходит.
- Напоминания (`WorkTaskReminderWorker`, каждые 15 минут после 09:00 по Ташкенту): «срок завтра» — исполнителю, «просрочена» —
  исполнителю и постановщику. Одно уведомление на срок: отметка `DueSoonNotifiedFor` / `OverdueNotifiedFor` ставится условным
  обновлением в базе, поэтому повторный запуск, обновление страницы или второй экземпляр API не дублируют. Перенос срока —
  новое напоминание. Выключить — `Work:Reminders:Enabled = false`.
- Колокольчик в шапке OneBase — `work.Notifications`, в Sales Base — `field.Notifications`. Колокольчик OneBase проверяет новые
  уведомления раз в 30 секунд, пока страница открыта, а новое показывает всплывающим окном — на каждом устройстве, где открыт OneBase
  (пришедшее push-ом окном не дублируется).
- Push уходит на все устройства пользователя, где он вошёл и разрешил уведомления (каждое устройство и каждый сайт — своя подписка).
  На устройстве без разрешения колокольчик предлагает «Включить push на этом устройстве»; запрещённые в браузере уведомления и iPhone
  без установки на экран «Домой» — с подсказкой, что сделать.
- Push на телефон и компьютер (Web Push): включается кнопкой «Включить уведомления» (баннер в «Задачах» и на главной Sales Base,
  колокольчик → «Уведомления и геолокация», в Sales Base — профиль). Окно разрешения браузера появляется только по нажатию.
  Разрешение помнит браузер; при каждом запуске приложение тихо проверяет подписку устройства и привязывает её к вошедшему
  пользователю. «Отключить» там же запоминается на устройстве — запуск приложения уведомления снова не включает.
  При выходе подписка устройства удаляется — на общем телефоне задачи прежнего сотрудника не приходят; отключённому
  пользователю push не отправляется, его подписки удаляются.
- Уведомление OneBase (задача отдела), пришедшее в приложение Sales Base, открывается на основном домене OneBase: домен
  Sales Base без «sales.» (sales.1base.uz → 1base.uz). Поэтому другой `FIELD_HOST` — тоже вида `sales.<основной домен>`
  (по префиксу «sales.» его узнаёт и service worker).
- iPhone: push только в приложении, добавленном на экран «Домой» (iOS 16.4+), — приложение подсказывает, как установить.
- Ключи VAPID создаются при первом обращении и хранятся в `work.PushKeys` (закрытый — зашифрован Data Protection) вместе
  с контактом отправителя `https://1base.uz`. Настраивать ничего не нужно.
- Серверу нужен исходящий HTTPS к push-сервисам: `fcm.googleapis.com` и `android.googleapis.com` (Chrome, Android),
  `*.push.apple.com` (Safari, iPhone), `*.push.services.mozilla.com` (Firefox), `*.notify.windows.com` (Edge в Windows).
  Других адресов сервер подписки не принимает.

## Разрешения: уведомления и геолокация

Браузер сам решает, как долго помнить разрешение; приложение не спрашивает лишний раз: проверяет состояние заранее, спрашивает
только по нажатию (визит, маршрут, «Моё местоположение», «Включить уведомления»), переиспользует свежие координаты и при запрете
показывает, как включить. Экран «Уведомления и геолокация» показывает, что браузер запомнил на этом устройстве.
Окно разрешения геолокации, дважды закрытое без ответа, приложение само больше не показывает (после третьего Chrome на неделю
блокирует геолокацию сайта): визит идёт без отметки места, а спросить снова можно кнопкой «Разрешить геолокацию» на этом экране.

- Android (Chrome): в окне разрешения выбирать «Разрешить при использовании сайта», а не «Только в этот раз».
- iPhone: Safari не хранит разрешение геолокации долго — постоянно разрешить можно в настройках Safari для сайта.

## API (`/api/work`, вход обязателен; права — в сервисе)

| Метод | Путь | Что |
|---|---|---|
| GET | `departments`, `overview` | отделы с доступом и руководством; сводка обзора |
| GET | `tasks?scope=all\|my\|department\|archive\|board&department=&projectId=&status=&priority=&assigneeId=&from=&to=&dateField=created\|due&search=&sort=&desc=&page=&pageSize=` | таблица и канбан |
| GET, POST, PUT | `tasks/{id}`, `tasks`, `tasks/{id}` | карточка, создание, правка (срок, исполнитель, проект, даты, приоритет) |
| POST | `tasks/{id}/status` (`status`, `comment`), `…/archive`, `…/restore`, `…/block`, `…/progress` | действия |
| POST, PUT, DELETE | `tasks/{id}/checklist[/{itemId}]`, `tasks/{id}/comments`, `tasks/{id}/attachments`, `attachments/{id}` | чек-лист, комментарии, вложения |
| GET, POST, PUT | `projects`, `projects/{id}`, `heads`, `departments/{code}/heads`, `users`, `assignees` | проекты, руководители, выбор людей |
| GET, POST, PUT | `suggestions`, `suggestions/generate`, `suggestions/{id}`, `suggestions/{id}/accept`, `suggestions/{id}/reject` | AI-диспетчер |

Прежний вызов `GET tasks?department=код` (без `scope`) работает как раньше — его использует AI-инструмент `get_department_tasks`.

## База данных

Миграция `20261025172837_WorkTasksProjectsSuggestions` — только добавление: колонки `work."Tasks"` (проект, начало, процент,
блокировка, архив, отметки напоминаний, источник-предложение, «на проверке с») и таблицы `TaskChecklist`, `TaskComments`,
`TaskAttachments`, `TaskEvents`, `Projects`, `ProjectMembers`, `DepartmentHeads`, `TaskSuggestions` (уникальный
`Fingerprint`). Статус «На проверке» хранится строкой `Review` — старые данные не меняются. Для существующих строк:
выполненным — 100 %, уже просроченным до выпуска — отметка «уведомлено» (чтобы после выкладки не пришла разом вся прежняя
очередь просрочек). Откат — `Down` миграции удаляет добавленное (сами задачи остаются).

## Развёртывание

1. Резервная копия перед обновлением: `bash deploy/backup.sh` (дамп в `~/onebase-backups`).
2. Обновление: `bash deploy/update.sh` — миграции применяются при старте API, тома Docker не затрагиваются.
3. Проверка: `docker compose logs --tail 100 api | grep -i "WorkTasksProjectsSuggestions\|error"`, затем «Задачи» в OneBase.
4. Назначить руководителей отделов: «Задачи → Проекты → Руководители отделов» (руководство).
