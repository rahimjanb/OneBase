# Продажи: интеграция с Linko External API

Раздел «Продажи» OneBase строится на копии данных Linko SFA в нашей PostgreSQL (схема `linko.*`).
Браузер к Linko не обращается: `Frontend → backend OneBase → Linko External API`.

## Настройка доступа

1. **Настройки → Интеграции → Продажи → Linko**: адрес сервера (`https://<tenant>.linko.uz`) и токен External API.
   Токен хранится зашифрованным (ASP.NET Data Protection, ключи — в БД), в браузер не отдаётся, в логах и ошибках не печатается.
2. Запасной вариант — переменные окружения `LINKO_BASE_URL`, `LINKO_TOKEN`, `LINKO_PLAN_TOKEN` (`.env`, docker-compose).
3. Заголовок запросов: `Authorization: External <token>`; базовый путь `api/v1/integration/external-api/`.
4. «Проверить подключение» делает три лёгких `*_count` запроса; «Сверить» сравнивает `*_count` Linko с копией.

Права OneBase: `sales.read` — смотреть, `sales.manage` — запускать синхронизацию, вести оргструктуру и цели, `integrations.manage` — менять подключение.

## Какие ресурсы загружаются (только GET)

| Ресурс | Endpoint | Как загружается |
|---|---|---|
| Заказы | `orders/`, `orders_count/` | окно по `created_date` (прошлый + текущий месяц, при полной — 12 мес.), дальше изменения по `last_tm` |
| Возвраты | `order_returns/` | так же; строки `returned_products` |
| Визиты | `visits/`, `visits_count/` | последние 3 дня, раз в 6 ч — весь месяц |
| Сотрудники, точки, привязки | `users/`, `markets/`, `market_users/` | справочники |
| Товары, типы, территории | `products/`, `product_types/`, `borders/` | справочники, `last_tm` |
| Склады, прайс-листы и цены, поставщики, валюты, договоры | `stocks/`, `price_lists/`, `price_list_items/`, `providers/`, `currencies/` (массив без пагинации), `contracts/` | справочники |
| Остатки | `product_balances/` | полная загрузка — снимок целиком, иначе `last_tm` |
| Перемещения | `stock_transfers/` | все при полной загрузке, дальше `last_tm` |
| Платежи | `payments/` | окно по `created_date`, дальше `last_tm` |
| KPI-планы | `kpi_plans/` | окно года |
| Планы агентов | API планов `ru/api/v1/staff/staff_balance/` (отдельный токен) | при новом пересчёте Linko |

**Факт — только из Linko; планы регионов (РОП, «Завод») и оргструктура (РМ, СВР, дилеры) — данные OneBase**: в Linko их нет
(см. «Планы» и «Оргструктура» ниже). План ТП — его план по весу (`product_sales_weight`) из API планов. Плана первички в Linko нет —
первичка берёт план вида «Первичка» из `sales."RegionPlans"` (сейчас не загружен — плана нет). Командные планы супервайзеров в Linko к региону не привязаны (в пользователе и в `staff_balance` нет филиала или команды) —
в план региона не входят.

**POST-операции (`sync_*`, `order_synced`, `order_return_synced`, `payment_synced`, `set_currency_rate` и др.) не реализованы
и не вызываются.** Они меняют данные production Linko, а отметка «синхронизировано» скрывает документы из выдачи по умолчанию —
и для других интеграций (1С). Включать их можно только по отдельному решению и на тестовом сервере.

## Нагрузка и надёжность

- Не больше **4 одновременных запросов** на процесс (`Linko:Parallelism`, максимум 4): 12 потоков однажды положили прод Linko.
- Страница — `Linko:PageSize` (1000, максимум по документации), у возвратов `Linko:PageSizes:order_returns` = 500.
  Если сервер отдал страницу меньше запрошенной, клиент проверяет следующую и идёт реальным шагом — строки не теряются (`LinkoPaging`).
- Повторы только для GET: сетевые ошибки, таймаут, 429 и 5xx — паузы 3, 6, 9 с, всего 4 попытки; `Retry-After` учитывается (до 60 с).
- 401/403 — «сервер не принял токен», неверный JSON — «ответ не в формате API». Тело ответа и параметры (там бывает токен планов) в ошибки не попадают.
- Фоновая синхронизация — раз в 20 минут; после неё кэш отчётов сбрасывается и текущий месяц пересчитывается заранее.

## Правила расчёта (вторичка)

Правила — по документации «Полевого контроля» v174 (05.10.2026). Где эталон расходится со своей документацией, мы следуем
документации, а расхождение записано ниже как дефект эталона.

- **Факт = заказы − возвраты.** Заказ: статус из `Sales:SoldStatuses` — `delivered` и `given` («отдан»: магазин товар принял,
  статус не переставили; у отменённых и недоставленных приёмки нет — «статус не фильтруется» эталона на деле и есть эти два),
  **дата приёмки `accepted_time`** в месяце и не позже отчётного дня, филиал не «Завод» (`Sales:ExcludedBranches`) и не
  «К К Мерч» (`Sales:IgnoredBranches`). `accepted_time` приходит без часового пояса, по местному времени.
- **Вес и сумма заказа — по строкам** (`order_products`), везде: плитки, регионы, ТП, категории и «План и факт по месяцам»
  (история по месяцам тоже из строк, текущий месяц — по отчётный день, поэтому факт месяца в графике равен плитке). Шапка заказа не берётся.
- **Возврат:** статус `delivered` (`Sales:ReturnStatuses`), `created_date` возврата в месяце, филиал не «Завод» и не «К К Мерч»; вес и сумма —
  **по строкам** (`returned_products[].total_weight`, `price × amount`), не по шапке. Возвраты без строк не вычитаются и показываются в «Качестве данных».
- **Отчётный день** — последний полный день по местному времени (Ташкент, UTC+5), то есть вчера: `DataThrough` идущего месяца =
  min(конец месяца, последняя дата приёмки вторички не позже вчера). Список месяцев, отчётный день, «принят после отчётного дня» и заказы
  без даты приёмки считаются без «Завода» и «К К Мерч». Заказы этого месяца, принятые после отчётного дня — сегодня или с приёмкой в будущем
  (бывает в Linko), — войдут в отчёт на следующий день после приёмки, а пока показаны в «Качестве данных» (`acceptedInFuture`: приёмка
  со дня после отчётного по конец выбранного месяца, `SecondarySales.AcceptedAfterReport`; у закрытого месяца — 0, плашки нет). Чип
  «данные по ДД.ММ» в шапке страниц вторички — отчётный день идущего месяца; у закрытого месяца его нет. Время синхронизации — отдельно,
  в полосе раздела.
- **Прогноз** на конец месяца = факт ÷ отработанные дни × дней в месяце — **только у идущего месяца**: у закрытого (данные за все дни)
  API отдаёт `null` во всех прогнозах (плитки, регионы, ТП, категории и «Экспорт и опт» — с их «к прошлому месяцу», это прогноз к прошлому
  месяцу; план по выручке).
- **«К К Мерч»** (филиал 24, сетевые магазины, заказы оформляет админ; кроме точек-каналов в закрытом месяце — «Регионы-каналы») — не регион и не «Экспорт и опт»: его нет во вторичке совсем —
  ни строк факта, ни региона, ни месяцев и отчётного дня, ни АКБ по месяцам, ни визитов в его точках (календарь визитов, «Проблемные
  агенты»), ни склада в остатке, ни аутстока. На первичку `Sales:IgnoredBranches` не влияет.
- **Валюта:** суммы складываются только в базовой валюте (`Sales:BaseCurrency` = SUM). Вес заказа в другой валюте
  (у «Завода» есть USD) учитывается, сумма — отдельной строкой по валюте, без пересчёта по курсу.
- **АКБ** — уникальные `market.id`, у которых чистый вес за месяц (заказы минус возвраты по строкам) больше нуля;
  точка, вернувшая всю покупку, в АКБ не входит; точка, купившая у двух ТП, считается один раз (август 2026: 13 025 = 13 025 по всем регионам).
- **АКБ на агента** = АКБ ÷ число ТП месяца без вакансий: ТП подразделения, у которых в месяце есть продажи, визиты или план
  (не только продававшие).
- **Старые филиалы** Linko («Жиззах (эски)», «Андижон (эски) 1/2») считаются в текущем регионе с тем же названием
  (`Sales:OldBranchSuffix`, регулярное выражение окончания; пусто — не объединять).
- **Конверсия визита (страйк)** = заказы ТП, принятые в месяце (те же, что дали факт), ÷ выполненные визиты (`status=done`); бывает больше 100%.
  **Визиты без заказа** = визиты − заказы (у агента может быть меньше нуля — не обрезается). У региона, РМ и республики визиты и заказы —
  сумма по ТП (должность `Sales:SalesRepJobs` «Агент», вакансии тоже) — тот же набор, что в таблице «Команда ТП»; выполненные визиты
  остальных (операторы, супервайзеры, пользователи вне справочника) отдаются отдельным числом `visitsOutsideTeam`. Регион без визитов ТП —
  страйк «—». Визит «с заказом» (`visitsWithOrder`, карточка ТП) — заказ того же агента в той же точке по `created_date` (день ввода).
- **Календарь визитов** (DOC-rules §9.1, DOC-filters §1; `visitCalendar`, итог `visitCalendarTotal` — с сервера, в браузере ничего не
  суммируется). Строки — ТП подразделения (тот же набор, что плитки и «Команда ТП»: должность «Агент» и вакансии); выполненные визиты
  остальных (операторы, супервайзеры) — `visitsOutsideTeam` у строки региона и итога, в строки они не входят и не теряются. План ТП — его визиты
  по маршруту (`IsInPlan`, любой статус) за выбранные дни; «по маршруту» / «вне маршрута» — выполненные визиты по плану / без плана. **Заказы —
  принятые в выбранные дни** (те же, что дали факт: статусы вторички, отчётный день) и стоят в календаре по дню приёмки; заказ «с визита по
  маршруту», если в день его **ввода** (`created_date`, `SaleLine.CreatedDate`) в этот магазин был выполненный визит по плану — любого ТП;
  «вне маршрута» — если только визит без плана; иначе «без визита» (`ordersNoVisit`). Сверка за сентябрь 2026 (ТП 579, Андижон): заказы по
  дням приёмки и «по маршруту» совпадают с v174 день в день. «Не посещено» = max(0, план − по маршруту) и «% плана» = по маршруту ÷ план —
  **по итогам самой строки**: у региона, РМ и республики — по суммарному плану и суммарным визитам, а не сумме недоборов ТП (цвет —
  `planShareLevel`). Дни: `from`/`to` в адресе — «с 1-го по N-е» (по умолчанию N — отчётный день) или один день (`from=to`); дни после
  отчётного — «факта нет». **Отклонение от v174:** план региона и подпись «ОКБ · в маршруте» у эталона — из недельной таблицы «план визитов»
  (сентябрь 2026: план 101 105), которой в OneBase нет: план здесь всегда маршрут Linko (сентябрь — 63 419 визитов по маршруту у ТП), ОКБ —
  точки Linko региона, «в маршруте» — точки с визитом по плану за выбранные дни. Итог республики за сентябрь по нашему набору ТП: 28 347 заказов
  (по маршруту 18 073, вне маршрута 9 642, без визита 632); у v174 — 28 841 (18 069 / 10 772): разница — в наборе ТП (его справочник с ID 0
  у Жиззаха и перепутанными ID Коканда против должности «Агент» в Linko), а не в правиле.
- **Календарь месяца по регионам** (`calendar` у республики и РМ, `metric=kg|sum|akb&category=`): тот же расчёт, что у календаря по ТП региона
  (`SalesAnalytics.CalendarOf`); сумма дней по кг и деньгам равна итогу месяца, АКБ итога — уникальные ТТ за месяц.
- **«АКБ по месяцам»** (`akbMonths`): сервер отдаёт АКБ, кг и сум (`kg`, `sum` — те же строки и правила: чистые кг и выручка по месяцам,
  давние месяцы — из того же SQL-агрегата `SalesHistoryReader.AkbByMonthAsync`) и среднее за месяц по месяцам с данными (`average`,
  идущий месяц в счёт). Категории из `Sales:AkbChartHiddenCategories` («Песочный», DOC-filters §1) не отдаются; линий — не больше семи, по
  объёму (кг за месяцы), остальные категории есть в карточках. Переключатель АКБ / кг / сум — общий для всех карточек «по месяцам» до
  перезагрузки страницы (`AkbMonthsCard`, состояние в модуле, не в адресе; DOC-filters §12). Компонент ничего не считает.
- **Проблемные агенты:** оцениваются ТП с ≥ 20 визитами (`Sales:Flags:MinVisits`); медиана региона — по ТП без вакансий, с ≥ 20 визитами
  и без флага «данные не сходятся». Заказов больше, чем визитов (конверсия > 100%), — риск «данные не сходятся», низкая конверсия у такого
  агента не оценивается. Мелкий чек — чек ниже ½ медианы (`SmallCheckOfMedian` = 0,5) при конверсии ≥ 25% и ≥ 20 заказах. «Категорий» у ТП —
  только категории отчёта (`Sales:Categories`; «бонус» и прочие типы Linko не считаются). Вакансия — «вакан» в имени (`Sales:VacancyMarkers`)
  или ID 0. **Порядок списка** — по тяжести, как в v174 (правила в документации нет, взято из app.js): `score` = 10 × критичных + 4 × рисков +
  (1 − min(страйк, 1)) × 3 у оцениваемых (≥ 20 визитов), при равной тяжести — меньшая выручка выше, вакансии последними; `rank` — место в этом
  списке (`SalesMath.ProblemScore`). `found` (ТП с замечаниями), `directions` (РМ для фильтра) и `fact` (сколько кг без агента) — с сервера.
- **Цели («% от цели»):** от 95% цели — зелёный, от 75% — оранжевый, ниже — красный (`SalesMath.TargetLevelOf`). **Выполнение** (плитки,
  регионы, ТП, категории, планы Linko, % плана визитов): от 90% — зелёный, от 60% — оранжевый, ниже — красный (`SalesMath.ExecutionLevelOf`,
  поля `executionLevel` / `forecastExecutionLevel` / `planShareLevel`); прогноз к плану по категориям — от 100% / от 90% (`forecastLevel`).
  Интерфейс только раскрашивает по уровню (`levelClass`, `levelTone`); пороги в браузере не считаются. У ТП с сервера и «сум с точки» /
  «кг на точку» (`revenuePerOutlet`, `kgPerOutlet`).
- **Сбросы (DOC-filters §12):** смена месяца на странице ТП или магазина уходит к региону (нет региона — к республике), план сохраняется
  (`MonthExit`, `SalesToolbar`); на остальных страницах — остаётся страница, сбрасываются `from`/`to`, `day`, `dealer`. Раскрытые секции,
  сортировки и раскрытые строки таблиц привязаны к месяцу (`key` по периоду) — после смены месяца старых выборов нет.
- **«Ещё не купили»:** база — точки прошлого месяца, молчат — ещё не купившие. Регион, где в месяце нет ни одной покупки, — «нет данных»
  (`noData`, доли нет): это почти всегда дыра в выгрузке. Итог таблицы (`notBoughtTotal`) считает сервер.
- **Категории** — по `product.type` (`Sales:Categories`): Помадка = типы 8, 17–21; «Снек» (22) = Придзел. Остальные типы — в диагностике.
- Доставщики/курьеры/экспедиторы (`Sales:NonSalesJobs`) — не ТП.
- **Не вторичка — свои статусы:** экспорт «Первичка → Экспорт» — только `delivered` (`Sales:ExportSoldStatuses`, сверен с эталоном до
  килограмма); Sales Base (`/api/field`) — `Sales:FieldSoldStatuses` = `delivered` и `Sales:FieldVacancyMarkers` = «вакант», его поведение
  от правил вторички не зависит.
- **Списки `Sales:*` в настройках заменяют значения по умолчанию из кода** (`SalesOptionsBinding`): стандартная привязка .NET дописывает
  элементы массива к значению из кода (`SoldStatuses` читался как delivered, given, delivered, given, а `["delivered"]` список не сужал).
  Так — у всех строковых списков `SalesOptions` и у списков в словарях (`ExportCountries`, `PlanIndicatorCategories` — по заданному ключу);
  пустой массив — пустой список; повторы убираются (статусы — с учётом регистра, остальное — без). Проверка — `SalesOptionsBindingTests`.
- Правила в коде: `SecondarySales` (чистые функции), `SalesPlans`, `SalesStructure`, `AgentFlags`, `SalesMath`, `SalesAnalytics` и тесты
  `SecondarySalesTests`, `SalesPlansTests`, `AgentFlagsTests`, `SalesMathTests`, `SalesAnalyticsTests`, `LinkoPurgeTests`.

13 415 862 156 сум. Вся разница объяснена: окно выгрузки по `created_date` (с 20-го прошлого месяца) выбрасывает принятые заказы —
+44,00 кг / 1 446 700 сум (Бухоро, 8 заказов, созданных 03–13.08); плитки регионов v174 берут вес шапки заказа вместо строк — +13,22 кг /
966 600 сум (Самарканд, заказы 578221 и 568389). АКБ плиток v174 за сентябрь–октябрь — точки с любым заказом (13 703), что расходится
с его же документацией и августом (нетто > 0); в блоках категорий v174 магазин у двух ТП считается дважды. Справочник ТП v174
(ID = 0 у всего Жиззаха, перепутанные ID Коканда) — тоже не повторяется: ТП — по должности Linko.

## Регионы-каналы (Урикзор, Сети)

- **Что это:** точки завода, которые «Полевой контроль» считает отдельными регионами: «Урикзор» (направление «Базар») — Низомиддин
  (точка Linko 26782 «Низомидин Урикзор»), Мурод бозор/Д63 (26576 «Murod D/63»); «Сети» (направление «КА», ключевые клиенты) — Хавас
  (26614), Макро (32553 «Макро РЦ»), Магнум (13686–13689, заказов в Linko нет), Энг якин маркет (26498), Барака маркет (26771), Болажон Сити
  молл (69891, филиал «К К Мерч»), Зарафшон (28012), Молочный домик (27994), Assorti Diskount Market (38159). Список — `Sales:ChannelRegions`.
- **Правило** (`SecondarySales.Build`, `ChannelsOn`, `ChannelBranch`): заказы этих точек из филиалов `Sales:PrimaryOrderBranches` («Завод»,
  «К К Мерч») в проданных статусах (delivered и given — не только «доставлен»), по дате приёмки, по строкам; возвраты — как во вторичке.
  Подключаются **только в закрытом месяце** (отчётный день месяца — его последний день); в идущем месяце регионы-каналы пустые, заказы «Завода»
  остаются в «Экспорте и опте», «К К Мерч» — вне вторички. Заказ той же точки у дилера — продажа дилера, не канал. Первый месяц канала —
  `Since` («гггг-ММ»): «Урикзор» — с августа 2026, как в «Полевом контроле» (раньше в нём 0); «Сети» — с начала данных.
  Страница региона-канала — без подсказки про СВР и дилера (`RegionView.IsChannel`): в «Настройках продаж» их не задать.
- **Где видно:** регион с виртуальным филиалом (−1, −2 … по порядку настройки) и постоянным id (`SalesStructure.StableId`), направление —
  канал из «Настроек продаж» с тем же названием или новое из настройки. Факт, выручка, категории, календарь месяца, месяцы года
  (`SalesDataLoader.ChannelHistoryAsync`, ряды «кг» и «сум» в `SalesHistoryReader.AkbByMonthAsync`) — с каналами; **АКБ, ТТ артикула и
  «Только он» — без них** (у канала нет полевой базы ТТ; в «Полевом контроле» АКБ этих регионов 0). Заказы каналов оформляет офис
  (Admin Ritm, склад) — в «ТП вне справочника» они не попадают. Плана у каналов нет (в «Полевом контроле» тоже). «Продажи по SKU»,
  первичка, остатки и аутсток каналы не меняют (в эталоне их там нет; первичка и так считает эти точки прямыми клиентами завода).
- **Сверка с «Полевым контролем» (сборка 06.10.2026), кг:** «Сети» — апрель 497,42 и май 2 167,39 совпадают; январь 780,33 / 771,64,
  февраль 1 397,42 / 1 373,25, март 2 154,74 / 2 139,68, июнь 2 420,83 / 2 511,26, июль 1 206,31 / 1 242,00, август 635,50 / 934,10,
  сентябрь 2 864,38 / 2 795,70. Расходятся отдельные точки, и не по одному правилу (август: Хавас 878,6 в эталоне при 533,6 в Linko, Барака —
  только «отдан» без «доставлен»; май: у Assorti в эталоне оба статуса) — значения эталона в эти месяцы не из Linko, а из его таблицы
  отгрузок. «Урикзор»: январь–июль 0 и у нас (`Since` 2026-08), и в эталоне; август 14 628 и сентябрь 10 641,10 в эталоне — из таблицы; у нас из Linko
  14 866,42 и 11 935,58 (Низомиддин 3 649,96 / 3 301,2, Мурод 8 285,62 / 7 195,9). «Фирменный магазин» (144 кг в сентябре эталона) — ни
  точки, ни склада в Linko нет. Отклонение — источник данных (решение: только Linko и данные OneBase).

## Планы (вторичка)

- **План — РОП (по умолчанию) или «Завод»**: `plan=rop|factory` в адресе страниц и в API (`SalesController.PeriodQuery.Plan` — строка:
  `factory` без учёта регистра — «Завод», любое другое значение — РОП, без ошибки 400, `SalesPlans.Parse`; во фронтенде так же —
  `planOf` в `lib/sales/query.ts`, в адрес пишется только `plan=factory`). Переключатель «План РОП / План «Завод»» — в полосе раздела, только
  на страницах с планом подразделений (старт вторички, республика, РМ, регион). Какие планы заведены на месяц, сообщает ответ страницы
  (`period.availablePlans` — `rop`, `factory` или ни одного, `SalesPlans.Available`; `period.plan` — по какому плану посчитан ответ):
  вид, которого на месяц нет, переключатель выбрать не даёт. Вид плана — часть ключа кэша расчёта (`sales:{год}-{месяц}:{Rop|Factory}`, `SalesPlans.CacheKey`).
  AI-инструменты, проактивные проверки и прогрев после синхронизации берут план по умолчанию — РОП. Страницы без плана подразделений
  (ТП, магазин, ассортимент, экспорт, «Проблемные агенты», «Планы») считаются по плану по умолчанию — второй расчёт месяца ради них не строится.
- **Источник** — `sales."RegionPlans"`: регион × вид (`Rop` / `Factory`) × год × месяц × категория (`CategoryId` — тип товара Linko, `null` —
  план без разбивки), кг. Загружены из «Полевого контроля»: РОП — январь–сентябрь 2026, «Завод» — сентябрь 2026; суммы равны эталону
  (сентябрь: РОП 484 937 кг, «Завод» 470 002 кг — по каждому региону и категории). Ввода и загрузки планов в интерфейсе нет. Загрузчик читает
  год выбранного месяца и следующий месяц; строки старого филиала («эски») — в текущем регионе, строки «Завода» и «К К Мерч» не читаются.
- **Выполнение** = факт ÷ план (DOC-rules §3): у региона — весь его факт (и ТП без плана, и факт без агента); у РМ и республики — весь
  факт их регионов ÷ сумма планов регионов: регион без своей строки плана добавляет факт, но не план (июнь 2026 по РОП: у Олмалика плана нет,
  республика 325 995,93 / 387 900 = 84,04%, а не 83,60% без его факта). Прогноз выполнения = прогноз ÷ план (только у идущего месяца).
  Сентябрь 2026 по плану РОП (план есть у всех 19 регионов): республика 365 112,48 / 484 937 = 75,29% (v174 по тем же 19 регионам — 75,28%:
  вся разница — в факте Бухоро и Самарканда, дефекты эталона выше), регионы — как в v174. Плитка республики v174 показывает 78,05%: в её факт
  входят Урикзор и Сети (13 437 кг, плана у них нет); в OneBase они считаются из Linko — см. «Регионы-каналы».
- **Нет планов регионов выбранного вида на месяц** (октябрь 2026; «Завод» вне сентября) — план региона и республики из Linko: сумма весовых
  планов ТП, выполнение — по факту этих ТП (ТП без плана не «выполняют» чужой план). Ответ это показывает: `kpi.planSource` = `linko`
  (`rop` / `factory` — планы регионов); плитка выполнения пишет, какого плана нет: «плана РОП на этот месяц нет — план ТП из Linko»
  (или «плана «Завод» …»). Источники в одном месяце не смешиваются: в месяце с планом РОП регион без своего плана остаётся без плана
  (его факт входит в выполнение РМ и республики).
- **«План и факт по месяцам»** — у каждого месяца свой источник (`months[].planSource`): план регионов выбранного вида, где он есть,
  иначе сумма планов ТП региона из Linko.
- **План по категориям** (DOC-rules §9.1) — сумма плана «регион × категория» по регионам охвата; тип Linko сводится к категории отчёта
  (`Sales:Categories`: типы 8, 17–21 — Помадка, «Снек» — Придзел). Факт — все строки категории в охвате. Выполнение, «осталось»
  (`remainingKg`), прогноз и прогноз к плану (`forecastExecution`; цвет `forecastLevel`: от 100% — зелёный, от 90% — оранжевый, ниже —
  красный) и итог по строкам с планом (`categoryPlanTotal`) считает сервер. Категории с продажами без плана — строки «плана нет», в итог
  не входят. Без планов регионов — по весовым показателям ТП в Linko (факт — ТП с этим планом).
- **План ТП** (карточка ТП, «Команда ТП») — всегда его весовые показатели в Linko; плана ТП по категориям из планов регионов нет.
- **План на следующий месяц** — планы регионов выбранного вида на следующий месяц, если они уже есть (`nextMonth.source` = `rop` / `factory`;
  в регионе — по категориям), иначе — планы ТП из Linko; изменение к текущему месяцу (`change`) считает сервер.

## Оргструктура

- **Направления** (`sales."Directions"`): РМ (`RegionalManager`) и каналы (`Channel` — Базар, ключевые клиенты), руководитель, описание
  (зона), порядок. **Регион** (`sales."Regions"`, строка на филиал Linko, создаётся синхронизацией) — направление, СВР, дилер. В Linko этого
  нет — ведётся в «Настройках продаж» (`/sales/setup`; API `POST/PUT/DELETE /api/sales/setup/directions`, `PUT /api/sales/setup/regions/{id}`,
  право `sales.manage`, запись в аудит, сброс кэша отчётов). Название региона — название филиала Linko: по нему склеиваются старые филиалы
  и склады, поэтому в «Настройках продаж» оно не редактируется. Синхронизация обновляет его по последнему заказу филиала: переименовали
  филиал в Linko — переименуется и регион (направление, СВР и дилер остаются).
- Читает `SalesDataLoader` (`SalesStructure.Build`): карточки и страницы РМ (`/sales/directions/{id}`; каналы — после РМ, направление без
  регионов вторички карточки не даёт), охват РМ в «Ассортименте», фильтр РМ в «Проблемных агентах», СВР и дилер в регионе, дилер в «Первичке»
  и «Аутстоке». «Завод», «К К Мерч» и старые филиалы регионами вторички не являются — их направление, СВР и дилер не используются.
  Профили агентов (`sales."AgentProfiles"`) не читаются: ТП и его регион — по Linko.
- Структура «Полевого контроля» v174 (для заполнения): РМ 1 — Ташкент, Сырдарья, Бекобод, Олмалик, Кибрай; РМ 2 — Коканд, Фаргона,
  Наманган, Андижон; РМ 3 — Самарканд, Термез, Карши, Денов, Шахрисабз, Жиззах; РМ 4 — Хоразм, Бухоро, Навои, Нукус. Базар (Урикзор) и КА
  (Сети) — регионы-каналы без филиала Linko (`Sales:ChannelRegions`, см. «Регионы-каналы»); в «Настройках продаж» их нет.
- **«Очистить данные и загрузить заново»** (`LinkoSyncService.PurgeAsync`) удаляет только пришедшее из Linko — схему `linko` и
  `sales."StaffPlans"` (`LinkoSyncService.PurgedTables`). Направления, регионы с направлением, СВР и дилером, планы РОП и «Завод», планы
  и профили агентов, цели остаются: регион после загрузки находит свой филиал по `LinkoBranchId` (`EnsureRegionsAsync` добавляет новые
  филиалы, а у известных обновляет название по последнему заказу — `LinkoSyncService.SyncRegions`). Удалять регионы нельзя ещё и потому, что
  `sales."RegionPlans"` удаляются вместе с регионом (каскад). Проверка — `LinkoPurgeTests` по модели БД. При смене сервера Linko регионы
  прежнего сервера тоже остаются — их стоит проверить в «Настройках продаж».

## Ассортимент и «Продажи по SKU»

Правила — по документации «Полевого контроля» v174 (DOC-rules §9.2, §9.6; DOC-filters §2, §6); строки продаж — те же, что во вторичке
(`SecondarySales`: delivered и given по дате приёмки, возвраты по строкам, без «Завода» и «К К Мерч»). Код: `SalesMath` (`Positive`, `SkuMarkets`,
`SkuTt`, `PositiveSkus`, `SoloByProduct`, `MatrixLevelOf`, `AbcOf`), `SalesAnalytics.Catalog` / `.Drill` / `CategoryCardsFor`, `SkuSalesReport`,
`SkuSalesService`, `SalesHistoryReader.SkuSalesAsync`; тесты — `AssortmentTests`, `SkuSalesTests`.

- **Положительная строка SKU** (DOC §9.6 «АКБ — точки с положительной строкой»): у ТТ есть товар, если её чистая строка по нему в охвате
  (заказы минус возвраты, по всем её ТП) положительна — кг > 0 **или** сумма > 0. **ТТ артикула** (АКБ SKU) — уникальные ТТ с такой строкой:
  ТТ, купившая у двух ТП, считается один раз. Одно правило (`SalesMath.SkuTt`) — у артикула категории (ТТ и дистрибуция), страницы артикула,
  разбивки по регионам / ТП / магазинам, «Товаров», «отстаёт по товарам» у ТП, матрицы и «Продаж по SKU».
- **«Продаётся»** в охвате — ТТ артикула больше нуля. Артикул, погашенный возвратами в одной ТТ и купленный в другой, продаётся (Коканд,
  август 2026, SKU 336: итог региона 0 кг, но 3 ТТ с положительной строкой — «SKU идёт» 76 / «не возят» 63 / «пропало» 6, как в v174).
  Статусы прежние: продаётся → пропал (продавался в полном прошлом месяце в этом охвате) → не возят (здесь нет, по республике идёт) → нет продаж.
- **АКБ категории** — по документации: ТТ с чистым весом категории больше нуля (`SalesMath.Akb`), а не правилом строки.
- **«Продаётся N из M SKU»**: M — SKU категорий отчёта с продажами во вторичке **с 1 января года по конец выбранного месяца**
  (`SalesDataLoader.AssortmentWindow`; у идущего месяца — по отчётный день) плюс проданные в прошлом месяце (для «пропало» в январе);
  N — SKU, которые продаются; «молчат» = M − N. Весь каталог Linko и SKU, которые продавал только «Завод», в M не входят. M — один на всю
  компанию и от охвата не зависит: на вкладке «Ассортимент» и странице категории список категорий — по каталогу
  (`SalesAnalytics.CatalogCardsFor`: категории с SKU в ассортименте или с продажами в этом либо прошлом месяце), категория без продаж в охвате
  остаётся карточкой «продаётся 0 из M» со своими SKU «не возят» / «нет продаж» (после карточек с продажами). Карточки категорий во
  «Вторичке» (регион, РМ, республика) категории без продаж по-прежнему не показывают (DOC-filters §1).
- **«Только он»** (DOC §9.2): моно-точка — ТТ охвата с положительной строкой ровно по одному SKU категорий отчёта (бонусы и подарки не
  считаются). У артикула — сколько моно-точек держатся на нём и их доля от его ТТ (`SkuRow.Solo`, `SoloShare`, `ProductView.Solo`), у охвата —
  всего моно-точек (`AssortmentSummary.Mono`, `CategoryView.Mono`).
- **Матрица «товар × регион»** (DOC §9.2): 20 товаров категорий отчёта с наибольшей выручкой в охвате × регионы с продажами; клетка —
  дистрибуция: ТТ региона с положительной строкой товара ÷ АКБ региона; «Всего» (средняя) — дистрибуция товара по всему охвату:
  Σ ТТ с товаром ÷ Σ АКБ регионов. Красный — товара в регионе нет, оранжевый — клетка меньше 40% «Всего»; цвет (`MatrixCell.Level`) считает
  сервер. Регионов с продажами меньше двух — матрицы нет.
- **«По регионам»** — только у охвата из двух и больше регионов (DOC-filters §2); регион без единой покупки за месяц не пропадает, а приходит
  строкой «нет данных» (`NoData`, счётчики — нули). У артикула направления из одного региона разбивка — по ТП региона.
- **«Товары»** — только восемь категорий отчёта; доля — от выручки этих товаров; число товаров других типов Linko (бонус, подарки) —
  `ProductsOutsideReport` (их вес и сумма — в «Качестве данных»). **Доля по весу** артикула в категории (`SkuRow.WeightShare`) — с сервера.
- **Магазин**: «Доля в объёме ТП» — **по весу**: кг магазина ÷ кг ТП (сентябрь, 24770 у ТП 396 — 28,01%, как в v174).
- **ТОП** — `Sales:TopProducts` (59 кодов списка ТОП «Полевого контроля», точные коды Linko без учёта регистра; `TopProductSet`): метка «ТОП»
  у артикулов, «Товаров», магазина, матрицы, страницы артикула и «Продаж по SKU». Аутсток пока читает тот же список своим `TopRule`
  (тот же код в настройке; перевод аутстока на `TopProductSet` — вместе с остальной правкой остатков).
- **«Продажи по SKU»** (`/sales/sku-sales`, `GET /api/sales/sku-sales?from=ГГГГ-ММ&to=ГГГГ-ММ&region=&top=all|only|not&abc=all|A|B|C&cat=Кекс,Помадка`,
  право `sales.read`; по умолчанию — с января года последних данных по их месяц): любой отрезок месяцев, в том числе через год, не длиннее
  24 месяцев и не дальше года, следующего за годом последних данных (ошибки периода — 400 с текстом по-русски: «Период — до ГГГГ-ММ.»).
  Регион — только из списка регионов (`SkuSalesService.RegionsOf`: регионы вторички по названию, старые филиалы — в текущем регионе);
  «Без региона» при отрезке без продаж вне структуры — пустой охват, а не вся страна. Новых источников нет: один SQL-агрегат
  `ISalesHistoryReader.SkuSalesAsync` по правилам вторички (дата приёмки, проданные статусы, без «Завода» и «К К Мерч», возвраты по строкам
  и дате создания, сумма возврата — количество × цена; выручка заказа не в сумах — 0) — кг и сумма по товару × региону × месяцу за дни
  `SkuSalesService.Window` (с 1-го числа начала отрезка по конец его последнего месяца, но не позже отчётного дня). **АКБ SKU** за отрезок —
  различные ТТ, у которых месячная строка товара положительна хотя бы в одном месяце (не сумма по месяцам). Строки — SKU категорий отчёта;
  ранг, доля, накопленная доля и **ABC** — внутри выборки после фильтров региона, ТОП и категорий, до фильтра ABC: по убыванию кг,
  A — накопленная доля ≤ 80% (вместе с самим SKU), B — ≤ 95%, остальные — C. «Регионов» — где у SKU кг > 0 (по стране). **Динамика** —
  кг в день в первом и последнем квартале отрезка (дни с данными; есть, если отрезок захватывает два квартала и больше) — только от
  положительной базы: отрицательное нетто первого квартала (возвраты больше продаж) динамики не даёт; «новый» — в первом квартале продаж
  не было (кг в день не больше нуля), а в последнем есть. **Карточки категорий** — как у эталона: фильтры региона, ТОП и ABC действуют
  (ABC — внутри набора без фильтра категорий), фильтр категорий — нет (иначе выбрав одну, на другую не переключиться); «доля выборки»

## Первичка и остатки

- **Первичка** (DOC-rules §3, §9.3; вход: «Республика» / «Экспорт»; страница республики — как в «Полевом контроле»; правила —
  `PrimaryMath`, `PrimaryService`, тесты `PrimaryTests`). Эталон берёт первичку из таблицы ГП (дилеры, базары, фирменный магазин, сети);
  у нас — только Linko (решение: без таблиц и загрузки файлов), ближайший аналог — два источника, сложенные в одни строки:
  - **перемещения** `stock_transfers` со склада завода (`Sales:FactoryStocks`) на склады дилеров, статусы `given`/`accepted`
    (`Sales:ShippedTransferStatuses`). Склад «Экспорт» (`Sales:ExportStocks`) — не дилер: перемещения завод ↔ экспорт в первичку не входят
    (август 2026 — 52,7 т туда, 8,0 т обратно), это внутреннее движение склада, а не экспорт;
  - **заказы прямых клиентов завода** — филиалы `Sales:PrimaryOrderBranches` («Завод», «К К Мерч»), точки **не** экспортного типа
    (`Sales:ExportMarketTypes`): базары (Murod D/63, Низомидин Урикзор), фирменный магазин (Ятт Илгоров), сети (Havas, Барака, Макро,
    ASSORTI, Bolajon citymall); статусы `Sales:PrimaryOrderStatuses` — `delivered` и `given` (у этих точек «отдан» и есть отгрузка);
    кг — вес строки, сумма — `total_price` строки в базовой валюте (заказ в другой валюте — вес без суммы, отдельной заметкой); минус
    их возвраты по строкам (статус `Sales:ReturnStatuses`, деньги = количество × цена, дата — создание возврата). Точки
    `Sales:PrimaryExcludedMarkets` (название или id) не входят: «Дегустатсия + Акция» (id 27896) — дегустации и акции. Каждая точка —
    отдельный контрагент группы `direct` («Прямые клиенты завода» — свои таблицы плана-факта и «С начала года»), склады дилеров — группа `dealer`.
    Во вторичку эти заказы по-прежнему не входят (`Sales:ExcludedBranches`, `Sales:IgnoredBranches`).
- **Возвраты вычитаются** (DOC-rules §3: возвраты — строки со знаком минус, простое сложение даёт нетто): перемещение со склада дилера
  на завод — строка дилера-отправителя с минусом в месяце, строках дилеров и категорий, товарах, календаре, «С начала года» и клиентах
  по месяцам. Плитка «Возвраты» с начала года остаётся (доля — от отгруженного без возвратов).
- **Дата**: перемещения — дата доставки (`DeliveryDate`, с ней сходится день таблицы первички: август 93,9%, сентябрь 99,9% кг по
  «регион × день» против 79,4% и 84,4% по выдаче), без неё — выдача, приёмка, создание; заказы — дата создания (`created_date`, как день
  таблицы; по приёмке совпадает 16%). Аутсток датирует перемещения сам — по выдаче, первичка на него не влияет.
- **Склады → регионы** (`Sales:StockRegionAliases`, `SalesOptions.StockRegionName` — чтобы остаток и аутсток взяли тот же список):
  «Коканд бозор» → Коканд (дилер Кахрамон Кукон), «Андижон эски 2» и «Андижон эски склад» → Андижон, «Жиззах (эски)» → Жиззах; одна строка
  на регион. Подпись строки — дилер региона (`sales."Regions".DealerName`, «Настройки продаж»), регион — второй строкой; без дилера —
  название региона или склада. Словарь в настройках дополняет записи из кода: словарь без учёта регистра (`StringComparer.OrdinalIgnoreCase`,
  привязка его сохраняет), поэтому ключ из настроек заменяет запись из кода с тем же складом в любом регистре, а не добавляется второй.
  **Дилер — только склад, чей регион (после `StockRegionAliases`) есть в справочнике регионов** (`sales."Regions"`, без «Завода» и
  «К К Мерч»). Склады без региона — «Основной», «Оптом», «Нукус (интеграция учун)», «Абдуманноб ААА» — не дилеры и не клиенты: их перемещения
  в первичку не входят и отдаются отдельно (`otherStocks` в API: склад, перемещений, кг за год; заметкой на странице). 2026 год: «Основной» —
  2 перемещения, 54 кг.
- **Деньги**: «Сумма (цена дилера)» (`sumFactory` в API) — сумма перемещения или заказа: по этой цене дилер берёт товар у завода, это
  «сумма дилера» эталона (совпадает по каждому артикулу). «Сумма по цене продажи дилера» (`sumDealer`) — количество × максимальная цена
  прайса `Sales:PrimaryDealerPriceList` («Дилердан чикиш нарх»); в эталоне такой суммы нет. **Цены завода в Linko нет**: «сумма завода»
  эталона (≈ цена дилера ÷ 1,057) ни одним из 28 прайсов не воспроизводится, поэтому единицы «сумма завода» у нас нет. Коробки — по весу
  коробки из названия (у весовых товаров — любой, у штучных — если в коробке целое число штук).
- **План** — `sales."RegionPlans"` вида `Primary` за год (регион плана → строка его дилера); плана первички в Linko нет, загружен он не
  был — первичка сейчас без плана. План, выполнение, «осталось» — только в кг; строка с планом остаётся и без факта, без плана и факта — скрыта.
- **Отчётный день и прогноз — по дате данных**, а не по сегодняшнему дню: отчётный день (`PrimaryMath.DataLimit`) — вчера по местному
  времени и не позже дня синхронизации; **строки позже него (сегодня, плановая доставка в будущем) в отчёт не входят** — ни в факт, ни в плитки,
  календарь, прогноз, `workedDays` и «данные по» (как `salesEnd` во вторичке; их число — заметкой «после отчётного дня», войдут, когда их
  день станет отчётным). Дата данных (`asOf`) — последний день со строкой не позже отчётного дня; доля месяца = день `asOf` ÷ дней в месяце;
  прогноз = факт ÷ доля — только у месяца `asOf`, если прошло не больше 98% его дней. API отдаёт `running` (выбранный месяц идёт) и
  `runningMonth` — страница не решает «идёт» по часам браузера. Так же у экспорта (дата данных — заказы филиала «Завод»; плитка «Экспорт»
  на входе — тоже по отчётный день).
- **Клиенты по месяцам** (DOC §9.3, «АКБ / кг / сум»): контрагентов с нетто кг за месяц больше нуля, в категории — с нетто кг категории
  больше нуля; кг — нетто, сум — по цене дилера; месяцы с 1-го по выбранный, категории без отгрузок скрыты (`clients` в API). «Сред/мес»
  (`average` у итога и у каждого ряда) считает сервер — по закрытым месяцам с данными, идущий месяц не в счёт (неполный месяц занижал бы
  среднее); страница только показывает.
- **Календарь отгрузок** (DOC-filters §3): `from`, `to`, `day`, `dealer` в `/api/sales/primary` и `/api/sales/primary/export` — сервер отдаёт
  матрицу «контрагент × день» за период (по умолчанию все дни с отгрузкой; перепутанные границы меняются местами), итоги строк и дней,
  «Дней», разбор выбранного дня и/или контрагента по товарам. Строки — только контрагенты с отгрузкой в периоде. Смена месяца сбрасывает
  период и разбор. Все доли, выполнение, итоги таблиц, цены за кг, наценку и долю возвратов считает сервер — страница только форматирует.
- **«С начала года»** — месяцы с января по выбранный (у эталона — всё до даты данных, при любом выбранном месяце).
- **Сверка с эталоном (таблица ГП)**: август 2026 — 408 993,65 кг против 408 387,75 (+605,90 кг, +0,15%), сентябрь — 369 524,27 против
  369 405,41 (+118,86 кг, +0,03%); до изменений было −3,50% и −3,83% (без точек завода, без вычета возвратов). Деньги августа по цене дилера —
  13 403 418 743 против 13 403 716 435. Клиенты по месяцам — на одного меньше эталона (август 25 против 26, сентябрь 26 против 27): эталон
  делит одну точку Linko «Ятт Илгоров» на две строки (см. ниже), у нас это один клиент; склады без региона («Основной») клиентами не считаются.
  **Отклонения от эталона (не повторяем):** точка «Ятт Илгоров» у эталона разделена на «Фирменный магазин» (отданные заказы) и «Накт пул
  бозор» (доставленные) — у нас это одна точка Linko; строки, которые есть только в таблице (август: Самарканд +1 812 кг в Linko и нет в
  таблице, Хоразм −744 кг, возврат Наманган 856 кг только в таблице), — данные Linko как есть; февраль 2026 у таблицы на 33 т меньше Linko
  (таблица, судя по всему, неполная); плитки месяца и «Клиенты по месяцам» эталона показывают сумму по цене завода — у нас сумму по цене
  дилера (цены завода в Linko нет); разрез «Ключевые клиенты (КА)» и прямой ввод плана первички — не сделаны (нужны список сетей и решение
  о загрузке плана).
- **Экспорт** (`/sales/primary/export`) — заказы филиала «Завод» (`Sales:ExcludedBranches`) торговым точкам с типом `EXPORT`
  (`Sales:ExportMarketTypes`), статус `delivered` (`Sales:ExportSoldStatuses` — не статусы вторички), дата — приёмка; возвраты по строкам вычитаются. Тип EXPORT стоит и у части
  магазинов других филиалов — их заказы в экспорт не входят. Страны отдельным полем в Linko нет: она берётся из названия или адреса
  точки по словарю `Sales:ExportCountries` («Daler Tojikiston» → Таджикистан, первое совпадение); Россия — по точкам, как у эталона:
  «Россия (Дагестан)» — «Дагестан ФАЙДА», «Россия (Уфа)» — «ООО ВЛАДКОН» (в Linko адрес — Москва), остальные российские — «Россия»;
  «Казахстан - Монголия» (Астана) — Казахстан (у эталона — «Экспорт (уточнить)»). Точка без совпадений показывается своим названием.
  Коробок у экспорта нет (`boxes` = null): в строках заказа Linko только штуки и кг. Сверка с «Полевым контролем» за январь–сентябрь 2026 —
  до килограмма и сума по месяцам и дням (сентябрь — 102 999,7 кг, 3 793 364 237 сум); по странам — тоже (апрель: Дагестан 12 000 кг +
  Уфа 10 330 кг, как у эталона), кроме августа: «Казахстан - Монголия» (2 868 кг) у нас в Казахстане.
- **Рекомендуемый остаток** (`/sales/stock`) — `product_balances.balance` в **штуках** (строкой «0.000000000» — разбирается как число);
  снимок на дату загрузки, без периода. Кг = штуки × вес штуки (Σ `total_weight` ÷ Σ `amount` по строкам заказов за год; без продаж —
  из фасовки в названии, с пометкой ≈); коробки = кг ÷ вес коробки из названия, если в коробке целое число штук.
  Стоимость = штуки × входная цена дилера (прайс `Sales:StockPriceList`, «Дилерга кириш нарх», последняя по `tm` строка товара) — цена и
  остаток в одной единице учёта, вес в сумме не участвует. Скорость — вторичка (`Sales:SoldStatuses`, без «Завода» и «К К Мерч») за `Sales:StockVelocityDays` (90) дней в регионе склада;
  запас на 15 и 30 дней — скорость × горизонт; дефицит < 15 дней, затоварка > 30, «не продаётся» — остаток без продаж.
  Склад региона — склад с таким же названием; остальные склады — отдельным списком; завод — не в итоге страны, его дни запаса — по скорости всей страны.
- **Аутсток** (`/sales/outstock`) — дни без товара у дилера за месяц. Остаток по дням восстановлен назад от снимка `product_balances`:
  утро = вечер + продано (заказы `Sales:SoldStatuses` — delivered и given — по дате приёмки, без «Завода» и «К К Мерч») − привезено
  (перемещения «Завод → склад региона» в статусах `Sales:ShippedTransferStatuses` по дате выдачи — у первички дата доставки; минус возвраты заводу);
  приход дилеру — только принятый к моменту выгрузки остатков; заказ, принятый после выгрузки остатков, но до выгрузки заказов, назад не прибавляется —
  в снимке его ещё нет; приёмка позже выгрузки заказов — плановая дата (у «отдан» Linko ставит её вперёд), товар к снимку уже ушёл со склада:
  такой заказ прибавляется ко дню снимка. Отрицательный остаток не обнуляется по ходу (идёт назад как есть), показывается как 0 и считается
  днём в нуле; доля таких клеток — «точность».
  **Отклонение от «Полевого контроля»:** эталон восстанавливал сентябрь от остатков на 01.10, мы — от последней выгрузки остатков. Корректировки
  остатка дилера в Linko между этими датами (не заказы и не перемещения) сдвигают всю историю назад; там, где их нет, пары совпадают до кг
  (Шахрисабз: 1 948 кг, 446 дней в нуле — как в эталоне). Исторических остатков Linko не отдаёт, поэтому для закрытого месяца разница остаётся.
  Средние продажи в день и цена — по тем же заказам (у «отдан» в Linko есть приёмка): что продано, то и ушло со склада дилера.
  Считаются товары с продажами в периоде; в нуле — утром ≤ 0,5 кг. Упущено = дней в нуле × (продажи за период ÷ дней периода) × средняя цена
  (сумма ÷ кг); «к факту» — упущенные кг к проданным; доля дней в нуле товара — среди регионов, где он хотя бы день стоял в нуле. Ядро — пары, набирающие 80% потерь; хронический — в нуле ≥ половины периода;
  недовоз — на заводе в тот день товар был (остаток завода — назад по его перемещениям; выпуска цехов в Linko нет, доля завода — оценка снизу).
  Область: `scope=top|all|rest` (ТОП — коды `Sales:TopProducts`: 59 кодов списка ТОП «Полевого контроля»; без них — категории отчёта; по умолчанию top), `cat=Кекс,Помадка` — карточки
  категорий, `region` — регион с календарём по дням (что и когда стояло в нуле, когда довезли). Блоки: карточки категорий, итоги, выводы
  текстом, по регионам (дилер, «к факту», тройка самых дорогих дыр), дилеры × категории (сум/кг), по товарам, все пары с потерями. AI: `get_outstock`.
