# Резервные копии и восстановление (Disaster Recovery)

Полная копия OneBase — один зашифрованный набор: всё, чтобы поднять систему на чистом сервере в том же состоянии.
План и решения — [IMPLEMENTATION_PLAN_DISASTER_RECOVERY.md](../IMPLEMENTATION_PLAN_DISASTER_RECOVERY.md).

> Сейчас копии хранятся **только на сервере** (решение D1). Если сервер погибнет, вместе с ним пропадут и копии —
> периодически скачивайте свежий набор в другое место (раздел «Скачать копию»). Набор зашифрован, хранить его можно где угодно.

## Что в копии

| Часть | Что | Зачем |
|---|---|---|
| PostgreSQL | вся база `onebase` (`pg_dump -Fc` в одном снимке) и роли кластера | пользователи, роли, сессии, отделы, HR, продажи, снабжение, AI, задачи, журнал действий, ключи DataProtection и через них — все токены интеграций и сессия Telegram |
| Счётчики | число строк **каждой** таблицы в том же снимке, список миграций | после восстановления сверяется точно |
| MinIO | все объекты бакета с Content-Type и SHA-256 | файлы отделов, вложения, фото визитов, документы базы знаний |
| Qdrant | снимок каждой коллекции | векторы базы знаний — без повторных платных эмбеддингов |
| `.env` | файл сервера целиком | ключ JWT (сессии пользователей), токен туннеля Cloudflare, пароли сервисов |
| Compose | `docker-compose*.yml` из каталога проекта | в том числе локальный override, которого нет в git |
| Код | `git bundle` текущего коммита (+ патч, если на сервере правили файлы) | восстановление без GitHub |
| Сервер | `crontab`, версии ОС, Docker, Compose, образы с digest | то же окружение на новом сервере |

**Не входит:** Redis — там только кэш ответов консультанта, он наполнится сам; маршруты туннеля (Public hostname) — они в
панели Cloudflare и не зависят от сервера.

Набор — каталог `~/onebase-backups/onebase-backup-ГГГГ-ММ-ДД_ЧЧММ/`:

| Файл | |
|---|---|
| `payload.tar.age` | всё содержимое, зашифровано ключом восстановления |
| `payload.tar.age.sha256` | контрольная сумма — проверка целостности без ключа (`sha256sum -c`) |
| `manifest.public.json` | версии и размеры, без секретов и персональных данных |
| `onebase-restore.pyz` | программа восстановления той же версии |

## 1. Один раз: ключ восстановления

Копии шифруются программой [age](https://age-encryption.org). На сервере лежит только **открытый** ключ: сервер шифрует
копии, но открыть их не может, и взлом сервера копии не раскрывает. **Закрытый** ключ хранит администратор.

```bash
sudo apt install -y age
cd ~/onebase
bash deploy/onebase-backup.sh init-key
```

Команда создаёт пару ключей: закрытый — в `~/onebase-recovery-key.txt`, открытый — в `~/onebase-backups/recipients.txt`.
Дальше:

1. Скачайте закрытый ключ на свой компьютер (PowerShell): `scp ПОЛЬЗОВАТЕЛЬ@IP_СЕРВЕРА:~/onebase-recovery-key.txt .`
2. Сохраните его в менеджере паролей и ещё одну копию — на флешке или бумаге в сейфе.
3. Удалите с сервера: `shred -u ~/onebase-recovery-key.txt`

**Без закрытого ключа копию не открыть — так задумано.** Потеряли ключ — старые копии бесполезны: создайте новую пару
(`init-key`), старую строку из `recipients.txt` удалите, сразу снимите новую копию.

Можно шифровать сразу для двух администраторов: каждый делает свою пару, открытые ключи — по строке в `recipients.txt`.

## 2. Копия сейчас

```bash
cd ~/onebase
bash deploy/onebase-backup.sh backup --keep 14
```

Перед стартом проверяется место на диске (нужно примерно вдвое больше, чем база и файлы вместе); в конце — готовый набор.
Незавершённый набор называется `….partial` и при ошибке удаляется; открытые данные во временном каталоге удаляются всегда.
Без `--keep` старые наборы не удаляются никогда; с `--keep 14` остаются 14 последних — и только после успешной новой копии.
Старые `*.dump` от `deploy/backup.sh` не трогаются.

Журнал — `~/onebase-backups/backup.log`, итог последнего запуска — `~/onebase-backups/last-backup.json` (`success` / `failed`
и причина). Секретов в журнале нет: значения из `.env` маскируются.

## 3. Каждую ночь

`crontab -e` — строка вместо старой `deploy/backup.sh`:

```
0 3 * * * cd ~/onebase && bash deploy/onebase-backup.sh backup --keep 14 >> ~/onebase-backups/cron.log 2>&1
```

## 4. Проверить копию

```bash
bash deploy/onebase-backup.sh verify --backup ~/onebase-backups/onebase-backup-2026-11-07_0300
```

Без ключа проверяются состав набора, формат и SHA-256 зашифрованного файла — повреждённый или изменённый набор не пройдёт.
С `--key ФАЙЛ_КЛЮЧА` набор ещё и расшифровывается, и сверяется SHA-256 каждого файла внутри. Делайте это не на рабочем
сервере (ключ там храниться не должен), а при учебном восстановлении.

## 5. Скачать копию в другое место

Пока внешнего хранилища нет, это единственная защита от гибели сервера. Раз в неделю (PowerShell на своём компьютере):

```powershell
scp -r ПОЛЬЗОВАТЕЛЬ@IP_СЕРВЕРА:~/onebase-backups/onebase-backup-2026-11-07_0300 D:\OneBase-backups\
```

Проверка на компьютере без Python и ключа: `Get-FileHash payload.tar.age -Algorithm SHA256` — хеш должен совпасть с
началом строки в `payload.tar.age.sha256` (регистр букв не важен).

## 6. Восстановление

Программа восстановления на чистом сервере (`onebase-restore`) — этап 3 плана, в работе. До неё — только база:
`bash deploy/restore-db.sh ФАЙЛ.dump` ([deploy.md](deploy.md)).

## 7. Копия для проверки: режим изоляции

Восстановленная копия работает на настоящих данных: в базе та же сессия Telegram, push-подписки сотрудников, токены Linko,
Google и Verifix, ключи AI. Запущенная как обычно, она начала бы писать людям, разорвала бы рабочую сессию Telegram и
потратила бы деньги на AI. Поэтому копию для проверки запускают только в **режиме изоляции** — переменная API
`Recovery__Isolated=true` (программа восстановления ставит её сама в режиме проверки; вручную — в `docker-compose.override.yml`
в разделе `api: environment:`, не в `.env`). В этом режиме:

- не запускаются службы, которые пишут людям или ходят наружу: подключение Telegram, автоотчёты, рассылки и ответы
  AI-агента, синхронизации Linko, Google-таблиц и Verifix, push-уведомления, напоминания о сроках, AI по расписанию и план на
  день, фоновые задачи Sales Base, а также подбора персонала — очередь исходящих Telegram (ответы кандидатам, публикации,
  напоминания), отклики HH.uz и автоматика подбора; работают только внутренние — журнал ошибок, прогрев кэша продаж и удаление
  данных кандидатов по сроку хранения;
- любой внешний HTTP-запрос API отклоняется, даже запущенный кнопкой («Проверить подключение» к Linko ответит, что копия
  наружу не ходит);
- Telegram не подключается, платные вызовы моделей заблокированы;
- вверху каждой страницы — плашка «Копия для проверки: внешние интеграции выключены»;
- в журнале API при запуске — строка «Режим изоляции … не запущены: …».

Работают сайт, вход, данные, файлы, поиск по базе знаний (без новых вызовов моделей).

**Проверка копии изнутри приложения** — `GET /api/recovery/check` (администратор с правом «Журнал ошибок» или программа
восстановления с заголовком `X-Recovery-Token`, равным `Recovery__CheckToken` — не короче 32 символов; без этой переменной
вход по токену выключен). Ответ: видит ли приложение восстановленную базу (миграции, пользователи, роли, сессии,
подразделения, сотрудники, журнал аудита), есть ли ключи шифрования, **расшифровывается ли каждый вид сохранённого секрета**
(ключи AI, токены Linko, client_secret Verifix, api_hash, сессии и номера Telegram, ключи Google, пароли и ссылки папок
отделов, ключ VAPID) — только количество, без значений, — есть ли в хранилище объект для каждой ссылки на файл и читается ли
файл. Любая неудача попадает в `problems`, и тогда `ok: false`.
