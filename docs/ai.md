# AI в OneBase: консультант и AI-сотрудники

Пользователь задаёт вопрос в разделе «Консультант». Главный консультант решает, каких AI-сотрудников привлечь, сотрудники параллельно берут данные OneBase через инструменты, а консультант собирает их результаты в один ответ с фактами, анализом, рекомендациями и источниками.

```
Браузер → /bff (токен из httpOnly-cookie) → OneBase API
  POST /api/ai/chat (поток событий)
    └─ OrchestratedConsultantEngine
         ├─ AiRouter — быстрая модель выбирает сотрудников и задачи (запасной вариант — ключевые слова)
         ├─ AgentOrchestrator — сотрудники параллельно, каждый в своей области DI
         │    └─ AgentRunner — цикл инструментов → итог agent/status/findings/metrics/problems/recommendations/data_sources
         │         └─ ToolExecutor — грант агента, открытый источник, право пользователя, аудит
         │              └─ инструменты данных (только чтение) → SalesDataLoader, StockService, PrimaryService, KnowledgeService
         └─ итоговый ответ консультанта
  Все вызовы моделей — через AI Gateway (IAiGateway): провайдер, модель, ключ, повтор, резерв, учёт токенов.
```

Код — в `backend/src/OneBase.AI`; карта данных — в [ai-data-map.md](ai-data-map.md).

## Как включить

1. «Настройки → AI → Провайдеры»: вставить ключ Anthropic (и OpenAI — для эмбеддингов и голоса), «Проверить ключ», «Сохранить», «Обновить список моделей».
2. «Модели»: отметить модели, которые можно использовать, и при желании указать цены за 1 млн токенов — без цены стоимость не считается.
3. «Общие»: выбрать основную модель, резервную, быструю модель маршрутизации и модель эмбеддингов (только OpenAI; без неё база знаний ищет только по тексту). «Проверить модель» отправляет короткий запрос.
4. Право `ai.agents.run` — пользоваться консультантом; `ai.settings.manage` — настраивать AI. Роль Admin получает оба.

Запасной вариант без интерфейса — переменные окружения `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_MODEL`, `EMBEDDING_MODEL`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`. Сохранённое в OneBase важнее.

### Модели: весь AI — на Claude

- По умолчанию основная модель — `anthropic/claude-opus-5-5`, резервная — `claude-sonnet-5-5`; маршрутизация — основной моделью или `claude-haiku-5-5`.
  Миграция `SwitchAiToClaude` перевела на Claude сохранённые настройки: основную, резервную и маршрутизацию, модели AI-сотрудников и Telegram-агентов
  (не Claude → пусто, то есть основная; генерация — Claude из AI Data Manager), добавила три модели Claude в список «Модели» и подняла лимит ответа до 16 000.
  Прежние значения лежат в `ai."ClaudeSwitchBackup"`, откат миграции их возвращает. Без строки настроек и без `LLM_PROVIDER`/`LLM_MODEL` — тоже Claude Opus 5.5.
- Не Claude остаются только эмбеддинги базы знаний и голос (распознавание и озвучка): у Anthropic таких API нет, они идут через ключ OpenAI.
- Как с Claude работает AI Gateway (`AnthropicProvider`):
  - рассуждения (adaptive thinking) у Claude 5 включены всегда — «Глубина рассуждений» уходит как `output_config.effort`; лимит ответа включает рассуждения;
  - `temperature` моделям Claude 5 и Opus 4.7–4.8 не отправляется — они отвечают на неё 400;
  - ответ Claude возвращается в диалог как пришёл, с блоками рассуждений: между вызовами инструментов их нельзя убирать или пересобирать;
  - на последнем шаге AI-сотрудника инструменты остаются в запросе с `tool_choice: none` — набор инструментов посреди диалога не меняется;
  - отказ модели по правилам безопасности (`stop_reason: "refusal"`) — ошибка, и отвечает резервная модель.

## AI-сотрудники

| Код | Сотрудник | Кому доступен | Данные сейчас |
|---|---|---|---|
| director | Главный консультант | всем с `ai.agents.run` | результаты сотрудников, история чата |
| sales | Sales AI | `sales.read` | все источники; в фокусе вторичка, визиты, планы, команда |
| finance | Finance AI | `finance.read` | все источники; в фокусе оплаты, акт сверки, DSO, P&L, выручка |
| marketing | Marketing AI | всем | все источники; в фокусе товары, категории, акции (кампаний и лидов нет) |
| hr | HR AI | `hr.read` | все источники; в фокусе данные Verifix (сотрудники, посещаемость, опоздания, отсутствия, табели), команда продаж и задачи отделов (ФОТ, кандидатов, оценок нет) |
| production | Production AI | всем | все источники; в фокусе первичка и остатки (выпуска нет) |
| supply | Supply AI | всем | все источники; в фокусе остатки, первичка, поставщики (закупок нет) |

У каждого сотрудника в «Настройки → AI → Агенты» настраиваются:

- название, роль и инструкция (System Prompt);
- модель, температура и максимум токенов ответа;
- источники знаний и разрешённые инструменты (с подтверждением человеком или без);
- право, без которого сотрудник не привлекается;
- включение и выключение.

Новый сотрудник — ещё одна запись в `AgentDefaults` и его инструменты; оркестратор, чат и настройки его подхватят.

Инструменты Sales Base видят только область пользователя: агент — себя, супервайзер — свою команду, РМ — всё или свои филиалы.
Источники выдаются сотрудникам в `AgentDefaults` (при запуске `AiSeeder` дописывает недостающие, выключенное администратором заново
не включает): у каждого отдельского сотрудника — все источники, чтобы вопрос «не своего» отдела он отвечал по данным, а не «нет доступа».
Что увидит пользователь, решают его права: `ToolExecutor` проверяет их при каждом вызове инструмента.

Детализация до отдельных записей (`DrillTools.cs`):

Страницы целиком отдаются через `PageJson`: длинные списки — первые строки и число всех (`…Total`), дробные числа округлены.
Результат инструмента режется на 40 000 символов (`AgentRunner.MaxToolResultChars`). ТП ищется по имени кириллицей или узбекской латиницей
(«Jasur Xamidov» = «Жасур Хамидов»); несколько совпадений — ошибка со списком, модель уточняет. `get_sales` принимает и направление РМ
(`direction`). В системном промпте сотрудника — правило: не перечислять, каких данных «нет», пока не вызваны инструменты; разрез «по маршруту»
есть у `get_visits`, продажи за дни — у `get_sales_days`.

`find_products` ищет категорию, тип Linko или товар по части названия, бренду или артикулу — кириллицей или латиницей («помадка» находит и тип «Помадка», и товары «POMADKA») — и отдаёт продажи найденного: по категории — итоги и SKU, по товару — факт, точки и регионы.

Маршрутизатор и сотрудники с данными продаж получают в промпт словарь названий компании (категории отчёта с типами Linko, регионы, число SKU), поэтому «помадка» или «Хоразм» в вопросе — знакомые слова, а не повод ответить «данных нет».

Как работают инструменты:

- Все только читают данные и считают их теми же сервисами, что страницы OneBase.
- Изменение данных по отчётам — отдельный раздел AI Data Manager (`docs/ai-data-manager.md`): Claude готовит план, применяет его человек.
- Каждый инструмент возвращает компактный JSON и ссылки на страницы-источники.
- Месяц без данных или неизвестный регион — это ошибка для модели со списком допустимых значений, а не нули.
- Проверить любой инструмент можно в «Настройки → AI → Инструменты».

## Безопасность

- **Ключи.** Ключи API хранятся зашифрованными (ASP.NET Data Protection). В браузер, журнал и аудит они не попадают, в интерфейсе видны только последние 4 символа. Ошибки провайдера очищаются от ключей и похожих на них строк.
- **Где выполняются запросы.** Браузер обращается только к OneBase: запросы к OpenAI и Anthropic идут с сервера.
- **Права пользователя.** AI работает с правами того, кто задал вопрос:
  - сотрудник без нужного права не привлекается;
  - инструмент без права не выполняется;
  - документ базы знаний другого отдела не находится;
  - консультант прямо говорит, что доступа нет.
- **Приватность.** Чаты и память видит только их автор.
- **Качество ответов.** Модель не должна придумывать данные: цифры берутся только из инструментов. Если данных нет, ответ говорит об этом. Это проверяет код — см. «Ответы по данным».
- **Лимит частоты.** Не больше 20 вопросов в минуту на пользователя (HTTP 429).

## Ответы по данным

Политика «Strict Data-Grounded Response»: правдоподобный ответ без подтверждения данными — неправильный. Она записана в промпт консультанта,
AI-сотрудников и AI Data Manager (`ConsultantPrompts.GroundingPolicy`), а главные правила проверяет код (`OneBase.AI/Grounding`):

| Механизм | Как работает |
|---|---|
| Source of Truth | у каждого показателя владелец (`SourceOfTruth`): факт продаж, возвраты, визиты, остатки, перемещения, оплаты точек, планы ТП — Linko; поле OneBase — включённая привязка Google Sheets или OneBase; выполнение плана, P&L, акт сверки и DSO — расчёт. Та же карта — в «Источниках данных» (кто ведёт данные) |
| Data Retrieval | факты — только от AI-сотрудников с инструментами; вопрос о данных, к которому маршрутизатор никого не привлёк, получает сотрудников по словам вопроса (`OrchestratedConsultantEngine.Enforce`) |
| Evidence Check | каждое число ответа (кроме разделов «Рекомендации» и «Прогноз») сверяется с числами из результатов инструментов — с учётом округления («1,2 млрд» ↔ 1 234 567 890), долей и процентов, длин списков (`EvidenceCheck`). Неподтверждённое — одна попытка исправить ответ, дальше пометка «⚠️ Не подтверждено данными OneBase: …» в тексте. Так же — итог каждого AI-сотрудника (оставшиеся числа — `unverified`) |
| Calculation Validation | производные числа (разница, доля, рост, выполнение) сотрудник считает инструментом `calculate` — их результат тоже доказательство; консультант сводит подтверждённые показатели (суммы, разницы, доли считает код) |
| Conflict Detection | инструмент `get_source_of_truth`: владелец показателя, свежесть (`SourceOfTruthService.FreshnessAsync`: у группы Linko — самая старая удачная синхронизация её сущностей и ошибка последней попытки; у поля таблиц — последний запуск привязки, `not_bound` — таблица не привязана), открытые конфликты источников, а для значений из разных источников — какое верно (`SourceOfTruth.Resolve`: побеждает владелец; без владельца значение не выбирается) |
| Data Search | до ответа «нет данных» — не больше трёх попыток на показатель: синонимы и опечатки («помада», «могул») — через справочник (`find_products`, `get_store`, `get_agent`); все инструменты, где показатель бывает (план категории — `get_sales` → `CategoryPlans` и `find_products` → `Plan`, план ТП — `get_kpi`, первичка — `get_primary_shipments`, остатки — `get_stock_reload`); затем `get_source_of_truth` с freshness. Несколько совпадений — варианты и вопрос; уточнение в диалоге меняет только названное. Общий лимит — `AgentRunner.MaxSteps` (8) и 40 000 символов результата |
| Empty States | 0 ≠ «не найдено» ≠ «источник не загружался / с ошибкой / не привязан» ≠ «нет доступа» ≠ «данные устарели» (с датой). Отсутствие значения не превращается в ноль; не вернулся план — «План не удалось подтвердить: <источник> не вернул значение», а не «плана нет». Тест — `ConsultantDataTests` |
| Correction Guard | возражение («ты ошибся», «неправильно», «передумай», «xato») — не доказательство. Сотрудники заново получают данные с заданием перепроверить; код сверяет числа прошлого ответа и пользователя со свежими данными и выносит итог: подтверждено, исправлено, недостаточно данных (`CorrectionGuard`). Число пользователя в ответе — только с оговоркой «не подтверждается»; повтор возражения без новых данных факты не меняет |
| Audit Log | в `ai.AuditLogs`: исходный ответ (`CorrectionOfMessageId`), аргумент пользователя (вопрос), источники, проверка чисел и итог (`Grounding`, `CorrectionVerdict`) |

В чате под ответом — «чисел сверено с данными: N» или что не подтверждено; после возражения — «Перепроверка: …» и разбор в «Как получен ответ». Источники в тексте ответа и под ним не перечисляются — они в «Как получен ответ» → «Данные ответа» (раздел, период, ссылка).
Тесты — `GroundingTests` и `GroundingScenarioTests` (пять сценариев: оспорен верный ответ, оспорен неверный, данных нет, Google Sheets
против Linko, пользователь настаивает).

Ограничения: проверяются числа, а не слова — неверное название, причина или период без числа проверку не проходят через код (их держит промпт).
Совпадение с любым числом данных считается подтверждением — случайное совпадение возможно. Числа прописью не проверяются.

## База знаний

«Настройки → AI → База знаний»: загрузка `.txt`, `.md`, `.csv` (UTF-8 или cp1251), `.xlsx`, `.docx` до 20 МБ. PDF и старые форматы Office пока не читаются.

- **Хранение.** Оригинал хранится в MinIO, текст — фрагментами в `ai.KnowledgeChunks`.
- **Поиск.** Полнотекстовый (PostgreSQL, `russian`) работает всегда; семантический (Qdrant) — если выбрана модель эмбеддингов. Результаты объединяются.
- **Кто видит документ.** Нужно право `files.read`; дальше — отдел документа (пусто — вся компания) и его дополнительное право.

## Память

- **Аналитическая.** Результаты сотрудников в чате: уточнение «а сравни с августом» понимает, о каком анализе речь.
- **Память агента.** Недавние выводы сотрудника для этого пользователя в других чатах, с пометкой, что цифры могли устареть.

Чаты, убранные из истории, из памяти не читаются.

## Проактивный анализ

Раз в час (`Ai:Proactive:IntervalMinutes`, 0 — выключить) и кнопкой на AI Dashboard (`/ai`) правила проверяют данные без модели:

- падение продаж регионов к тем же дням прошлого месяца;
- план регионов и компании;
- первичка против плана;
- проблемные агенты;
- дефицит и неликвид на складах;
- возможности: перевыполнение плана и SKU, которых нет в регионе.

Повторная находка обновляется, а находка с исчезнувшим условием закрывается.

## Отчёты Excel (консультант)

Консультант формирует отчёт-файл **только когда пользователь сам просит**: в вопросе есть «отчёт», Excel / «эксель», xlsx,
«выгрузи», «скачать» или «hisobot» (`ReportIntent`). Это проверяет код до вызова модели: без такой просьбы инструмента
`create_report` у AI-сотрудников просто нет, а случайный вызов отклоняется. «Экспорт» — раздел продаж, отчёт по нему не включается.

- **Откуда цифры.** Сотрудник сначала получает данные инструментами, затем один раз вызывает `create_report`. Лист описывается
  ссылкой на данные: инструмент, его аргументы, `path` к массиву в JSON-результате и колонки (`field` → заголовок, формат).
  Backend сам вызывает этот инструмент через `ToolExecutor` с правами пользователя и раскладывает строки — модель цифры не
  перепечатывает. Для отчёта инструменты отдают списки целиком (`ToolContext.Report` → `ToolArgs.Cap`: без топ-10/25 для модели).
  Лист с `rows` вместо ссылки — только небольшая таблица, которую сотрудник посчитал сам (до 200 строк).
- **Ошибки описания** (нет такого `path` или поля, неизвестный формат) уходят модели со списком того, что есть, — она исправляет вызов.
- **Форматы:** text, integer, number, kg, money (сумы), percent (значение в процентах: 27.8 = 27,8 %), date. Без формата —
  по значениям и имени поля (`…Pct` — проценты, `…Kg` — кг, `revenue`/`sum` — сумы).
- **Лимиты:** до 10 листов, 40 колонок, 10 000 строк на лист, 300 000 ячеек, один отчёт на сотрудника за вопрос.
- **Хранение:** `ai.Reports` (миграция AiReports): автор, чат, сотрудник, название, листы в jsonb. Отчёт виден только автору.
  В ответе консультанта — `details.reports` (id, название, листов, строк).
- **В чате:** под ответом — карточка: «Скачать Excel», вкладки листов, предпросмотр первых 100 строк с итогом, пояснение и источники.
- **Файл:** собирается при скачивании (ClosedXML, `ReportWorkbookWriter`): название и дата формирования (Ташкент), источники,
  закреплённая шапка с автофильтром, форматы чисел, итоговая строка формулами СУММ (кроме процентов), проценты — числами с форматом %.
- **Журнал:** создание отчёта — `ai.report.created` в аудите; вызовы данных — как обычные вызовы инструментов.

## Голос (только консультант)

Работает только в чате консультанта:

- **Вопрос голосом.** Кнопка микрофона в поле ввода: нажали — говорите, нажали ■ — запись ушла на распознавание.
  - Текст вставляется в поле: его можно поправить и отправить.
  - Запись — до 2 минут, на сервере не сохраняется.
- **Озвучка ответа.** Кнопка «Озвучить» под каждым ответом.
  - Повторное нажатие («Остановить») прерывает чтение.
  - Таблицы читаются по строкам: «столбец: значение»; разметка, ссылки и код не читаются.
  - Источники не читаются: строки «Источник: …», список «Источники» и имена инструментов вроде `get_sales`.
  - Голос — мужской, «живой» (cedar), инструкции модели — разговорная подача, а не дикторская.
- **Голосовой режим** — переключатель «Голос» в шапке чата. Вопрос голосом отправляется сразу, а ответ читается вслух сам.
  Выбор запоминается в браузере.

Как устроено:

- Распознавание и озвучка — через OpenAI (`audio/transcriptions` и `audio/speech`). Ключ тот же, что у провайдера OpenAI:
  «Настройки → AI → Провайдеры» или `OPENAI_API_KEY`.
- Модели и голос — секция `Ai:Voice` в `appsettings.json`:
  - `TranscribeModel` (по умолчанию `gpt-4o-transcribe`);
  - `SpeechModel` (`gpt-4o-mini-tts`), `Voice` (`cedar` — мужской, самый естественный у OpenAI);
  - `FallbackVoice` (`ash`) — если OpenAI основной голос не принял (ответ 400 про voice): запасной берётся сам на 12 часов;
  - `Instructions` — как читать;
  - `TranscribePrompt` — термины продаж для точного распознавания.
- Ответ озвучивается частями. Первая часть короткая, поэтому звук начинается через пару секунд, а следующая загружается, пока играет текущая.
- Готовый звук хранится в памяти сервера 6 часов (ключ — текст части, голос и инструкции): повторное прослушивание не стоит денег.
- Озвучить можно только свой ответ из своего чата.
- Без ключа OpenAI работает голос самого браузера, если он есть: распознавание — в Chrome, Edge и Safari, чтение вслух — почти везде.
- На записи без речи модель иногда возвращает саму подсказку с терминами. Такой ответ отбрасывается: «Речь не распознана».
- Вызовы пишутся в `ai.Usage` с назначением `voice`. Лимит — 60 голосовых запросов в минуту на пользователя.
- Микрофон в браузере работает только по HTTPS или на localhost.

## Учёт и журнал

- **`ai.Usage`.** Каждый вызов модели: пользователь, агент, задача (`Purpose`), модель, токены, стоимость, время, ошибка. Токены — четырьмя счётчиками, как их тарифицирует провайдер: `InputTokens` — вход без кэша, `CacheReadTokens` — прочитано из кэша промпта, `CacheWriteTokens` — записано в кэш, `OutputTokens` — выход. У Anthropic `input_tokens` не включает кэш — он приходит в `cache_read_input_tokens` / `cache_creation_input_tokens`.
- **Стоимость** (`AiPricing`) — по четырём ценам модели из «Настройки → AI → Модели» (за 1 млн токенов: вход, выход, кэш-чтение, кэш-запись). Нет цены входа или выхода — стоимость `null` («нет цены»); нет цены кэша при кэш-токенах — тоже `null`, а не оценка по цене входа. Claude Haiku 5.5 при промпте длиннее 100 000 токенов (вход + кэш) считается по тарифу ×5 — как в прайсе Anthropic. Миграция `AiUsageCacheTokensAndPrices` проставила цены Claude Opus 5.5, Sonnet 5.5, Haiku 5.5 и Fable 5.1 по прайсу Anthropic от 25.10.2026 — только там, где цена не была задана; администратор может их менять.
- **`ai.AuditLogs`.** Каждый вопрос: сотрудники, модель, инструменты, источники, токены (вход — весь промпт, включая кэш), стоимость, время, начало ответа; проверка чисел ответа и итог перепроверки (`Grounding`, `CorrectionVerdict`, `CorrectionOfMessageId`).
- **Где смотреть.** «Настройки → AI → Использование» (сегодня / 7 / 30 / 90 дней: по дням, моделям, пользователям, отделам, AI-сотрудникам и задачам; доля промпта из кэша) и «Журнал».

## Кэш промпта (prompt caching)

- `AnthropicProvider` помечает системный промпт точкой кэша (`cache_control: ephemeral`, 5 минут; вместе с ним кэшируются инструменты — они идут первыми в префиксе) и включает автоматическое кэширование хвоста переписки (`cache_control` на уровне запроса). Каждый следующий шаг цикла инструментов читает предыдущие шаги из кэша; повторные вопросы в течение 5 минут читают системный промпт и инструменты сотрудника по цене кэш-чтения.
- Чтобы префикс не менялся, в системном промпте сотрудника нет даты и времени — они в первом сообщении пользователя (`AgentRunner.UserMessage`). Не добавляйте в системные промпты текущие значения (время, имя пользователя, счётчики) — это ломает кэш.
- `AiCallOptions.CachePrompt = false` — для промптов, уникальных в каждом запросе (Telegram-агент по материалам чата, разовый подбор колонок листа): запись в кэш стоит на четверть дороже входа и без повторов не окупается.
- Если модель или адрес (прокси) отвечает на `cache_control` ошибкой 400, шлюз повторяет запрос без кэша и запоминает это для модели (как с `temperature` и `effort`).
- Проверка: в «Использование» колонки «Кэш-чтение» / «Кэш-запись» — у работающего кэша чтение заметно больше записи; нули при включённом кэше означают, что префикс меняется между запросами.
- Итоговый ответ консультанта — два системных сообщения: неизменные правила (`ComposeRules`, кэшируются между вопросами) и данные этого вопроса (дата, результаты сотрудников, память, отчёты, ограничения доступа). Хвост переписки у него не кэшируется (`CacheConversation = false`): запись окупилась бы только при перепроверке ответа. Долю перепроверок видно в «По задачам» (`consultant.revise` к `consultant.answer`) — если она высокая, хвост стоит кэшировать.

## Кэш ответов консультанта

- Тот же **первый** вопрос чата от того же пользователя, пока данные не обновились, — ответ из кэша, без вызовов модели (`ConsultantAnswerCache`, хранение — `ISharedCache`: Redis, без Redis — память процесса). Время жизни — `Ai:AnswerCache:Minutes` (по умолчанию 30; 0 — выключено).
- Ключ: пользователь, его отдел и права, канал (веб или Telegram с его моделью и инструкциями), вопрос без различий в регистре, пробелах и знаках в конце, дата по Ташкенту, время изменения настроек AI и AI-сотрудников и **версия данных**: последняя успешная синхронизация Linko, последний запуск источников Google Sheets, версия кэша продаж (`SalesCacheSignal.Version` — меняется при правках данных, загрузках и в Data Manager; после перезапуска API — новая). Данные обновились — ключ другой.
- Кэшируется только ответ, который однозначно определяется вопросом и данными: были AI-сотрудники, все завершили работу, нет неподтверждённых чисел, отчёта Excel и перепроверки, и каждый инструмент с данными берёт их из источника, который обновляется синхронизацией (`sales.*`, `field.*`, `finance.*`, `supply.*`). Задачи отделов, Telegram и документы меняются без синхронизации — такие ответы не кэшируются. Продолжение разговора (есть история) и просьба об отчёте — всегда заново.
- В AI-журнале такой ответ отмечен `FromCache`, токены и стоимость — 0; в «Использование» — «из кэша ответов N».

## Бюджет и лимиты

- «Настройки → AI → Общие → Бюджет и лимиты»: дневной и месячный бюджет в USD (по Ташкенту; пусто — без ограничения), порог предупреждения (% бюджета, по умолчанию 80) и число одновременных вызовов моделей (по умолчанию 8, 0 — без ограничения).
- Траты — сумма `ai.Usage.CostUsd` (вызовы моделей без цены не считаются). Бюджет исчерпан — AI Gateway и AI Data Manager не начинают новые вызовы, пользователь видит причину; при пороге и при исчерпании администраторам AI (`ai.settings.manage`) приходит уведомление (колокольчик), не чаще раза в день на событие. В «Использование» — полоса бюджета.
- Сверх лимита одновременных вызовов запросы ждут очереди (а не получают 429 от провайдера); лимит общий для консультанта, AI-сотрудников, Telegram-агента и Data Manager.

## Модели по задачам (простые задачи на Haiku)

- **Что можно перевести на отдельную модель** — две категории простых задач (`AiTaskRouting` — единственное место выбора модели):
  - «Маршрутизация» — выбор AI-сотрудников и задач им по вопросу (классификация по отделам). Модель — существующий слот «Модель маршрутизации».
  - «Извлечение JSON» — подбор колонок Google Sheets к полям OneBase (`SheetMappingAdvisor`). Модель — слот «Модель извлечения JSON».
- **Что всегда идёт основной моделью** (Opus 5.5): цикл AI-сотрудника с инструментами и проверкой чисел, итоговый ответ консультанта и его
  перепроверка, AI Data Manager. Telegram-агент — своей моделью из настроек аккаунта (это уже отдельная настройка, не дублируется).
- **Настройки** («Настройки → AI → Общие → Простые задачи — отдельная модель»): общий флаг «Отдельные модели для простых задач» и для каждой
  категории модель и режим:
  - «Выкл» — основная модель (как раньше);
  - «Сравнение» — пользователь получает результат основной модели, модель категории решает ту же задачу в фоне; итоги — в `ai.ModelComparisons`
    (`source = shadow`), вызовы — в «Использование» с задачей `….shadow` без пользователя (не входят в стоимость его вопроса). Фон не
    запускается, если траты дошли до порога предупреждения бюджета;
  - «Включено» — модель категории; при сбое провайдера — сразу исходная модель (без повтора дешёвой: запрос, оборвавшийся по времени,
    провайдер мог уже посчитать); при некорректном результате (не JSON, нет списка `agents` / `suggestions`, только несуществующие
    сотрудники) — один повтор исходной моделью (`….fallback`); бюджет исчерпан — маршрутизация по ключевым словам, без ещё одного списания.

  Вернуть прежнее — режим «Выкл» или общий флаг; действует сразу (настройки перечитываются после сохранения).
- **Миграция `AiTaskModelRouting`** сохраняет поведение: где «Модель маршрутизации» уже была выбрана, флаг включён и режим «Включено»; где нет —
  флаг выключен, режимы «Выкл».
- **Проверка на эталонном наборе** («Настройки → AI → Модели по задачам → Запустить проверку», `POST /api/ai/routing/evaluate`): 24 обезличенные
  задачи маршрутизации (`RouteEvalCases`: продажи, поле, финансы, склад, производство, маркетинг, HR, приветствия, уточнение по истории) с
  ожидаемыми сотрудниками. Каждая — основной моделью и моделью маршрутизации, одинаковые сообщения, без резервной модели и повторов. Итог:
  верно / JSON корректен / ошибки / токены (вход, кэш, выход) / стоимость / время по каждой модели и совпадение выборов; строки — в
  `ai.ModelComparisons` (`source = eval`), вызовы — в «Использование» (`eval.route`). Это реальные вызовы API.
- **Как включать**: «Сравнение» для маршрутизации → проверка на эталонном наборе и несколько дней задач пользователей → «Включено», только если
  модель категории не хуже основной (верно, JSON, расхождения разобраны в «Последние сравнения»). Затем — по той же схеме «Извлечение JSON».

## Чего пока нет

- Данных финансов (расходы, бюджеты, прибыль), маркетинга, HR, производства и закупок. Сотрудники этих отделов честно отвечают, что данных нет.
- Потокового вывода текста ответа: ответ приходит целиком, но прогресс работы сотрудников идёт потоком.
- Чтения PDF и Google Sheets.
