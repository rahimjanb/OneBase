# Универсальный аналитический движок (срезы)

Смысловой слой над движком запросов «Аналитика». Вопрос «выручка по каждой товарной группе за каждый день» превращается в запрос
«показатели × измерения × шаг × период × фильтры». Готовый отчёт под такой вопрос не нужен. Где проходили аудит и какой был план —
`ONEBASE_ANALYTICS_ENGINE_PLAN.md`, итог работ — `ONEBASE_ANALYTICS_ENGINE_REPORT.md`.

## Зачем

До движка AI отвечал «данных нет», когда нужного среза не было ни в одном инструменте:
- `get_sales_period` даёт дни, но без товаров;
- `get_sku_sales` даёт товары, но только помесячно.

При этом в базе есть каждая строка заказа с датой, филиалом, агентом, точкой и товаром. Движок считает любой совместимый срез из этих
строк по правилам «Продаж».

## Устройство

```
AI (analytics_query, analytics_capabilities) ─┐
Экран «Аналитик → Срезы» (/analytik/explore) ─┴─ SemanticEngine
   QueryPlanner     — проверка запроса, права показателей, совместимость измерений, шаг, период, сравнение
   SemanticResolver — названия → id («Самарканд», «Кекс», имя агента; нет совпадений — ошибка с вариантами)
   SemanticSql      — SQL фактов из белого списка (значения — параметры) → IAnalytikSql (READ ONLY, таймаут, EXPLAIN)
   SemanticPlans    — планы (месяц «Продаж» по регионам, планы регионов по категориям, планы ТП Linko)
   калькулятор      — доля, средний чек, цена кг, выполнение и прогноз плана, дни запаса, сравнение периодов
   проверка         — период и данные по, шаг, сопоставление регионов и групп, валюта, итоги, загрузки, область, обрезка
   журнал           — analytik.Queries (Origin = «…:semantic»: запрос, SQL, параметры, область, строки, статус)
CapabilityRegistry  — реестр: факты, показатели, измерения, шаги, диапазоны данных, загрузки, другие инструменты, чего нет в источниках
```

Код:
- `OneBase.Application/Analytik/Semantic` — модель, реестр, контекст, SQL, планы, движок, реестр возможностей;
- `OneBase.AI/Analytik/SemanticTools.cs` — инструменты;
- `OneBase.Api/Controllers/AnalytikExploreController.cs` — API;
- фронтенд: `frontend/src/app/(app)/analytik/explore`, `components/analytik/explore`, `lib/explore.ts`.

Справочники движка те же, что у страниц «Продаж»:
- `SalesStructure` — регионы по филиалам, старые филиалы, регионы-каналы;
- `SalesCategories` — категории отчёта по дереву типов Linko.

Справочники кэшируются на 5 минут и сбрасываются с синхронизацией Linko и правкой «Настроек продаж» (`SalesCacheSignal`).

## Запрос

```json
{ "metrics": ["revenue", "kg"], "dimensions": ["date", "product_group", "region"], "grain": "day",
  "dateFrom": "2026-08-01", "dateTo": "2026-11-11", "filters": [{ "dimension": "region", "op": "in", "values": ["Самарканд"] }],
  "compare": "previous", "sort": [{ "by": "revenue__pct", "dir": "asc" }], "limit": 500, "offset": 0,
  "segment": "secondary", "planSource": "auto", "planKind": "rop", "coverDays": 14, "fillZeros": false, "tenant": "onebase" }
```

Ограничения запроса:
- **Объём:** до 12 показателей и до 5 измерений; период — до 732 дней.
- **Группы:** до 60 000 до разбиения на страницы. Больше — отказ с советом сузить запрос.
- **Сравнение:**
  - `previous` — предыдущий такой же отрезок; для целых месяцев — предыдущие месяцы;
  - `year_ago`;
  - `custom`.
- **Колонки сравнения:** `{metric}__prev`, `__delta`, `__pct`; по ним можно сортировать.

## Показатели

| Факт | Показатели |
|---|---|
| Продажи (`sales`) | `revenue`, `gross_revenue`, `returns_revenue`, `discount`, `kg`, `gross_kg`, `returns_kg`, `units`, `orders`, `outlets` (АКБ), `avg_check`, `avg_price_kg`, `revenue_share`, `other_currency_revenue` |
| План (`plan`) | `plan_kg`, `plan_revenue`, `plan_fact_kg`, `plan_execution`, `plan_deviation_kg`, `forecast_kg`, `forecast_execution` |
| Оплаты (`payments`) | `payments` (право `finance.read`) |
| Остатки (`stock`) | `stock_units`, `cover_days`, `need_units` |

У каждого показателя в реестре (`SemanticCatalog`) записаны:
- формула и источник;
- единица измерения;
- право доступа;
- ограничения.

Реестр отдаёт `analytics_capabilities` и `GET /api/analytik/explore/capabilities`. Выручка, отгрузка (первичка) и оплаты — разные показатели и
не смешиваются.

## Измерения

**Время.** `date`, шаг day / week / month / quarter / year.

**Оргструктура:**
- `region`;
- `branch` — филиал Linko;
- `direction` — направление: РМ или канал;
- `manager` — РМ направления;
- `supervisor` — СВР региона;
- `dealer` — дилер региона;
- `sales_channel` — регионы, каналы (базар, сети) или «Завод».

**Торговля:** `agent`, `market` (точка или клиент), `market_type`.

**Товары:**
- `product`, `sku`;
- `product_group` — категория отчёта «Продаж»;
- `product_type` — тип Linko;
- `stock`.

**Прочее:** `source`.

Можно задать любое сочетание, если все показатели запроса раскладываются по этим измерениям. Например, план — только по месяцам,
регионам, группам и агентам; остатки — без дат и регионов.

## Правила фактов

**Продажи — как `SecondarySales` / `SalesHistoryReader`.**
- **Заказы.** Статусы `Sales:SoldStatuses` (delivered, given) по дате реализации — по умолчанию дата приёмки, по Ташкенту. Сумма и вес берутся
  из строк заказа; заказ не в сумах даёт выручку 0, вес учитывается.
- **Возвраты.** Строки со статусом `Sales:ReturnStatuses` (delivered) с минусом, по дате создания возврата.
- **Филиалы.**
  - «К К Мерч» не входит никуда;
  - «Завод» — экспорт и опт, сегмент `factory`;
  - точки-каналы («Урикзор», «Сети») в закрытых месяцах относятся к своему региону-каналу.
- **Регион** — по филиалу заказа, как «Продажи по регионам» и «Продажи по SKU»; старые филиалы считаются в текущем регионе. «Продажи за
  период» относят продажи агента к его основному региону, поэтому суммы регионов там могут отличаться. Об этом есть заметка в результате.
- **АКБ** — точки, у которых чистый вес в группе за период больше нуля. Точки-каналы не входят. АКБ считается двумя уровнями, как в «Продажах».

**План.**
- **Срез по регионам или без измерений.** План и «факт для плана» каждого региона за месяц берутся из месяца «Продаж»
  (`SalesAnalytics.RegionPlanFacts`):
  - если есть планы регионов (Google Sheets / AI Data Manager), используются они; для плана «Завод» — с раскладкой по РОП;
  - иначе берётся сумма планов ТП Linko по региону ТП.
- **Выполнение** — «факт для плана» ÷ план, как на странице.
- **Срез по товарным группам** — категории планов регионов.
- **Срез по агентам** — планы ТП Linko: «Тотал» или сумма показателей, без командных планов СВР.
- **Шаг меньше месяца** — отказ: план по дням не делится и не распределяется.

**Оплаты.** Принятые оплаты без удалённых, по дате создания. Регион — по филиалу точки.

**Остатки.**
- Берётся текущий снимок `linko.ProductBalances` в единицах товара.
- **Дни запаса** = остаток ÷ средние продажи в день за 30 дней.
- **Потребность** = max(0, продажи в день × дни запаса − остаток).
- Истории остатков нет. Сравнение и даты для остатков запрещены.

## Проверка полноты

Результат содержит признак `complete` и проверки `checks`. Ответ AI начинается с того, чего не хватает.

| Проверка | Когда не пройдена |
|---|---|
| `sales.period` / `payments.period` | Данных нет за часть периода. Указан последний день данных — это не нулевые продажи |
| `sales.start` | Период начинается раньше, чем загружена история |
| `region_mapping` | Есть строки «Без региона»: филиал не найден в регионах OneBase. Указаны сумма и доля |
| `group_mapping` | У товара нет типа Linko («Без группы») |
| `totals` | Сумма строк не равна итогу периода |
| `sync` | Последняя загрузка заказов Linko завершилась ошибкой |
| `plan` | Нет плана за часть месяцев |

Остальные проверки информационные:
- `grain` — каждая строка дневная, без средних;
- `keys` — уникальность по id Linko, статусы;
- `scope` — область пользователя;
- `limit` — показана часть строк.

Заметки (`notes`) рассказывают:
- как сопоставлены названия в фильтрах;
- что заказы не в сумах в выручку не входят;
- как привязан регион;
- что план сравнивается за неполный месяц.

## Источники и история загрузок

`sources` у каждого результата:
- система и таблицы;
- когда Linko загружал данные (`linko.SyncState`);
- последний день данных;
- правила отбора.

Новая таблица `sales.LinkoSyncRuns` — история каждой синхронизации Linko:
- режим, начало и конец, итог (ok, failed, cancelled);
- строки и ошибки по шагам;
- самая ранняя изменённая дата документов.

Пишет её `LinkoSyncCoordinator`. Хранится 90 дней. «Очистить и загрузить заново» её не стирает, поэтому она в схеме `sales`, а не `linko`.
Последние запуски видны в реестре возможностей и на экране «Срезы».

Миграция `Analytik4_LinkoSyncRuns` создаёт таблицу. Ранняя сборка разработки успела создать её как `linko."SyncRuns"` — такую таблицу
миграция переносит вместе со строками.

## Права и безопасность

- **Права на показатели:** продажи и остатки — `sales.read`, оплаты — `finance.read`. Нет права — ответ `denied`.
- **Область продаж** (`AnalytikAccess`) накладывается условием в SQL:
  - РМ и СВР видят филиалы своих регионов вместе со старыми;
  - агент видит только свой `AgentId`.
- **Остатки** доступны только при доступе ко всей организации.
- **SQL** собирается только из белого списка измерений и показателей. Значения передаются параметрами, модель SQL не пишет. Защита от
  подстановки проверена тестом.
- **Tenant.** База однопользовательская. Запрос с чужим `tenant` отклоняется, `tenant` пишется в журнал.
- **У консультанта** пользователь с неполной областью, как и раньше, не получает данных продаж (`LimitSalesAsync`). Срезы с учётом
  области доступны в «Аналитике».

## Производительность

Замеры на копии рабочей базы: 1,2 млн строк заказов, 01.08–11.11.2026. Отдельных таблиц фактов и материализованных представлений нет:
`linko.*` — уже нормализованная копия источника.

| Срез | Время |
|---|---|
| Месяц по регионам (выручка, кг, АКБ) | 0,6 с |
| День × товарная группа, 103 дня | 0,9 с |
| Регион × товарная группа | 0,8 с |
| День × регион × группа, 10 060 строк | 1,0 с |
| То же с заказами, АКБ и средним чеком | 1,4 с |
| Агент × группа, 12 месяцев | 2,9 с |

Запросы ограничены:
- `EXPLAIN` до выполнения;
- `statement_timeout` (`Analytik:QueryTimeoutSeconds`);
- не больше 4 запросов разом;
- 60 000 групп.

Модели уходят до 200 строк, а также итоги и проверки. Полный список выдаётся через `create_report` (`all_rows`) или по ссылке.

## AI

**`analytics_query`.** Источник `sales.slices`, он есть у консультанта и у аналитиков продаж, производства, склада, финансов и BI.
- Аргументы:
  - `metrics`, `dimensions`, `grain`;
  - `date_from` / `date_to` или `period` (`last_30_days`, `last_3_months` и т.п.);
  - `filters` с названиями;
  - `compare`, `sort`, `limit`, `offset`;
  - `segment`, `plan_source`, `plan_kind`, `cover_days`, `fill_zeros`.
- Ответ:
  - строки объектами (подходят для `create_report`);
  - итоги и сравнение;
  - `complete`, `checks`, `notes`, `sources`;
  - ссылка `link` на экран «Срезы».

**`analytics_capabilities`.** Реестр: что есть, за какие даты, какие инструменты отдают остальное и чего нет в источниках.

**Правила промптов** (`AgentRunner`, общий промпт аналитиков):
- разрез, которого нет в готовых инструментах, считается одним вызовом `analytics_query`;
- дни — фактические, месячные итоги по дням не делятся;
- ответить «данных нет» можно только после `analytics_capabilities`.

## Экран «Аналитик → Срезы»

**Конструктор:**
- показатели по фактам с формулой в подсказке;
- измерения по порядку группировки;
- шаг, период, сравнение, сегмент продаж;
- дни без продаж нулём;
- фильтры по названиям.

**Готовые срезы:**
- выручка по группам по дням;
- регион × группа;
- план и факт по регионам;
- группы к прошлому периоду;
- топ-10 товаров;
- остатки и дни запаса.

**Результат:**
- полнота и непройденные проверки;
- источники со временем загрузки;
- итоги с изменением;
- график: линии по датам с сериями второго измерения или столбцы;
- таблица:
  - сортировка на сервере;
  - поиск по строкам;
  - группировка по первому измерению с подытогами;
  - переход вглубь щелчком по значению: регион → агенты, группа → товары, агент → точки, месяц → дни;
  - итог периода;
- CSV и Excel (`POST /api/analytik/explore/export`, лист «Проверка и источники»);
- реестр «Какие данные есть» с последними загрузками Linko.

Запрос хранится в адресе (`?q=`), поэтому срезом можно поделиться. Ссылка из ответа AI открывает этот же срез.

## API

| Метод | Что делает |
|---|---|
| `GET /api/analytik/explore/capabilities` | Реестр возможностей с учётом прав |
| `POST /api/analytik/explore/query` | Срез (`AnalyticsQuery`) |
| `POST /api/analytik/explore/export` | Срез в Excel, до 50 000 строк |

Для API нужно право `analytik.use`. Ошибки: `denied` → 403; `invalid`, `unsupported`, `too_heavy`, `timeout` → 400 с кодом.

## Чего нет в источниках

То же записано в реестре и показывается пользователю и AI.

- **1С не подключена.** Факты продаж из Excel и CSV не загружаются: единственный источник фактов — Linko.
- **История остатков не загружается** (`balances_by_date` Linko), остатки — только текущий снимок.
- **Удаление заказа в Linko не передаётся.** Признака удаления Linko не отдаёт; отмена (статус) учитывается.
- **Планы регионов — только в кг.** Денежный план есть только у ТП.
- **Нет связи строки заказа с акцией Linko.**
- **Территории Linko не связаны с точками** — измерения «территория» нет.
- **Себестоимости продукции нет** — маржинальности по продажам нет.
