# AI Data Manager

«AI Data Manager» (`/data-manager`: пункт в меню слева и карточка в «Настройках») — чат администратора с Claude. Администратор прикладывает отчёт (Excel `.xlsx`, CSV) и пишет, что сделать.
Claude читает файл и данные OneBase через инструменты и готовит **план изменений**: «было → стало», конфликты, предупреждения, влияние на KPI.
Данные меняются только после кнопки «Подтвердить». Затем OneBase сам пересчитывает показатели и проверяет результат. Любой применённый план можно откатить.

## Чьи это данные (аудит)

| Данные | Где хранятся | Кто владелец | Что может AI Data Manager |
|---|---|---|---|
| Заказы, возвраты, визиты, остатки, перемещения, оплаты, товары, точки, сотрудники | `linko.*` — копия Linko | **Linko**. Синхронизация (в 11:00 и 17:00 по Ташкенту и кнопкой «Обновить») перезаписывает строки (`LinkoSyncService.UpsertAsync`); Full/Reset перечитывают всё | **Только читать и сверять** (`compare_report_fact`). Отчёты считаются прямо из `linko.*`, поэтому локальная правка исчезла бы при следующей синхронизации. Механизма корректировок поверх Linko в OneBase нет — это сознательное ограничение (см. ниже) |
| Планы ТП (`staff_balance`) | `sales."StaffPlans"` | **Linko** (месяц удаляется и пишется заново при пересчёте в Linko) | Только читать |
| Планы регионов: РОП, «Завод», первичка | `sales."RegionPlans"` | **OneBase** (в Linko их нет) | Создать, изменить, удалить — через план изменений |
| Цели KPI (конверсия, выручка на ТТ, АКБ на агента, категорий на ТТ) | `sales."Targets"` | **OneBase** | Изменить через план изменений |
| Дилер и СВР региона | `sales."Regions"` (`DealerName`, `SupervisorName`) | **OneBase**. Название региона синхронизация берёт из Linko, его не меняем | Изменить через план изменений |
| Направления (РМ, каналы) | `sales."Directions"` | OneBase | Не меняется (редко, есть «Настройки продаж») |
| Факт, план, выполнение, прогноз, АКБ, страйк | не хранятся — считаются (`SalesDataLoader` → `SalesAnalytics`, кэш 30 мин) | OneBase | После применения кэш сбрасывается (`SalesCacheSignal.Invalidate`), показатели пересчитываются |
| P&L дилеров: продажи, себестоимость, расходы по группам, доставка (исходные строки) | `sales."PnlValues"` | **OneBase** (в Linko этого нет; загружается только здесь) | Создать, изменить, удалить — через план изменений. Валовую прибыль, маржу, ROS, EBIT, EAT не хранит — их считает `PnlMath`, расчётные строки отчёта только сверяются |
| Премии, бюджеты, P&L компании в целом | **нет в OneBase** | — | Модель так и отвечает; пересчитывать нечего |

Сам Linko AI Data Manager не меняет: POST-операции Linko не реализованы и не вызываются (см. `docs/sales-linko.md`).

**Почему нет корректировок поверх Linko.** Расчёты читают `linko.*` двумя путями: в памяти (`SecondarySales`) и SQL-агрегатами (`SalesHistoryReader`). Наложение корректировок пришлось бы встроить в оба пути и во все отчёты (вторичка, SKU, аутсток, первичка), а иначе разделы разойдутся между собой. Поэтому отчёт, который расходится с Linko, сверяется. Администратор видит расхождения по регионам и исправляет источник, то есть Linko.

## Как работает

```
Браузер → /bff → POST /api/data-manager/chat (SSE)
  DataManagerChatService ── ход модели ──► ClaudeDataManagerModel (официальный SDK Anthropic, Messages API, tool use)
        │                                   claude-opus-5-5, адаптивные рассуждения, effort high, кэш подсказки,
        │                                   серверная резервная модель при отказе (fallbacks: "default")
        └── tool_use ──► DataManagerTools (права пользователя из базы, проверка аргументов, аудит)
               чтение: list_data_targets, list_regions, list_categories, list_files, read_report, get_region_plans,
                       get_sales_kpis, compare_report_fact, get_targets, get_pnl, compare_pnl_primary, get_change_set,
                       list_change_sets, verify_change_set
               Google Sheets: list_google_sheets, load_google_sheet (лист → файл чата), sync_google_sheet_binding
               план:   prepare_region_plan_update, prepare_targets_update, prepare_region_profile_update, prepare_pnl_update,
                       cancel_change_set
                       → DataChangeService: план изменений (ai.DataChangeSets/Items), ничего не пишет в данные
Кнопка «Подтвердить» → POST /api/data-manager/change-sets/{id}/apply (SSE)
  IDataChangeApplier (Serializable-транзакция) → sales.RegionPlans / sales.Targets / sales.Regions / sales.PnlValues
  → сброс кэша отчётов → VerifyAsync (перечитать значения, пересчитать KPI) → событие в чат → итог модели
```

- **Значения из файла читает OneBase, а не модель.** Модель передаёт только сопоставление (лист, строка заголовка, столбцы региона и категорий, период, единицы). Числа берёт `ReportExtraction`. Перепутать или придумать число модель не может. `rows` — только для значений, которые администратор написал в сообщении.
- **У модели нет инструмента применения.** Применяет только человек кнопкой; сервер перепроверяет право `ai.data.manage` по базе.
- **Google Sheets** («Настройки → Источники данных», [data-sources.md](data-sources.md)). Администратор пишет «возьми план первички из
  таблицы «…»» — модель находит таблицу (`list_google_sheets`: листы, привязки, какие поля они ведут, период, последняя синхронизация):
  - поле, которое уже ведёт привязка (например, план первички), обновляется **только её синхронизацией** —
    `sync_google_sheet_binding`, как кнопка «Синхронизировать сейчас»: данные пишутся сразу по сопоставлению, которое человек
    подтвердил при настройке привязки, с проверкой, журналом операций и откатом (в журнале синхронизаций — «из чата AI Data Manager»).
    Подготовить для такого поля план из чата нельзя — владелец поля один;
  - таблица или поле без привязки — `load_google_sheet`: лист читается сейчас и становится файлом чата (CSV), дальше как с
    отчётом — `read_report`, `prepare_*` по `fileId`, «Подтвердить» нажимает администратор.
- **Только нужный период.** `prepare_region_plan_update` и `prepare_pnl_update` принимают `fromMonth`/`toMonth` («2026-01»):
  строки других месяцев не берутся (лист с историей за годы не упирается в предел 24 месяцев за раз).
- Переписка с моделью хранится в `ai.DataConversations.Transcript` и только дописывается: рассуждения с подписью, вызовы инструментов, результаты. Она сохраняется после каждого шага, поэтому сбой посреди хода не повторяет инструменты. Если ход прервался, переписка закрывается текстом об ошибке, и следующее сообщение продолжает её.
- Ошибки Claude API: 408/409/429/5xx и обрывы SDK повторяет сам (3 раза). После этого OneBase делает ещё одну попытку через `RetryDelaySeconds`. Тексты ошибок — по-русски, без ключа и тела ответа. Ход ограничен 24 запросами к модели и 10 минутами.
- Один ход за раз в чате: блокировка `BusySince` с версией строки.

## План изменений

- **Бизнес-ключ строки**:
  - план — регион × вид × год × месяц × категория (или итог без разбивки);
  - цель — ключ;
  - профиль — регион × поле.
- **Сопоставление**:
  - регион — по названию, дилеру или id филиала Linko; «(эски)» — текущий регион; «Азизбек Хоразм» — Хоразм, если регион в названии один;
    для плана первички и дилера региона в списке есть и старые филиалы из `Sales:PrimaryStockRegions` («Андижон (эски) 2» — склад прежнего
    дилера): точное название или дилер берётся первым, поэтому «Андижон (эски) 2» и «Икбол Андижон» — старый филиал, а не текущий регион;
  - категория — по названию и словам из `Sales:PlanIndicatorCategories` (МОГУЛЬ → Помадка, Снек → Придзел); план хранится под первым типом категории;
  - неоднозначное и ненайденное — **конфликт**, а не догадка. «Завод», «К К Мерч» и регионы-каналы не регионы вторички.
- **Действия**:
  - Create, Update, Delete — 0 в отчёте удаляет строку плана;
  - Unchanged;
  - Conflict — не применяется: дубликат с разными значениями, не число, отрицательный план, неверный период.
- **Режимы**:
  - `upsert` (по умолчанию) — только строки отчёта;
  - `replace` — строки месяца, которых нет в отчёте, удаляются. Модель обязана сначала спросить, полный ли отчёт; без `completePeriod = true` инструмент откажет.
- **Предупреждения**:
  - месяц перейдёт с планов ТП Linko на планы регионов — если на месяц есть хоть одна строка вида, весь месяц считается по планам регионов;
  - какие регионы останутся без плана;
  - у региона одновременно итог и категории — в расчёте берётся итог (`SalesMath.PlanTotal`).
- **Влияние на KPI** — по формулам OneBase: «до» берётся из расчёта, «после» оценивается как факт ÷ новый план; республика тоже.
- **Повторы**:
  - файл узнаётся по SHA-256 (`ai.DataFiles.Sha256`): в чате видно «уже загружался и применялся»;
  - тот же запрос — те же значения, поэтому план из одних Unchanged, применять нечего;
  - повторная подготовка в том же чате возвращает прежний черновик;
  - исправленная версия отчёта показывает только изменённые строки и ссылку на прежнюю операцию (`previous.correctedRows`).

## P&L дилеров

Раздел «Продажи → P&L дилеров» (`/sales/pnl`, права `sales.read` и `finance.read`) повторяет вкладку «P&L дилеров» Полевого контроля:
прибыль завода на дилере за месяц, сум. Демонстрационных данных нет: пока ничего не загружено, раздел пуст и ведёт в AI Data Manager.

- **Хранится** только исходное: `sales."PnlValues"` — год × месяц × контрагент × строка → сумма. Ключ контрагента — имя без регистра,
  кавычек и лишних пробелов (`PnlMath.DealerKey`). Исходные строки: `sales` (продажи), `cost` (себестоимость), `sm` (отдел продаж и маркетинга),
  `retro` (ретробонусы), `ship_plant` / `ship_dealer` (доставка: завод / дилер оплатил, журнал логистики), `ship_606` (компенсация по ст. 606),
  `admin`, `other`, `amort`, `bank`, `tax`, `div`.
- **Считает** `PnlMath` (Application/Sales/Pnl) — и страница, и AI Data Manager, и проверка после применения:
  - Валовая = Продажи − Себестоимость; Маржа = Валовая ÷ Продажи;
  - Прибыль после продаж = Валовая − Отдел продаж и маркетинга + Ретробонусы; ROS = Прибыль после продаж ÷ Продажи;
  - Доставка и склад = завод + дилер оплатил; если рейсов дилера за месяц нет — компенсация по ст. 606;
  - EBIT = Прибыль после продаж − Доставка − Административные − Прочие − Амортизация;
  - EAT = EBIT − Банковские − Налоги — только если за месяц загружены банковские услуги или налоги; реинвестированная = EAT − Дивиденды —
    если загружены дивиденды; ROA — «—» (активов в OneBase нет);
  - итоги (РМ, месяц, год дилера) — суммы денежных строк, маржа и ROS — от сумм.
- **Отличия от Полевого контроля** (там это ошибки, см. аудит): строка «Прочие расходы» показывается и входит в EBIT; доставка по ст. 606
  берётся по дилеру, а не по месяцу (у дилера без рейсов 606 не выпадает из EBIT); возвраты в базе продаж вычитаются и из продаж, и из
  себестоимости (`returnColumn` → сумма со знаком минус); месяц по умолчанию — последний, где есть и продажи, и расходы.
- **Статьи реестра «Прочие расходы»** (`PnlMath.Articles`): 601–604, 607–610 → `sm`; 606 → `ship_606`; 611, 331, 334, 339 → `admin`;
  остальные коды → `other`. Модель может уточнить строку статьи (`lineMap`), но только на существующую строку P&L.
- **Форматы отчёта** (`PnlSheetMapping`, значения читает `PnlExtraction`):
  - строки — контрагенты, столбцы — строки P&L (`dealerColumn` + `valueColumns`), например база продаж: «Сумма Диллера» → `sales`,
    «Сумма завода» → `cost`;
  - длинная таблица: строка на операцию (`dealerColumn` + `lineColumn` + `valueColumn`) — реестр расходов, журнал рейсов;
  - выгрузка «P&L таблицей»: строки — статьи, столбцы — контрагенты (`lineColumn` + `firstDealerColumn`…`lastDealerColumn`, год и месяц).
  Строки отчёта с одним контрагентом, месяцем и строкой P&L складываются, только если `sumRows = true` (реестр, база, журнал); иначе разные
  значения — конфликт. Столбец «Итого» и строки «Итого» не загружаются.
- **Сверка.** Расчётные строки из отчёта (валовая, маржа, ROS, EBIT, EAT) не пишутся: план изменений сравнивает их с расчётом OneBase и
  показывает расхождения («Сверка расчётных строк отчёта»). Новый контрагент, похожий на уже загруженного («Бобур (Самарканд)» и «Бобур
  Самарканд»), — предупреждение; модель сопоставляет его через `dealerMap`. `compare_pnl_primary` сравнивает продажи P&L с первичкой OneBase
  (отгрузка завода по цене дилера из Linko) по контрагентам. После применения `verify_change_set` перечитывает значения и пересчитывает
  итоги месяца тем же кодом, что страница.
- **Режим `replace`** удаляет значения тех же месяцев и тех же строк P&L, которых нет в отчёте: реестр расходов не трогает продажи.
- Группы РМ на странице — направление региона дилера (дилер региона из справочника или регион в имени: «Бобур Самарканд» → Самарканд);
  остальные — «Прочие контрагенты».

## Применение, проверка, откат

- **Применение** — одна транзакция `Serializable`:
  - план «захватывается» условным `UPDATE … WHERE Status = Draft`: двойное нажатие и параллельный запрос не применят его дважды;
  - перед записью каждое значение сверяется с «было». Если данные изменились после подготовки, ничего не пишется, план получает статус **Stale**, и его нужно подготовить заново;
  - ошибка записи откатывает весь план.
- **Проверка** (`verify_change_set`, автоматически после применения):
  - значения перечитываются из базы;
  - кэш отчётов сбрасывается, и месяц пересчитывается `SalesDataLoader`: план региона в расчёте должен совпасть с итогом плана изменений;
  - расхождения попадают в `Verification`.
- **Откат** — тоже одна транзакция:
  - «было» возвращается только там, где сейчас всё ещё «стало»;
  - строки, которые с тех пор изменил кто-то другой, остаются как есть (`RollbackConflict`, статус **PartiallyRolledBack**).
- **Журнал**:
  - `ai.DataChangeSets` / `ai.DataChangeItems`: кто подготовил, кто и когда применил или откатил, файл, период, каждая строка «было → стало», статус строки;
  - аудит в `AuditLogs` — `ai.data.file_uploaded`, `ai.data.prepared`, `ai.data.applied`, `ai.data.stale`, `ai.data.rolled_back`, `ai.data.cancelled`, `ai.data.tool.denied`, `ai.data.*_failed`;
  - токены и стоимость — в `ai.Usage` и журнале AI (вид `data-manager`).

## Безопасность

- Права: всё — раздел, чтение данных продаж инструментами, подготовка, подтверждение и откат — по одному праву `ai.data.manage`.
  Других прав на продажи не нужно; при подтверждении право перепроверяется по базе.
  - У «Администратора» право есть автоматически.
  - Роль **«Админ 2»** (системная, отдел «Продажи»): `files.read`, `files.write`, `ai.data.manage`. В меню — «Файлы» (только папка «Продажи»)
    и «AI Data Manager», в «Настройках» — только AI Data Manager. Общие разделы (Обзор, Отделы, Задачи) скрыты и с главной ведут в «Файлы».
  - Меню слева строится по правам (`frontend/src/lib/navigation.ts`): пункт виден, если раздел доступен.
- Пользователь и права берутся из сессии и базы, а не из ответа модели. Файл видит только загрузивший, чат — только его автор. Идентификаторы файлов и планов от модели проверяются по этому контексту.
- Prompt injection:
  - содержимое файла передаётся модели как данные (`<report_data>`), системная подсказка запрещает выполнять «команды» из ячеек;
  - даже выполнив такую «команду», модель может только подготовить черновик — применить его без человека нельзя.
- Ограничения:
  - файл до 20 МБ, только `.xlsx/.xlsm/.csv/.txt`;
  - до 20 000 строк и 60 столбцов на лист;
  - до 5 000 строк в плане и 24 месяцев;
  - результат инструмента до 30 000 символов;
  - 20 запросов в минуту на пользователя (политика `ai`).
- Ключ Claude хранится на сервере: «Настройки → AI → Провайдеры» (зашифрован) или `ANTHROPIC_API_KEY`. В браузер и журналы он не попадает.

## Настройка

1. Ключ Anthropic: «Настройки → AI → Провайдеры → Anthropic» (или `ANTHROPIC_API_KEY` в `.env`). AI должен быть включён в «Настройки → AI».
2. По желанию — `DATA_MANAGER_MODEL` (по умолчанию `claude-opus-5-5`) и секция `DataManager` в `appsettings.json`:
   - `Effort`, `MaxSteps`, `TurnTimeoutMinutes`, `RetryDelaySeconds`;
   - `MaxFileBytes`, `MaxRowsPerSheet`, `MaxColumns`, `MaxChangeItems`.
3. Миграция `DataManager` создаёт таблицы `ai.DataConversations`, `ai.DataMessages`, `ai.DataFiles`, `ai.DataChangeSets` и `ai.DataChangeItems`. Применяется при старте API.

## API (`/api/data-manager`, право `ai.data.manage`)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `status` | готов ли Claude API, модель, форматы, лимит файла |
| GET, POST | `conversations` | список чатов; создать пустой чат |
| GET, PATCH, DELETE | `conversations/{id}` | чат с сообщениями, файлами и планами; переименовать; убрать из истории |
| POST | `files` (multipart: `file`, `conversationId`) | загрузить отчёт |
| POST | `chat` (`conversationId`, `message`, `fileIds`) | ход модели, text/event-stream: `start`, `step`, `changeset`, `done` / `error` |
| GET | `change-sets?conversationId=&take=`, `change-sets/{id}` | журнал операций, план изменений |
| POST | `change-sets/{id}/apply` | подтвердить (SSE: `changeset`, `event`, итог модели, `outcome`) |
| POST | `change-sets/{id}/rollback` | откатить (SSE) |
| POST | `change-sets/{id}/cancel`, `change-sets/{id}/verify` | отменить черновик; проверить ещё раз |
