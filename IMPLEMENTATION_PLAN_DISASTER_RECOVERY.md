# OneBase — Disaster Recovery: аудит и план

Цель: если сервер уничтожен целиком (Docker, тома, PostgreSQL, MinIO, Qdrant, Redis, сам проект), поднять OneBase на чистом
Ubuntu Server из резервной копии в том же состоянии — пользователи входят теми же сессиями, видят те же данные, файлы,
базу знаний, настройки и интеграции.

Статус: этапы 0 (аудит и план), **1 (полная копия)** и **2 (режим изоляции и проверка копии в API)** готовы —
[отчёт этапа 1](ONEBASE_DISASTER_RECOVERY_STAGE1_REPORT.md), [отчёт этапа 2](ONEBASE_DISASTER_RECOVERY_STAGE2_REPORT.md), инструкция —
[docs/disaster-recovery.md](docs/disaster-recovery.md). Production не менялся.

Решение 07.11.2026: **копии пока хранятся только на сервере** (D1). Внешнее хранилище — этап 6, отложен; формат набора копии
от него не зависит, подключить хранилище можно позже без переделок.

## 1. Что есть сейчас

Восстановление сейчас — `deploy/restore-db.sh`: только база и только в пустую.

**Вывод:** при гибели сервера сейчас теряются все резервные копии, все файлы, векторы базы знаний, ключ JWT и токен
туннеля. Восстановимо только то, что лежит в GitHub.

### Найденные риски, которые план закрывает

1. **Копии на том же сервере.** По решению D1 так и остаётся на первое время: при гибели сервера вместе с ним пропадут и
   копии. Смягчение без внешнего хранилища — каталог копий на отдельном диске (`--dir`) и ручное скачивание свежего набора
   (`scp`, команда — в инструкции); набор зашифрован, поэтому его можно держать где угодно.
2. **Дамп не зашифрован, а ключи DataProtection лежат в нём же.** Утечка дампа = утечка всех токенов интеграций и
   персональных данных. Копия должна быть зашифрована ключом, которого нет на сервере.
3. **Двойник в Telegram.** Сессия Telegram в базе. Если восстановленная копия подключится, пока жив старый сервер (или
   при тестовом восстановлении), Telegram увидит один ключ авторизации с двух мест и может разорвать сессию — сломается
   рабочий Telegram-агент.
4. **Тестовая копия пишет живым людям.** Push-подписки, Telegram-отчёты и рассылки, напоминания — в базе. Тестовое
   восстановление без изоляции отправит уведомления настоящим сотрудникам и запустит синхронизации Linko, Google-таблиц,
   Verifix и платный AI-анализ.
5. **Два коннектора одного туннеля.** Тот же `CLOUDFLARE_TUNNEL_TOKEN` на двух серверах — Cloudflare делит трафик между
   ними. Production-восстановление должно требовать подтверждения, что старый сервер выключен.
6. **`cloudflared:latest`** не закреплён — версия на новом сервере будет другой (некритично, но фиксируем в манифесте).

### Хорошая новость: DNS при новом IP менять не нужно

Cloudflare Tunnel — исходящее соединение с сервера. С тем же токеном новый сервер подключается к тому же туннелю, и все
домены (основной, `sales.`, домен файлов) открываются без правок DNS, на любом IP. Правки нужны, только если токен
потерян и туннель создаётся заново: тогда Restore Engine показывает, какие Public hostname завести (`nginx:80`, `nginx:81`,
`nginx:82`). DNS автоматически не меняется.

## 2. Состав полной копии

Набор копии — папка `onebase-backup-ГГГГ-ММ-ДД_ЧЧММ/`:

| Файл | Что | Зашифрован |
|---|---|---|
| `payload.tar.age` | всё содержимое (ниже) | да, `age` |
| `payload.tar.age.sha256` | контрольная сумма зашифрованного файла — проверка до расшифровки | нет |
| `manifest.public.json` | время, версия OneBase (коммит), версии компонентов, размеры, SHA-256 payload, отпечаток ключа получателя. Без персональных данных и секретов | нет |
| `onebase-restore` | копия Restore Engine той же версии — чтобы восстановить без GitHub | нет |

Внутри `payload.tar`:

| Путь | Содержимое |
|---|---|
| `manifest.json` | полный манифест: версии (коммит, образы с digest, PostgreSQL, Qdrant, MinIO, Docker, ОС), **число строк всех таблиц** на момент дампа, список миграций, число и объём объектов MinIO, коллекции Qdrant (точки, размерность, метрика), SHA-256 каждого файла копии |
| `postgres/onebase.dump` | `pg_dump -Fc` в снимке, экспортированном `pg_export_snapshot()` — счётчики строк считаются в том же снимке, поэтому сверка после восстановления точная |
| `postgres/globals.sql` | роли кластера (`pg_dumpall --globals-only`, без паролей) |
| `minio/onebase-files/…` | все объекты бакета |
| `minio/objects.tsv` | ключ, размер, SHA-256, Content-Type каждого объекта |
| `qdrant/onebase_knowledge.snapshot` | снимок коллекции (REST API Qdrant) |
| `config/env` | `.env` сервера |
| `config/crontab`, `config/host.json` | расписание копий, версия ОС, Docker, Compose |
| `source/onebase.bundle` | `git bundle` текущего коммита — восстановление без GitHub |

Redis в копию **не входит**: там только кэш, который сам наполнится. Docker-образы api/web по умолчанию собираются заново
из `source/` (флаг `--with-images` — сохранить и их, тогда восстановление не зависит от npm/NuGet).

Порядок съёмки: база → MinIO → Qdrant. Файл, удалённый между дампом и копированием MinIO, — единственное возможное
расхождение; проверка после восстановления считает ссылки `ObjectKey` без объекта и показывает их.

## 3. Ключи и внешние секреты

**В копии (зашифровано):** `.env` (ключ JWT, токен туннеля, пароли сервисов), ключи DataProtection (в базе), а через них —
все токены интеграций и сессия Telegram.

**Вне копии — нужно администратору при восстановлении:**

1. **Ключ восстановления** — закрытый ключ `age`. На сервере лежит только открытый: сервер шифрует копии, но расшифровать
   их не может, и взлом сервера не раскрывает копии. Две копии закрытого ключа: менеджер паролей и бумага/флешка в сейфе.
   **Без него копию не расшифровать — это сделано намеренно.**
2. **Сам набор копии.** Пока копии только на сервере (D1), на новый сервер его переносят вручную — из того места, куда
   администратор его скачал. После этапа 6 — доступ к внешнему хранилищу.
3. **SSH к новому серверу.**
4. Доступ к Cloudflare — только если токен туннеля нужно выпустить заново.

Правило Restore Engine: если нужного ключа нет, восстановление **останавливается и просит его**, а не генерирует новый.
Исключение только с явным флагом: `--accept-new-jwt-key` для старых копий без `.env` (пользователи заново войдут, данные
не теряются). Новый ключ DataProtection не генерируется никогда: если в базе есть зашифрованные секреты, а таблица ключей
пустая — стоп.

## 4. Архитектура

```
Сервер (каждую ночь, cron)                                   Новый сервер
onebase-backup ──► набор копии в ~/onebase-backups/ ──────►  onebase-restore
                   (age, SHA-256, 14 последних)   вручную     ├─ проверка и расшифровка
                            ┆                    (scp)        ├─ Docker, тома, сервисы
                            ┆ этап 6, позже                   ├─ Health Check
                            └┄┄► внешнее хранилище            └─ Recovery Report
```

**`onebase-backup`** (замена `deploy/backup.sh`, старый скрипт остаётся рабочим): блокировка от двух запусков →
предпроверка места → снимок базы и счётчики → копия MinIO → снимок Qdrant → `.env`, crontab, `git bundle` → манифест и
SHA-256 → шифрование `age` → проверка готового набора → ротация (только с `--keep N`, только наборы этого инструмента, только
после успешного нового; старые `*.dump` не трогаются). Незавершённый набор пишется в `*.partial` и не выглядит готовым;
открытые данные во временном каталоге удаляются при любом исходе. Журнал без секретов. Статус последнего запуска —
`last-backup.json` (позже его покажет раздел «Резервные копии»).

**`onebase-restore`** — Restore Engine. Python 3 только со стандартной библиотекой (есть в любом Ubuntu Server) и тонкая
обёртка `onebase-restore`. Шаги и статусы `Pending / Running / Completed / Failed / Skipped` — в журнале
`/var/lib/onebase-restore/<запуск>/state.json`, лог — рядом, секреты в лог не попадают (маскирование по значениям из `.env`
и по шаблонам ключей).

```
onebase-restore --backup /backups/onebase-backup-2026-11-07_0300 [--key /root/recovery.key]
                [--mode drill|production] [--target /opt/onebase] [--from-remote <rclone-путь>]
                [--dry-run] [--resume] [--ui] [--check-ai] [--with-images]
```

| # | Шаг | Компонент в отчёте | Если ошибка |
|---|---|---|---|
| 1 | Аргументы, root, Ubuntu 22.04/24.04, x86_64, память ≥ 4 ГБ, место ≥ 3× объёма копии, свободные порты | Infrastructure | стоп до начала |
| 2 | Есть ли уже OneBase (каталог, проект compose `onebase`, тома) — **есть → отказ**; перезапись только `--mode production --overwrite` и ввод фразы подтверждения | Infrastructure | стоп |
| 3 | SHA-256 зашифрованного файла, расшифровка `age` во временный каталог `0700`, SHA-256 каждого файла по манифесту | Verification | стоп: повреждённую копию не восстанавливаем |
| 4 | Совместимость: PostgreSQL 16, Qdrant 1.19.x (снимок привязан к версии), образы по digest из манифеста | Compatibility | стоп |
| 5 | Docker CE + Compose из репозитория Docker, `age` — если нет | Infrastructure | стоп |
| 6 | Код из `git bundle` на коммит копии, `.env` из копии (`chmod 600`), тома | Infrastructure | стоп |
| 7 | PostgreSQL: пустая база → `pg_restore --exit-on-error` → сверка строк всех таблиц | PostgreSQL | стоп зависимых |
| 8 | MinIO: бакет → загрузка объектов → сверка числа, размеров и SHA-256 | MinIO | стоп зависимых |
| 9 | Qdrant: загрузка снимка → сверка точек и параметров коллекции | Qdrant | стоп зависимых |
| 10 | Redis: чистый (по манифесту — только кэш) | Redis | — |
| 11 | Сборка (или загрузка) образов api/web, запуск api: миграции не нужны — база на той же версии; `/health` | Backend | стоп |
| 12 | web, nginx: `/login`, `/health`, Sales Base `:81`, файлы `:82` | Frontend, Admin, Nginx | стоп |
| 13 | **production:** подтверждение «старый сервер выключен» → `cloudflared`, интеграции. **drill:** туннель и интеграции не запускаются никогда | Integrations | — |
| 14 | Health Check и Recovery Report | — | отчёт с причиной |

Повторный запуск `--resume` продолжает с упавшего шага; повторяемые шаги безопасны. Шаг базы переделывается, только
если эту базу создал тот же запуск (метка в журнале). Исходная копия не удаляется никогда; удаляется только временная
расшифрованная копия по окончании. Итог `Completed` ставится только если все обязательные шаги и проверки прошли —
иначе `Failed` с причиной.

**Режим изоляции** (`--mode drill`, по умолчанию) — новый флаг API `Recovery__Isolated=true`: выключает всё, что выходит
наружу — Telegram (подключение, отчёты, агент, рассылки), Linko, Google-таблицы и журнал склада, Verifix, push, напоминания,
проактивный AI-анализ и план дня, AI-вызовы из интерфейса. В интерфейсе — плашка «Копия для проверки: внешние интеграции
выключены». Без этого флага тестовое восстановление настоящей копии запрещено.

**Recovery Center** — два места:

- **Во время аварии** OneBase ещё нет, поэтому страницу показывает сам движок: `onebase-restore --ui` → `127.0.0.1:8090`
  с одноразовым токеном (доступ через `ssh -L 8090:127.0.0.1:8090 сервер`). Разделы: Upload Backup, Select Backup, Backup
  Verification, System Compatibility, Recovery Configuration, Restore Progress (по 10 компонентам), Recovery Logs, System
  Health Check, Recovery Report. Браузер только отправляет команды и показывает журнал — работает серверный процесс, закрытие
  вкладки восстановление не прерывает. Разрушительные шаги — только после ввода фразы подтверждения.
- **В рабочем OneBase** — «Настройки → Резервные копии» (администратор): последние копии (время, размер, проверка SHA-256,
  выгружена ли во внешнее хранилище), последний отчёт учебного восстановления, тревога, если копии не было больше суток.

**Health Check** (после восстановления; результат каждой проверки — в отчёт):

- PostgreSQL отвечает; таблиц и строк в каждой таблице — как в манифесте; миграции те же.
- Пользователи, роли, сессии, сотрудники и подразделения — числа совпадают.
- Ключи DataProtection: тестовая расшифровка каждого типа секрета (AI, Linko, Telegram, Google, Verifix, файлы, VAPID) —
  без вывода значений. Это и есть доказательство, что интеграции восстановимы.
- MinIO: объекты, размеры, SHA-256 — как в `objects.tsv`; у каждой ссылки `ObjectKey` в базе есть объект; файл скачивается
  через API.
- Qdrant: коллекция, число точек, параметры; поиск по вектору одной из точек находит её же (без платных вызовов).
- Backend `/health`, Frontend `/login`, «Настройки» открываются, Sales Base `:81`, WebDAV `:82`.
- Авторизация: сессия, выданная до копии, действует после (ключ JWT восстановлен); вход логином и паролем — в учебном
  восстановлении на учебном пользователе.
- История операций: журнал аудита и последние записи складов, задач, продаж — на месте.
- AI Consultant: по умолчанию — проверка настроек и расшифровки ключа; живой вопрос — только с `--check-ai` (платный вызов).
- Telegram и Linko: в drill — сессия и токены есть и расшифровываются; в production — после запуска статус подключения.

**Recovery Report** — `report.json` и `report.html`: каждый шаг (время, длительность, статус), каждая проверка, что требует
ручного действия (например, «войдите под своим логином», «туннель создан заново — заведите Public hostname»).

## 5. Учебное восстановление (обязательный тест)

Только на этом ПК, только в изолированной среде; production и локальный Docker Desktop (`onebase-postgres-1` и др.) не
трогаются.

1. Два чистых дистрибутива WSL2 из официального образа Ubuntu 24.04: `onebase-dr-src` и `onebase-dr-dst` в отдельной
   папке. В каждом — свой Docker CE (не Docker Desktop: интеграция с другими дистрибутивами выключена, сеть WSL — NAT, порты
   не пересекаются с Docker Desktop).
2. В `onebase-dr-src` — OneBase с нуля и учебные данные: пользователи и роли, отделы и сотрудники, задачи с вложениями,
   файлы отделов, снабжение и сырьё, документы базы знаний с векторами (без платных эмбеддингов), учётная запись Telegram с
   учебной зашифрованной сессией, учебные токены Linko и AI, журнал аудита. Никаких настоящих данных и токенов.
3. `onebase-backup` → набор копии → скопировать в Windows-папку.
4. «Сервер уничтожен»: `wsl --unregister onebase-dr-src`.
5. `onebase-dr-dst`: ничего, кроме Ubuntu. Скачать `onebase-restore`, запустить на копии.
6. Сверка: строки всех таблиц, SHA-256 всех файлов, точки Qdrant, расшифровка секретов, вход учебным пользователем,
   сессия «до аварии» действует, открытие файлов, база знаний.
7. Время каждого шага и общее время восстановления → `ONEBASE_DISASTER_RECOVERY_DRILL_REPORT.md`.

По желанию — второй прогон на копии **настоящей** системы (её снимает сам администратор на сервере новым
`onebase-backup`), только в режиме drill.

## 8. Ограничения

- Внешнее хранилище и ключ восстановления — на стороне администратора; без них восстановление невозможно по замыслу.
- Состояние между ночными копиями теряется (RPO — до суток). Чаще — дамп базы каждый час, файлы инкрементально: при
  необходимости отдельным этапом.
- Тестирование — на WSL2 Ubuntu, не на «железном» Ubuntu Server; различия (systemd, диски) проверяются отдельно в
  предпроверках.
- Сессия Telegram может потребовать повторного входа, если Telegram сочтёт смену сервера подозрительной — тогда это
  отмечается в отчёте как «требует переподключения».

## 9. Что не делается никогда

`docker compose down -v`, удаление томов Docker, `git reset --hard`, `git clean -fd`, правка существующих `.env`, смена
действующих паролей и секретов, восстановление на production для проверки, удаление копий, необратимые шаги без
подтверждения, платные вызовы AI без разрешения.
