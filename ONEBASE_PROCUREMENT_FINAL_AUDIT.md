# Снабжение (Procurement Management) — финальный аудит

Дата: 01.11.2026. Основа — аудит и отчёты этапов 1–6 ([аудит](ONEBASE_PROCUREMENT_AUDIT.md), [1](ONEBASE_PROCUREMENT_STAGE1_REPORT.md), [2](ONEBASE_PROCUREMENT_STAGE2_REPORT.md), [3](ONEBASE_PROCUREMENT_STAGE3_REPORT.md), [4](ONEBASE_PROCUREMENT_STAGE4_REPORT.md), [5](ONEBASE_PROCUREMENT_STAGE5_REPORT.md), [6](ONEBASE_PROCUREMENT_STAGE6_REPORT.md)).

**Итог одной строкой:** основной бизнес-сценарий — от групповой заявки до выдачи цеху, с аналитикой, уведомлениями и AI — проходит сквозной тест на PostgreSQL. 24 из 26 сценариев ТЗ подтверждены тестами. Оплаты (сценарии 17–18) не реализованы — по решению отложены до модуля «Финансы». Поэтому модуль готов к опытной работе **без оплат**, но не объявляется готовым полностью.

## Как проводился аудит
- **Сценарии ТЗ** сопоставлены с тестами этапов 1–6.
- **Сквозной тест** основного сценария (`ProcurementEndToEndDbTests`) добавлен: одна цепочка от заявки до выдачи, на каждом шаге — запреты из раздела «Особое внимание», права берутся из ролей в базе.
- **Сборки и тесты:**
  - `dotnet build`, `dotnet test` (все проекты);
  - нагрузочный тест (`ONEBASE_PERF=1`);
  - `npx tsc`, `npm test`, `npm run build`.
- **Миграции:** SQL пяти миграций снабжения сгенерирован и просмотрен; проверено, что модель совпадает с миграциями.
- **API вживую** (локальный сервер):
  - 26 GET-эндпоинтов — с токеном и без;
  - все 81 действие проверены на авторизацию;
  - пишущие запросы вживую не отправлялись, чтобы не менять данные пользователя, — они проверены тестами.
- **Интерфейс:** все 20 страниц «Заявок» и «Снабжения» на 1440 и 390 px, RU и узбекский кириллицей — ошибки консоли и API, горизонтальная прокрутка.
- **Безопасность и логирование:** авторизация, сырой SQL, проверки прав в сервисах, журнал истории, лог API.

## 1. Что реализовано
| Этап | Что есть |
|---|---|
| 1. Заявки | черновик и отправка, групповые заявки (до 100 позиций), вложения, номера без дублей, свои / отдела / все, история |
| 2. Склад и согласование | каталог, остатки, резерв под заявку, выдача, приход, списание, инвентаризация, журнал движений; утверждает только роль «Директор»; повторное согласование при существенной правке |
| 3. Поставщики и заказы | реестр (импорт CSV / Excel, ИНН без дублей), коммерческие предложения и сравнение, заказы (одна заявка — несколько заказов, один заказ — несколько заявок), согласование заказа директором выше допуска, задачи снабжения в «Задачах» |
| 4. Приёмка | черновик и подтверждение кладовщиком, брак и недостача — претензии, частичные поставки, закрытие остатка, рейтинг поставщика, уведомления всем участникам; **оплаты отложены** |
| 5. Контроль | обзор по ролям, KPI из данных, ежедневная сводка (уведомление + журнал), эскалация просрочек, 8 отчётов в Excel и PDF, заявка в Word, акт приёмки в PDF |
| 6. AI | Supply AI с 12 инструментами только для чтения, маршрутизация, рекомендации, быстрые вопросы |

## 3. Какие ошибки исправлены
**В ходе аудита:**
- **История изменений правил.** Изменения настроек снабжения (допуск повторного согласования, пороги эскалации), категорий и карточек склада (в том числе минимального остатка) не оставляли следа. Теперь они пишутся в общий журнал аудита OneBase со значениями «было / стало». Добавлен тест.

Сквозной тест других ошибок в модуле не нашёл: три его первых падения были неверными ожиданиями в самом тесте (тип отказа при лишней приёмке; администратор как обычная роль вместо системной). Они исправлены в тесте.

**На этапах 1–6** (подробно — в отчётах этапов). Главное:
- **Двойное резервирование:** параллельные приёмки упирались в уникальный индекс резерва — добавлен повтор при конфликте.
- **Сравнение предложений:** отклонённые предложения выпадают из «лучших».
- **Заявка в Word:** подчёркивания в строках подписей ломали разметку.
- **Узбекский перевод:** серверные тексты с «{status}» не переводились после нового правила — исправлено при слиянии с узбекской кириллицей.
- **Маршрутизация AI:** «заказ поставщику» давал ложное «нет доступа к заказам продаж».

## 4. Какие проблемы остались
| Проблема | Влияние | Что делать |
|---|---|---|
| Нет оплат поставщикам (сценарии 17–18, права на оплату) | расходы — по заказанному и принятому, не по оплаченному | реализовать вместе с модулем «Финансы» |
| Не проверено вживую в браузере: действия директора, приёмка и графики с данными | в локальной базе нет закупок и пользователя с ролью «Директор» (выдача роли не разрешена) | проверено тестами; посмотреть на пилоте |
| Ответ Supply AI настоящей моделью не проверен | платные вызовы не разрешены, в локальной базе нет ключа | разрешить 1–2 пробных вопроса или проверить на пилоте |
| Позиции без карточки склада сравниваются по названию | разные названия одного товара — разные позиции в истории цен | заводить карточки склада для повторяющихся закупок |
| Описания инструментов снабжения уходят и в вызовы других AI-сотрудников (так устроен OneBase) | ≈ 5,7 тыс. токенов на вызов у директора и снабжения (с кэшем — по цене чтения кэша) | при необходимости отключить источник «Снабжение» у отдельных AI-сотрудников |
| Нет ESLint и мобильного приложения | — | вне модуля |
| Изменения ещё не на production | — | миграции применяются при запуске API; выкладка — с вашего отдельного разрешения |

## 7. Какие права реализованы
| Право / роль | Что даёт |
|---|---|
| `procurement.request` — «Заявки: свои заявки» | создавать свои заявки, видеть свои; руководитель отдела — заявки отдела |
| `procurement.read` — «Заявки: все заявки компании» | все отправленные заявки, заказы, поставщики, отчёты, аналитика, AI-цены и расходы |
| `procurement.manage` — «Снабжение: обработка заявок» | передавать директору, возвращать, вести поставщиков, предложения и заказы, решать претензии |
| `procurement.settings` — «Заявки: категории и правила» | категории, допуск повторного согласования, пороги эскалации |
| `procurement.warehouse` — «Склад снабжения» | каталог, приход, выдача, списание, инвентаризация, приёмка товара |
| Роль «Директор» (не право) | утверждать, отклонять, возвращать заявки и заказы на согласовании; обзор директора |
| Руководитель отдела снабжения (`WorkDepartmentHeads`) | обзор руководителя, сводка, эскалация с 1 дня |
| Системная роль «Администратор» | права есть, но утверждать не может и рабочих уведомлений снабжения не получает |

Роли по умолчанию:
- **сотрудники отделов** — `request`;
- **«Снабжение»** — `read` + `manage`;
- **«Кладовщик»** — `warehouse`;
- **«Директор»** — `request` + `read` + `settings`.

## 9. Рекомендации для следующего этапа
1. **Модуль «Финансы» и оплаты поставщикам:** частичная и полная оплата, права на оплату, расходы по оплаченному, сроки оплаты в рейтинге поставщика.
2. **Пилот на production** с одним отделом и директором — после вашего разрешения на выкладку:

4. **Сводка в Telegram** — отложенное решение этапа 5, когда понадобится.
5. **ESLint во фронтенде** — общий вопрос OneBase.
