# Этап 1 — сервер: приезд машины, качество до склада, приёмка с весом

Дата: 09.11.2026. План — [ONEBASE_ARRIVAL_PLAN.md](ONEBASE_ARRIVAL_PLAN.md).

## Что сделано

### Поставка AR-

`ProcurementArrival` и `ProcurementArrivalLine`.

- **Статусы:**
  - на проверке качества;
  - готово к приёмке;
  - принято;
  - возврат;
  - отменена.
- **Машина:** госномер, водитель, накладная, кто и когда отметил.
- **Строка:**
  - позиция тендера (одна партия поставщика), по накладной — в единице тендера и в единице карточки;
  - партия поставщика, дата изготовления, срок;
  - контроль и проверка;
  - решение;
  - при приёмке — места, вес, на склад, партия.

### «Машина приехала» — `RegisterAsync`

- Отмечает только кладовщик склада. Склад при этом не меняется.
- Сверх остатка по тендеру не отметить; уже привезённое на приёмку тоже вычитается.
- У позиции с партиями обязателен срок или дата изготовления при сроке хранения.
- По строке с контролем заводится QC- без партии — в той же очереди «Качество».
- Уведомления:
  - лаборатории и назначенным — «Приехала машина — проверьте качество»;
  - тому, кто вёл тендер, — «Машина приехала».
- Повтор формы возвращает ту же поставку.

### Проверка качества до склада — `ProcurementQualityService`

- У проверки теперь `ItemId`, `SupplierId` и `ArrivalId`; `BatchId` стал необязательным.
- Шаги и права те же.
- Проба только записывается: товара на складе ещё нет, документа WO- не создаётся.
- Решение по строке:
  - решено по всем, есть допущенное — «Готово к приёмке», кладовщикам приходит «Можно принимать»;
  - забраковано всё — «Возврат», кладовщикам приходит «Не разгружать — вернуть поставщику»;
  - забракованное — снабжению: «Забраковано при приёмке».
- Два одновременных решения по одной поставке не оставят её «на проверке»: защищает версия поставки.

### «Принять на склад» — `AcceptAsync`

- Принимает кладовщик склада. Обязательна каждая допущенная строка; забракованную не принять.
- **Места и вес:**
  - у весовой карточки (кг, г, т), если тендер в другой единице, нужны места и вес нетто: на склад идёт вес, тендеру засчитываются места;
  - ничего не принято по строке — только с причиной.
- **Одной записью:**
  - приход RC- по цене тендера;
  - партии — сразу допущенные, со ссылкой на проверку (и проверка — на партию);
  - «поставлено» у тендера, а если поставлено всё — тендер поставлен;
  - в истории — расхождения с накладной («недостача 60 кг»).
- **«Принято на склад»** получают:
  - снабжение: кто вёл тендер и все с правом обработки;
  - аналитики;
  - финансист маршрута, а пока он не выбран — роль «Финансы»;
  - автор заявки тендера.

  Принявшему уведомление не приходит.
- Повтор и двойное нажатие возвращают тот же приход. Приход по тендеру, как и раньше, не сторнируется.

### Остальное

- **Отмена** до приёмки — кладовщик склада или снабжение, с причиной. Открытые проверки закрываются, остаток по тендеру снова свободен.
- **Рейтинг поставщика** и отчёт «Проверки» считают по поставщику проверки — значит, и брак при приезде, который на склад не попал.
- **Ожидаемые поставки** — `ExpectedAsync`: тендеры, где поставлено не всё. Сначала просроченные, дальше по сроку. У каждого — сколько уже
  на приёмке и может ли пользователь отметить приезд.

### API

| Метод | Адрес | Что делает |
|---|---|---|
| GET | `/api/procurement/arrivals/expected?tender=&take=` | ожидаемые поставки |
| GET | `/api/procurement/arrivals?status=open\|quality\|ready\|accepted\|returned\|cancelled\|done\|all&q=&tender=` | список поставок |
| GET | `/api/procurement/arrivals/{id}` | карточка поставки |
| POST | `/api/procurement/arrivals` | «Машина приехала» |
| POST | `/api/procurement/arrivals/{id}/accept` | «Принять на склад» |
| POST | `/api/procurement/arrivals/{id}/cancel` | отмена поставки |

### Миграция `Arrivals`

- **Новые таблицы:** `procurement.Arrivals`, `procurement.ArrivalLines`.
- **Поля проверки:** у `QualityChecks` добавлены `ItemId`, `SupplierId`, `ArrivalId`; `BatchId` может быть пустым. Прежние проверки
  заполняются по своим партиям. Ничего не удаляется.
- **Откат:** `dotnet ef database update ProductionOutput`. Он возможен, пока нет проверок поставок без партии.

## Проверка

- **Сборка** без новых предупреждений.
- **Новые тесты** `ProcurementArrivalDbTests` на PostgreSQL — 2 сценария:
  1. Мука двумя партиями и сахар без контроля:
     - права и отметка сверх остатка;
     - склад не меняется до приёмки;
     - проба не списывается;
     - допуск и брак, уведомления;
     - на склад — 5 940 кг муки при 119 упаковках;
     - цена 6 200 сум/кг, сумма 45 828 000;
     - партия связана с проверкой;
     - повтор приёмки;
     - рейтинг поставщика.
  2. Брак целиком — возврат; отмена второй машины закрывает её проверку и освобождает остаток.

- **Временные базы** удалены: в Postgres только `onebase` и `postgres`.
