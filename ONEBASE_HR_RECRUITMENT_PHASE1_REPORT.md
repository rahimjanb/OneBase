# HR Recruitment — этап 1: маршрутизация диалогов Telegram по подразделениям

Дата: 08.11.2026. План — [IMPLEMENTATION_PLAN_HR_RECRUITMENT.md](IMPLEMENTATION_PLAN_HR_RECRUITMENT.md), описание для администратора —
[docs/telegram.md](docs/telegram.md), раздел «Подразделения и маршрутизация диалогов».

## Зачем

До этапа все входящие Telegram получал один потребитель — AI-агент продаж. Чтобы HR работал на той же инфраструктуре (вход, сессии,
приём, отправка) и при этом не смешивался с продажами, перед агентом нужен маршрутизатор: у каждого диалога — подразделение-хозяин.

Решение 08.11.2026 (Р1): у HR **отдельный номер**, подключённый тем же механизмом в «Настройки → Telegram». Второго входа, второй
сессии и второго клиента нет — это ещё один аккаунт в той же таблице, у которого в «Подразделениях» выбран HR.

## Что сделано

| Часть | Как |
|---|---|
| Подразделения аккаунта | `telegram.AccountDepartments`: для кого работает номер и кому новые диалоги. **Не заданы — всё как раньше**: каждый диалог у продаж, диалоги не записываются |
| Хозяин диалога | `telegram.Conversations` (уникально аккаунт × чат): подразделение или «не распределён», причина, режим (AI / ведёт человек), ответственный, связанная запись (у HR — вакансия), время последнего сообщения |
| Маршрутизатор | `TelegramMessageRouter`: закреплённый диалог — хозяину; новый — по признаку подразделения в первом сообщении, иначе — подразделению по умолчанию; признаки двух подразделений и люди из списка агента продаж — «не распределён», решает человек |
| Обработка входящих | `TelegramAgentWorker`: очередь чата строго по порядку, общая для всех подразделений; слоты подразделений раздельные (продажи — 4, остальные — 2); агент продаж — обработчик подразделения «Продажи» без изменений своих правил |
| Ручное управление | `TelegramConversationService`: передать диалог подразделению или оставить «не распределённым», остановить AI или вернуть — с записью в аудит |
| Номер HR и продажи | номер, который работает не для продаж, не предлагается и не принимается рассылками и автоотчётами продаж; агент продаж его сообщений не получает, даже если включён |
| «Ответ на сообщение» | `TelegramIncoming.ReplyToMessageId` из MTProto — HR по нему узнает ответ на пост вакансии (этап 3) |
| Интерфейс | «Настройки → Telegram» → аккаунт → «Подразделения»: галочки подразделений, «Новые диалоги», пометка «без AI-обработчика» (RU/UZ) |
| Выключатель | `Telegram:Routing:Enabled=false` — маршрутизатор не спрашивается, всё агенту продаж, как до этапа |

API (`/api/settings/telegram`, право `telegram.manage`): `GET|PUT accounts/{id}/departments`, `GET accounts/{id}/conversations?department=`,
`PUT accounts/{id}/conversations/{peerId}/department`, `PUT accounts/{id}/conversations/{peerId}/mode`.

База: миграция `TelegramConversations` — только две новые таблицы; существующие таблицы и данные не меняются. Откат —
`dotnet ef database update RawMaterialProduction`.

HR-логики на этапе нет: у HR пока нет AI-обработчика, поэтому диалоги номера HR **никто не отвечает автоматически** — номер можно
подключить заранее, кандидатам ничего не уйдёт. Обработчик и признаки HR (ответ на пост, код вакансии) появятся на этапе 3.

## Проверка

**Новые тесты** — `TelegramRoutingTests`, 11, все проходят (подставной Telegram и модель, PostgreSQL 16):

| Тест | Что доказывает |
|---|---|
| аккаунт без подразделений | сообщение через новый обработчик доходит до агента продаж, ответ тот же, что раньше; строк диалогов нет; маршрут — «как раньше» |
| номер HR | агент продаж на номере HR включён и «отвечает всем» — и не получает ни одного сообщения: нет ответа, нет записи входящего и журнала агента; диалог закреплён за HR; рассылки и автоотчёты продаж номер HR не показывают и не принимают |
| «не распределён» | никто не отвечает; после того как человек отдал диалог продажам, следующее сообщение отвечает агент продаж |
| признаки подразделения | признак HR открывает диалог за HR один раз, дальше признак продаж хозяина не меняет; признаки двух — «не распределён»; признак выключенного подразделения не считается; люди из списка агента продаж (по ID и ожидающие по username) — «не распределён»; свои исходящие диалог не открывают |
| ручное управление | назначить можно только включённое подразделение и только у аккаунта с подразделениями; «ведёт человек» — AI не отвечает, «вернуть AI» — отвечает; подразделение убрали у аккаунта — его диалоги «не распределены»; все изменения — в аудите по порядку |
| настройки подразделений | пусто, неизвестное подразделение, «по умолчанию» не из выбранных, чужой аккаунт — отказ; смена «по умолчанию» за одно сохранение, по умолчанию — одно |
| очередь и слоты | 10 сообщений одного чата — строго по порядку и по одному; пока HR занят тремя кандидатами (работают ровно 2 слота HR), продажи отвечают без задержки |
| выключатель | `Telegram:Routing:Enabled=false` — даже сообщение номера HR уходит обработчику продаж, диалоги не пишутся |
| «ответ на сообщение» | из MTProto берётся только ответ внутри того же чата |

**Все тесты бэкенда** на PostgreSQL 16: Files 41/41, Sales 461/461, AI 1131/1133 (2 — платные проверки моделей, пропускаются без

## Ограничения

- Очередь входящих по-прежнему в памяти: при падении сервера сообщения, которые ещё не дошли до обработчика, теряются (для продаж так
  было и раньше). Для кандидатов это закрывает этап 3: сообщения HR-диалогов сохраняются в базу сразу при получении.
- Список диалогов и ручная смена хозяина пока есть только в API; экран диалогов HR — этап 3.
- Номер HR, выбранный в автоотчётах до этого этапа, не отключается сам: при сохранении настроек автоотчётов он уже не принимается.
