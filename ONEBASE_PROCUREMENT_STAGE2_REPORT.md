# Снабжение, этап 2: склад и согласование директором — отчёт

Дата: 01.11.2026. Основа — аудит ([ONEBASE_PROCUREMENT_AUDIT.md](ONEBASE_PROCUREMENT_AUDIT.md)) и этап 1 ([ONEBASE_PROCUREMENT_STAGE1_REPORT.md](ONEBASE_PROCUREMENT_STAGE1_REPORT.md)).

## Что сделано

### Часть A. Склад
- **Каталог:** артикул (уникален), название, категория, единица, штрихкод, описание, минимальный остаток. Позиции не удаляются, а отключаются. Единицу нельзя сменить, если по позиции уже были движения.
- **Склад:** засевается «Центральный склад». Остаток хранит «на складе» и «в резерве»; доступно = на складе − в резерве.
- **Операции (кладовщик):**
  - приход — с ценой за единицу и номером накладной;
  - выдача отделу без заявки — отдел и кто получил;
  - списание — причина обязательна;
  - инвентаризация — по факту, разница идёт корректировкой;
  - выдача по заявке — из резерва, можно частями.
- **Документы:** номера `RC-`, `ISS-`, `WO-`, `INV-год-NNNNN`, ключ повтора формы: двойное нажатие не проводит документ дважды.
- **Журнал движений:** вид, количество ±, остаток до и после, документ, заявка, кто, отдел. Журнал не правится — исправление делается новым документом.
- **Защита остатков:**
  - проверка в `ProcurementStockLedger`: на складе не меньше нуля и не меньше резерва;
  - версия строки `xmin` и повтор операции при одновременном изменении;
  - последняя линия защиты — CHECK в базе (`OnHand ≥ 0`, `0 ≤ Reserved ≤ OnHand`).
- **Новая роль «Кладовщик» (`procurement.warehouse`):**
  - видит склад и заявки, где есть часть «со склада»;
  - утверждать заявки и менять цены не может.

### Часть B. Проверка склада в заявке
- Позицию можно выбрать из каталога: подсказки по артикулу и названию показывают доступное количество.
- Пример: запрошено 100, доступно 40. Система предлагает «со склада 40, к закупке 60».
- Если на складе есть, а сотрудник просит купить, нужно обоснование.
- **При отправке** часть «со склада» резервируется. Заявке, которая просит больше доступного, сервер отвечает 409: остаток мог уйти другой заявке.
- **Заявка только со склада** утверждается сама, без директора (решение 3 аудита), и уходит кладовщику на выдачу.
- **Резерв снимается** при отмене, отклонении и возврате на доработку. При повторной отправке он ставится снова.

### Часть C. Согласование директором
- **Кто утверждает:** только пользователь с ролью «Директор»; роль проверяется по базе на сервере.
  - Администратор со всеми правами, снабжение и инициатор при прямом вызове API получают 403.
- **Вкладка «Согласования»** видна только директору. Очередь показывает:
  - сумму к закупке и причину;
  - сколько заявка ждёт;
  - пометку о повторном согласовании.
- **В карточке заявки:**
  - позиции: со склада, к закупке, выдано, обоснование закупки;
  - блок «Согласование директора» со всеми раундами;
  - кнопки «Утвердить», «Отклонить» и «Вернуть на доработку». Комментарий обязателен при отказе и возврате.
- **Решение сохраняется** с раундом, комментарием, кто и когда, снимком позиций и суммой к закупке. Повторное нажатие ничего не меняет: одно решение на раунд.
- **Повторное согласование.** Правка утверждённой заявки снабжением возвращает её директору на новый раунд, если:
  - добавлены или удалены позиции;
  - сменился товар;
  - выросло количество к закупке;
  - цена или сумма выросли больше допуска.
  Уменьшение записывается только в историю. Допуск в процентах настраивает директор в «Заявки → Настройки»; по умолчанию 0 %.

### Часть D. Интеграция
- Заявка, склад и согласование связаны: резерв → выдача → статус заявки. «Частично выполнена» — пока часть к закупке не пришла. «Выполнена» — когда выдано всё.
- Заказ поставщику автоматически не создаётся: заказов ещё нет, это этап 3.
- **Уведомления:**

| Событие | Кому |
|---|---|
| Заявка со складской частью отправлена | кладовщику |
| Передана на согласование, в том числе повторное | директору |
| Утверждена | инициатору и снабжению |
| Отклонена, возвращена на доработку | инициатору и снабжению |
| Выдан товар со склада | инициатору |

## API (`/api/procurement`, новое)
| Метод и путь | Что делает |
|---|---|
| `POST requests/{id}/approve` | утвердить |
| `POST requests/{id}/reject` | отклонить |
| `POST requests/{id}/issue` | выдать по заявке |
| `GET`, `PUT settings` | допуск повторного согласования |
| `GET stock`, `GET stock/summary` | остатки и сводка |
| `GET catalog?q=` | поиск товара для формы |
| `GET items/{id}`, `POST items`, `PUT items/{id}` | карточка и правка каталога |
| `GET movements` | журнал движений |
| `GET stock/to-issue` | заявки к выдаче |
| `GET stock/departments` | отделы для выдачи |
| `POST stock/receipt`, `write-off`, `inventory`, `issue` | складские операции |

## Интерфейс
- **Меню:** новый пункт «Снабжение» (`/procurement`) с вкладками «Склад», «К выдаче» (со счётчиком) и «Движения».
- **Склад:**
  - плитки: позиций, ниже минимума, нет на складе, с резервом, заявок к выдаче;
  - поиск, категория, фильтры, таблица остатков;
  - карточка товара: остатки, резервы по заявкам, движения, правка;
  - операции — в шапке.
- **«Заявки»:** вкладка «Согласования» (только директору), «Категории» → «Настройки» (допуск и категории).
- **Форма заявки:** выбор товара из каталога, строка «на складе / со склада / к закупке», обоснование, сумма к закупке. Для снабжения есть режим правки утверждённой заявки с предупреждением о повторном согласовании.
- **Телефон:** нижний бар не изменился, «Снабжение» — в веере; кнопки операций — значками.

## Ограничения этапа 2
- **Склад один** (центральный); несколько складов и перемещения — позже.
- **Часть «к закупке»** после утверждения ждёт заказа поставщику и приёмки — это этапы 3–4. До этого заявка с закупкой не станет «Выполнена».
- **Уведомление «остаток ниже минимума»** — этап 5 (автоматизация). Сейчас низкий остаток виден на складе плиткой и фильтром.
